# 功能原理与数据契约

本文描述当前已实现并由公共行为测试覆盖的功能。分层与数据域见 [系统架构](architecture.md)；仍需真实
环境或上游能力的部分见 [当前路线图](roadmap.md)。

## 1. 账号、设置与工作台

应用以 `AppContext` 管理当前账号和 generation。账号数据库、截图与日志互相隔离；切换账号时先停止或
阻止后台任务，再重建同步、扫描、鉴定和战报依赖。旧 generation 的 worker 结果不更新页面或数据库。

主题写入 `config/global_ui_preferences.json`，对全部账号生效；旧账号主题只在全局文件首次建立时迁移。
计算偏好、基础权重、热键、扫描、倒带和 UI 选择按既定 key 写当前账号。工作台只读取账号摘要、环境状态
和当前稳定快照，不重新实现业务查询。

## 2. 库存同步与不可变快照

nte-core 库存事件经过收集、完整性检查和 `InventorySnapshotStabilizer` 内容稳定化后，一次事务提交装备、
词条、角色实例和当前指针。稳定判断使用完整内容指纹与安静窗口，不使用历史最大数量。

`inventory.get_latest` 读取最近捕获数据，不触发强制刷新。下游启动时解析一次当前 `snapshot_id`，运行中
不追随最新指针。快照清理保护当前快照、活动配装槽位、锁定方案和未完成任务引用。

账号 schema v21 支持原生库存的运行时状态增量。残缺装备事件只覆盖当前完整快照中已知正式 UID 的
`locked`、`discarded`、`equipped`、角色实例和位置；旧 sequence 不覆盖新状态，未知 UID 被忽略，库存
成员和当前快照指针不改变。极速装配和一键弃置/锁定的已接受指令也会写入相同的当前快照投影，供仓库立即
显示目标角色/状态；后续 nte-core 事件仍覆盖同一 UID。该投影不新增、删除装备，也不推进当前快照指针。

## 3. 视觉与手柄全量扫描

鼠标和虚拟手柄是同一视觉库存能力：

```text
mouse capture  ─┐
                ├→ 有界截图流 → OCR/解析 → 完整 vision snapshot
gamepad capture ─┘
```

扫描冻结账号、generation、用户库、截图目录、静态 dataset、解析 profile、捕获驱动、窗口和 token。
OCR 初始化在首次游戏输入前完成。取消、窗口变化、截图缺失、解析失败、索引不连续或数量不一致时保留旧
当前快照，不提交半成品。

### 3.1 鼠标捕获模型

- 基准画布为 2560×1440、7 列×4 行；坐标映射到客户区顶部对齐的 16:9 物理像素内容区。
- 首屏最多 28 件；后续每页跳过重叠首行并新增 3 行、最多 21 件。
- 鼠标与虚拟手柄全量扫描在各自既有导航前，均执行一次从上向下的长按滑动，使用与全自动增量扫描相反的两点方向重置列表位置。
- 鼠标全量扫描使用用户输入总数生成不可变分页计划；末页按总行数映射到底部对齐后的四行视窗，只点击该计划格位，并用连续占用检测复核数量。虚拟手柄扫描保持原有流程。
- 首次点击前对计划首屏执行格位预检，拦截错误页签、未加载、遮挡和整体偏移。
- 普通滚动 profile 为 `-280 × 7 + -120 × 2`；每第六次翻页使用累计补偿
  `-280 × 6 + -120 × 4`。滚轮 delta 不随分辨率缩放。
- 点击位置与时序在安全范围内随机；测试可注入固定 seed。每件截图仍保存完整客户区，以兼容统一解析器。
- 双线程模式使用单截图生产者、单 OCR 消费者和 21 张有界队列；兼容低负载模式使用更慢输入和串行解析。

当前自动化覆盖 1080p、2K、4K、2560×1600 顶部对齐、末页 1–21 件及底部对齐、2000 件分页、滚动补偿、随机安全
区、背压、取消和失败不提交。真实设备行为按 [Windows 验收](validation/windows.md) 记录。

### 3.2 扫描报告与扫描后管理

每次鼠标扫描原子更新账号截图目录中的 `mouse_scan_last_report.json`，记录分辨率、profile、预检计数、
分页、滚轮、预计/捕获数量、耗时和终止状态；不记录 UID、OCR 全文、截图内容或绝对路径。

启用扫描后管理时，完整视觉快照先提交，再根据同一次冻结扫描索引生成锁定/弃置计划。执行从最大索引
倒序回退，每件依次验证原始截图身份、操作前图标、动作和操作后图标。锁定切换弃置必须等待确认弹窗。
操作前图标与固定计划不一致时，该件不执行输入、记录后继续其余计划，并在扫描完成提示中汇总；定位、
身份、弹窗或操作后复核失败仍停止后续输入。

结果写 `mouse_state_sync_last_report.json`，保存聚合数量、状态迁移、状态不一致跳过项、耗时和安全错误类型。该会话能力
不把视觉临时 UID 变为仓库可延后写回的正式 UID。

## 4. 计算、角色配置与自建角色

计算请求冻结账号、generation、快照、静态数据集、profile、角色顺序/平级组、目标配装槽位和锁快照，
返回不可变 `WeightedAllocationPreview`。保存只消费原 preview，不重新读取最新库存或配置。

候选规则：

1. 锁定真实 UID 在候选构造前联合排除；失效锁阻止计算。
2. 账号级“筛选设置”默认不选择品质和类型。选择卡带或驱动后必须同时选择至少一种品质；对已选类型，仅已选品质进入角色管理筛选，其余品质被过滤；未选类型按默认规则处理。该筛选在角色配置前执行一次，角色优先、全局最优和增量更新共用同一候选结果。
3. 驱动副词条黑名单默认是硬过滤；启用“黑名单为零权重”后不淘汰命中驱动，而是在 Top-K 评分时将黑名单词条按零权重计分。副词条自选按最深/最多命中候选池优先，组合无解时逐层放宽。
4. 卡带先执行套装与主词条硬过滤，再执行同一副词条回退；默认四件套。
5. “不限制评分等级”只移除副词条自选门槛，不移除套装、主词条，也不改变黑名单当前的硬过滤或零权重语义。
6. 平级组暴击恢复依次为只换卡带、冻结必需套装件后重选额外件、仅失败角色从零重配。
7. 前序角色已分配 UID 不进入后续候选；虚拟占位评分为 0，不进入锁或极速装配。

未显式覆盖时，官方角色使用毕业模板套装与专武；卡带主/副词条默认未选择；暴击率上限按满级默认专武
生成。升级保留账号已有配置，包括主角「零」的历史“环合强度”设置。

账号基础权重是持久计算输入。角色详情动态权重只根据当前面板的直伤边际生成，用于分析与替换排序，
不写回基础权重。官方额外形状读取公共共享覆盖；自建角色名称、权重、额外形状、默认套装和 5×5 底盘
只写当前账号。自建底盘固定 20 个启用格位，单格可锁定。

自建角色可参与视觉库存计算和游戏界面自动装配；不进入官方角色详情、nte-core 角色实例、游戏配装导入
或极速装配。

卡带统一使用 `StatCatalog` 满级主词条值：金/橙 1.0、紫 0.8、蓝 0.6。方案保存
`payload.tape_main_values` 与 `payload.assignment_scores`；旧方案缺字段时才调用统一 helper 回退。

单件卡带和驱动仍按“得分 /（面积 × 10）”的比例评为 D 至 ACE。完整配装方案的总评只按总分固定区间
评定：D `<160`、C `>=160`、B `>=180`、A `>=200`、S `>=220`、SS `>=240`、SSS `>=260`、
ACE `>=280`。该总评规则不依赖角色来源或槽位：官方角色、自建角色和同角色的每个配装槽位分别按各自
方案总分评级，不改变任何单件装备的评分与评级。

## 5. 配装槽位、游戏导入与锁

每个角色最多三个可见槽位。`primary` 是兼容默认槽位，默认显示角色名；用户可新建、重命名、归档和
选择槽位。每个槽位同时只有一个当前方案，覆盖会创建新方案版本并原子更新 `current_plan_id`，历史方案
仍按自己的来源快照解析。

同一角色的多个槽位是备选配装：它们可引用同一个真实 UID，不视为装备复用冲突。角色优先、全局最优和
增量更新均以角色为 UID 冲突边界；只有不同角色的当前槽位同时引用同一 UID 时处理冲突。

计算和加权计算保存前为每个角色显式选择目标槽位，可新建槽位或跳过；差异比较使用同一目标槽位，
不把其他备用槽位当成基线。批量保存是事务性的，后续角色验证失败时整批回滚。
计算结果仅提示本次第二步角色选择中“全部槽位已锁定”的角色；未选择的锁定角色不显示该提示。

游戏配装是 nte-core 稳定快照的只读投影。显式导入后保存为 `game-observed-loadout-v1`，冻结来源快照、
目标槽位、逐件评分和卡带满级值。完整驱动但缺卡带的方案可保存为 `incomplete/missing_tape`；视觉来源
不进入游戏配装导入。

锁作用于当前账号的具体槽位方案，不调用游戏锁 RPC。至少一个真实装备即可锁定；空方案和虚拟占位方案
不可锁。锁定槽位不可覆盖、归档或单件替换；其他角色/槽位不得借用其 UID。归档 `primary` 时由 DAO
提升剩余可见槽位；每个角色至少保留一个可见槽位。

配装页、角色空幕详情、替换、倒带和装配都读取选中/默认槽位。批量装配对每个角色显式选择一个 `slot_id`，
并在执行前检查角色唯一、槽位存在、原生来源和跨角色 UID 无冲突。

## 6. 仓库与鉴定

仓库读取固定快照并通过 `WarehouseInventoryService` 生成投影。卡带按套装、主属性、副属性筛选；驱动按
形状和副属性筛选。条件使用正式 ID，同组为“或”、跨组为“且”；状态分为已装备、已锁定、已弃置和其他。
重置清除全部条件，视觉来源因无可靠原生状态归入其他。

原生仓库状态管理固定快照和正式 UID，Service 生成计划，Integration 提交 RPC，随后等待递增完整快照
确认。一键弃置/锁定和仓库状态保存会在命令接受后立即更新目标 UID 的仓库投影；若这两个动作守卫期内
收到单个、覆盖全部目标 UID 的背包快照，则由动作本身替换库存集合，允许新增或移除库存。只有该动作收到
声明数量减少的背包事件时提示玩家重新在游戏登录页面同步；后台监听不会单独执行这种库存替换。视觉仓库本身只读；只有扫描完成后的同会话
鼠标管理使用扫描索引执行即时写回。

评估角色范围只影响仓库锁定/弃置评分，与计算角色、活动配装和倒带偏好隔离。

鉴定把截图、剪贴板、手工输入和仓库单件入口投影为统一装备对象，调用公共评分与
`EquipmentPresentation`，不写库存、基础权重或配装。扫描与鉴定共享 `GlobalHotkeyManager`，通过 owner
隔离会话和停止权限。

## 7. 倒带推荐与执行

工具页读取固定库存、账号偏好和活动配装槽位。打开页面或修改选项不自动求解；显式生成后返回八槽形状
多重集合。偏好字段为 `target_character_ids`、`main_character_ids`、`strategy`、`target_grade`、
`target_threshold_mode` 与 `target_custom_percent`。标准等级保留 D 至 ACE；选择“自选”后必须填写
1.0% 至 100.0% 的目标百分比，按 0.1% 精度保存到当前账号。

```text
标准目标分 = 等级比例 × max(1, 驱动面积) × 10
自选目标分 = 自选百分比 × max(1, 驱动面积) × 10
缺口 = max(0, 目标分 - 方案保存的逐件评分)
```

等级比例：D=0、C=.2、B=.3、A=.4、S=.5、SS=.6、SSS=.7、ACE=.8。自选百分比按每件驱动自身的
实际面积分别计算，等于目标不形成缺口；高于目标的分数不抵消其他驱动缺口。该阈值只改变倒带推荐的
缺口统计，不改变单件评分或配装方案总评；自建角色和同角色的每个活动配装槽位均独立参与统计。

- 全面均衡：全部培养角色每种正缺分形状保留一槽，余位按“形状缺口 ÷ 库存”比例分配。
- 少角冲分：只看冲分角色，每种正缺分形状保留一槽，余位只按评分缺口比例分配。

超过八种正缺分形状时返回提示。每槽概率 12.5%；同形状重复 `q` 次时，每槽价格
`10 + 5 × (q - 1)`，总价为 `q × 每槽价格`。难度只决定蓝/紫/金品质，不进入形状、概率和价格。

显式执行冻结品质、定制模式和八槽方案。每个品质先切换对应难度再读取该难度余额；余额不跨难度复用。
初级随机十连固定 600；紫/金定制从右侧硬币口下方识别十连价格。“不做更改”保留现有候选，“应用方案”
通过轮廓与 12 种拓扑全局匹配后配置八槽。十连循环为点击、等待 1 秒、Esc、等待 1 秒、Esc、等待 0.5 秒；
执行期间可按设置中的全局停止键停止。真实执行仍为实验能力。

## 8. 极速装配与游戏界面自动装配

极速装配只消费 nte-core 正式 UID、角色实例和已保存槽位方案；游戏界面自动装配消费视觉投影与输入动作，
可支持自建角色。两条链路冻结账号、generation、来源快照、槽位列表和任务 token，并持久化角色项与事件。

极速装配每个角色最多三次完整请求。每次下发后先等待 10 秒完整递增快照；无论后续收到完整快照、范围化
装备事件或没有事件，已接受指令中的卡带/驱动都会立即投影为目标角色和格位。完整快照是首选确认来源，
可核对角色、实例和装备全集；不以驱动格位差异触发复装。范围事件仅用于发现遗漏：目标装备出现在事件中但
未装备时，才重试对应角色；没有快照或范围事件时本轮直接结束，不将其当作遗漏，也不改写库存集合。

第一次或第二次明确不一致时卸空重装，第三次仍不一致才生成最终错误。报告区分管道缺失、短暂不可用、
队列繁忙、核心请求超时、完整快照等待超时、范围事件未确认，以及角色/实例/位置/装备集合不一致。

游戏界面自动装配使用角色识别、鼠标/虚拟手柄和画面状态。普通鼠标路径是当前公开能力；云模式代码保留
但 Controller 固定关闭，阻塞条件见 [路线图](roadmap.md)。

## 9. 战报

战报使用 nte-core combat 会话的聚合摘要、`battle.get_record` 和 `battle.get_axis`。背包同步与战报共享
捕获进程生命周期，不同时争抢 capture 会话。采集期间以 500 行分页持续排空逐击轴，停止后再读取最终
record 并排空尾页；cursor 过期或 Core 报告 `complete=false` 时保留不完整状态，不用摘要补造逐击。

账号 schema v23 保存规范化逐击、时停区间、上游 record/generation/sequence、完整性和原始脱敏轴行。
旧战报继续保持 `summary_only`；有逐击的记录投影为 `hit_axis`。当前页面仍只展示正式摘要，逐击日志、
时间轴、区间统计和边际收益见 [路线图](roadmap.md)。没有正式字段时不推测暴击、Buff/Debuff 区间、
护盾、治疗、角色施法、完整队伍或敌人实例。

开始采集时只固定账号 generation 并暂存逐击。结束后以逐击和摘要中实际出现的官方角色 ID 为范围，读取
当时最新一份完整 `nte_core` 背包中的游戏当前装备，并读取这些角色当时角色页有效养成，只物化相同人数的
等级、突破、觉醒、弧盘、技能、空幕和驱动；不读取配装槽位。物化完成后战报副本独立于原背包快照。

实时悬浮窗只在当前采集会话期间显示；点击“结束并生成战报”立即隐藏，采集结束、错误和历史战报也保持
隐藏。下一次显式开始采集时，仅在“显示实时悬浮窗”已开启的前提下重新显示。

手工记录与自动记录按账号保留策略清理，删除战报级联删除逐击与配装副本。结构化日志只记录记录 ID、
状态、数量和安全错误，不记录原始摘要、逐击、装备 UID 列表或完整伤害表。

## 10. 环境、更新与日志

环境诊断分别检查 Npcap、nte-core、dwmapi、备用 Mod Loader、Microsoft Visual C++ 运行库、运行时 SDK
缓存、IPC 管道和资源。插件默认在用户确认后备份并复制发行代理 DLL；代理方式不生效时可显式改用
管理员 Loader。两种加载方式互斥，Loader 会话由应用 stop event 和 owner PID 管理。工作区升级只更新
受管脚本并保留动态 SDK 缓存。游戏主程序自动检测先读取 Windows 卸载注册表，再检查各盘符下固定的
常见游戏库目录；检测不递归扫描磁盘，确认候选后才把路径保存到当前账号偏好。启动 Loader 时从该
`HTGame.exe` 的官方目录结构定位同一安装根中的启动器，并显式交给 Loader；监控进程存活不等于插件
已加载，装备 IPC 管道存在才是可用确认。Loader 不设固定哈希门禁，用户可直接用可信来源的同名文件
覆盖随包 `nte-mod-loader.exe`；替换文件仍会以管理员权限运行。

启动 Loader 前检查游戏目录的 `dwmapi.dll`：与当前发行插件或账号部署记录哈希一致时直接移除；旧版
或来源未知时，先复制到当前账号的插件备份目录并复核源文件与备份 SHA-256，再移除游戏目录文件。备份、
校验、删除或 Loader 启动任一步失败时中止操作；如果文件已经移除但 Loader 启动失败，则恢复原 DLL。

Mirror Controller/Integration 负责版本检查、下载、取消和安装器启动。日志不记录 CDK、Token 或鉴权 URL。

常驻日志为账号目录下 `nte_runtime.log`；用户开启详细日志时创建独立时间戳文件。账号切换结束旧账号会话
并在新账号目录创建会话。稳定事件名、公共字段和脱敏边界见 [日志事件规范](reference/logging-events.md)。
