# 功能与操作语义地图

本文面向使用者和维护者，按 Calc 菜单、子页面和深层操作说明功能、配置的实际限制及结果。这里是领域契约的阅读摘要，详细规则通过各节末尾链接维护；不是每一个装饰控件的清单。描述以生成时工作区静态核对为准，不代替发行包或实机验收。

## 总览：从操作理解三个项目、两个 Core

先按你要做的事找菜单，再看操作会影响什么。配置允许、任务启动、取得数据、保存成功和游戏实际执行成功，是不同的状态。

| 你要做什么 | 谁负责 | 对使用者意味着什么 |
| --- | --- | --- |
| 管理账号、选择功能、保存方案 | Calc | 当前账号的数据在这里管理；切换账号后，旧任务不能写入新账号 |
| 从游戏获取数据或执行原生操作 | 采集 Core：nte-core.exe 与游戏 DLL | 需要相应工作模式、游戏连接及该项业务能力；连接成功还不等于数据完整 |
| 配装计算、查看历史战报与反事实分析 | 计算／分析 Core：nte-analysis-core.exe | 用已经准备好的本地输入计算；不因采集故障就自动判定分析也故障 |
| 在游戏进程内读取、观察或执行 | UETools 游戏侧组件 | 由 Calc 与采集 Core 使用相应能力；菜单数不等于 DLL 文件数 |

已有完整库存上的配装求解与历史战报分析可以离线进行。需要重新从游戏准备输入的步骤，仍受采集或界面操作条件限制。

旧布局是最小 d3d12 代理与常驻 NTE_Capture.dll。当前工作区随附包复用无界面 Toolkit 宿主，拆为常驻 d3d12、User、Combat、HUD 和 Performance 五 DLL；首次迁移或宿主变化都必须退出游戏。随附包接入、游戏部署和实机验收分开，需按组件清单确认当前使用哪套。

HUD 已独立，背包、角色、装备继续归 User，战斗、Buff 与上下文继续归 Combat；按模块分离职责，不强制每个领域一个 DLL。当前候选已完成构建、保护、隔离验证和本地接入，真实游戏验收仍待完成。规则见 [本方插件宿主](reference/native-plugin-host.md)，余项见 [DLL 分离路线图](roadmap/native-plugin-separation.md)。

独立 Performance 已属于当前随附包。组件编译成功、Calc 能管理它和游戏正在使用它，是三件不同的事；查看本页时应一起核对随附与驻留组件身份。

### 状态文字应该怎样理解

| 显示的状态 | 实际含义 | 下一步 |
| --- | --- | --- |
| 模式允许 | 本机配置允许尝试该类功能 | 继续核对该功能的组件、连接与业务条件 |
| 等待 | 游戏、登录、组件连接或完整数据尚未就绪 | 按具体等待原因处理；不把等待自动当成安装损坏 |
| 已部署／文件已核对 | 对应文件检查通过 | 仍需连接与业务检测，不能据此认定装配或完整库存可用 |
| 未完成检测 | 本轮没有完成该项核对 | 查看共同失败原因；不是每一项都已经分别确认故障 |
| 已保存 | 本次结果已写入对应本地数据 | 若要改变游戏配装，还需要执行装配操作 |
| 结果未知 | 操作可能已派发，但还没有足够证据确认结果 | 先核对实际状态，不盲目重复可能已经执行的游戏操作 |

证据：[功能契约](features.md)、[工作模式](reference/work-modes.md)、[系统架构](architecture.md)、[外部集成](integrations.md)、[当前导航](../src/ui/navigation.py)。

## 工作台：自动同步、重启与关闭

自动同步是持续接收背包数据的开关。原生模式还会按已有能力同步角色字段；开启它不会自动开始战报、装配或 HUD。

| 按钮或操作 | 点击后发生什么 | 限制与完成条件 |
| --- | --- | --- |
| 自动同步：开启 | 先核对准备条件，通过后开始等待游戏与数据 | 离线模式不能开启；缺组件或待清理时按提示处理后重新开启。开关开启不等于新背包已经保存 |
| 自动同步：关闭 | 停止本次自动背包同步及等待游戏任务 | 保留已保存背包与方案；不代表停止独立手动角色任务、手动战报或按模式管理的组件维护 |
| 重启同步 | 打开来源对应的重启引导；同步关闭或暂停时先走开启准备 | 已运行战报时拒绝重启。保留已保存数据，只重建同步任务及未提交候选，不承诺重启全部进程或卸载 DLL |
| 开始重启同步 | 开始收尾旧同步并重新建立同步任务 | 抓包来源先回登录页，等监听就绪再登录；原生来源进入游戏场景等待数据，不要求退回登录页 |
| 取消重启 | 在重启准备尚未就绪时，取消本次重启请求 | 这是明确的取消按钮；与右上角关闭窗口不同 |
| 重启弹窗：右上角关闭／Esc | 隐藏重启引导窗口 | 不停止后台同步。准备就绪后的“完成／关闭”也只关闭展示；停止持续同步用首页开关 |
| 检测详情 | 查看逐功能检测结果及具体处理入口 | 不把文件、连接、握手和业务就绪合并成一个“正常” |

**“立即刷新”尚未作为独立操作交付。** 它的目标是在现有监听中请求一次新快照；当前“重启同步”仍是重建同步任务，不能按那个目标理解。

明确的原生连接中断后，若自动同步仍开启、账号与模式未变、组件已握手且没有战报或维护占用，显示“等待恢复”，按 2、5、15 秒退避最多恢复三次；成功回到稳定监听后重新计数。主动关闭、权限撤销、账号切换及未知原因的停止不按连接中断自动恢复。用尽重试或其他原因停止时显示“同步已停止”或具体异常，提示点击“重启同步”。旧快照不会被当成本次同步成功；自动同步偏好开启也不代表后台任务一定在运行。

性能监控和环境检测共用串行的状态查询入口；性能采样遇忙跳过本次采样。已确认的“请求正在处理／数据暂未就绪”只影响该次检测，不关闭背包同步正在使用的连接；协议损坏或连接故障仍按具体错误收尾。

完整且稳定的数据保存后才会成为当前背包。游戏退出、读取等待或收到部分数据时，原来保存的背包仍可查看，但它不因此成为最新游戏状态。

证据：[同步契约与引导](reference/work-modes.md)、[首页按钮](../src/features/home/page.py)、[重启弹窗](../src/features/home/sync_retry_dialog.py)、[自动同步控制器](../src/ui/controllers/auto_sync_controller.py)、[同步服务](../src/services/inventory/sync/service.py)、[同步执行](../src/services/inventory/sync/runtime.py)、[共享原生会话](../src/services/native_session/session.py)、[背包读取](../src/services/native_session/inventory.py)。

### 重启同步引导 <!-- page: sync-restart; type: 弹窗 -->

进入路径：工作台 → 重启同步。按钮关闭或暂停时显示“开启自动同步”，先处理开启条件。

- 抓包来源先回登录页，等监听就绪再登录；原生来源进入游戏场景等待读取。
- “开始重启同步”才发起重建；准备期间“取消重启”取消该请求。
- 右上角关闭和 Esc 只隐藏窗口。停止持续同步使用工作台开关；已保存背包和方案保留。
- 战报运行时不能重启同步；这项当前限制不能被未来的并行设计替代。

证据：[重启弹窗](../src/features/home/sync_retry_dialog.py)、[同步契约](reference/work-modes.md)。

## 角色：同步状态、图纸与权重

| 按钮或配置 | 实际作用 | 限制与保留内容 |
| --- | --- | --- |
| 同步状态 | 手动读取当前支持的角色养成字段并保存到当前账号 | 需要原生角色能力；只更新已证实字段，不把未返回字段清零，不宣称整个面板全部支持 |
| 取消同步 | 请求停止本次手动角色同步 | 未完成读取不提交；取消后的迟到结果不能覆盖角色档案。不会因此关闭其他独立采集功能 |
| 角色图纸、基础权重 | 改变后续配装计算所用的形状、约束与偏好 | 不是修改游戏角色属性；旧的计算预览不会自动按新配置重算 |
| 角色暴击率上限 | 约束分配使用的暴击上限 | 手工填写 0 表示不设上限；不是把角色暴击率设为 0。自动上限还会考虑角色面板扣除项 |
| 家具、好感等面板输入 | 为本地评分与计算提供角色条件 | 不能仅因这里填过数值，就宣称游戏已经获得相应效果 |

关闭首页自动同步不等于取消这次手动同步；切换账号、撤销模式权限和退出程序则涉及全局任务收尾。

证据：[角色与面板规则](features.md)、[角色同步控制器](../src/features/official_role/sync_controller.py)、[字段保留规则](../src/domain/native_role_sync.py)。

### 角色养成与面板 <!-- page: role-profile; type: 详情区 -->

进入路径：角色 → 选择官方角色。这里编辑本账号用于计算的养成配置。

- “保存”持久化配置；“重置当前”与“重置所有”的范围分别是当前角色与全部角色，不能把重置当成关闭编辑。
- 角色与弧盘临界等级需要区分突破前后。觉醒等级表示解锁数量，具体勾选表示启用效果；允许解锁后留空，勾选数量不能超过等级。
- 常驻属性进入静态面板；带触发、持续时间或层数条件的效果不因此始终生效。
- 页面修改不会改变游戏角色的真实等级、技能或觉醒。
- 详情与替换候选使用同一份已核对静态包；资料更新或包不完整时停止本次替换，重新打开角色详情后重试。旧结果不会自动改用最新资料。

读取与保存边界见[系统架构](architecture.md#21-角色配置领域入口与测试发现)。

证据：[养成规则](features.md)、[角色页面](../src/features/official_role/role_shell.py)、[保存与重置](../src/features/official_role/controller.py)。

### 基础权重 <!-- page: role-weights; type: 子页面 -->

## 计算：开始计算、保存与约束

配装求解使用计算／分析 Core 的 Rust 实现。对使用者更重要的是：一次计算固定使用发起时的库存、角色顺序、权重、锁和相关设置；运行中同步到新库存，不会偷偷改变这次结果的输入。

| 按钮或配置 | 实际作用 | 限制与完成条件 |
| --- | --- | --- |
| 开始计算 | 按所选输入方式准备完整库存，再计算本次配装预览 | 准备输入与求解是不同阶段；没有有效完整输入时不能拿残缺背包凑结果 |
| 分配策略旁的“设置” | 打开本账号的分配设置草稿，确认有效内容后保存 | 取消不保存草稿；修改影响后续计算，不自动重算已经显示的预览 |
| 分配类型／分配品质 | 对已选类型限定可进入筛选的品质 | 未选类型按默认规则处理，不等于把所有未选类型全都排除；其他角色约束继续生效 |
| 保存装备锁定 | 将本次有效结果保存到选定的本地配装槽位 | 消费刚才的预览；不是执行游戏装配或游戏锁定。缺少有效结果或冻结依据时需要重新计算 |
| 图纸组合数 | 限制当前优先级组的组合求解预算 | 必须为正整数；同级组共享联合搜索预算。加大可能增加耗时，不保证全局最优；超过理论总数不会凭空增加组合 |
| 黑名单为零权重：关闭 | 命中驱动副词条黑名单的候选被硬过滤 | 降低分数与排除装备不是同一种行为 |
| 黑名单为零权重：开启 | 不因命中黑名单直接淘汰驱动，而将对应词条按零权重评分 | 套装、主词条、锁等其他约束继续生效 |
| 不限制评分等级 | 放开副词条自选门槛 | **不等于取消全部限制**：套装、主词条和当前黑名单规则仍然生效 |
| 角色优先级／同级组 | 高优先角色先分配，同级角色联合分配 | 同次分配不重复消费真实装备；同角色已保存备选方案可共用装备，受保护的方案锁仍排除对应装备 |
| 锁定更新（原“增量更新”，界面遗留选项） | 页面显示“锁定所有计算配装，只用其他装备分配”，策略身份仍为 `update_mode` | **当前 Rust 分配入口不支持该策略**：界面会传入另一策略值，而入口只接受角色优先。本次仅调整显示名称，不新增算法支持。不能因选项可见就按可用功能依赖；此能力不一致仍待单独修复与验收 |

全局停止键可停止本次计算并回收对应计算进程。已保存方案不会因为取消新的求解而被覆盖；新配置需要发起新计算才能得到相应结果。

证据：[分配与设置规则](features.md)、[计算页](../src/features/allocation/execute_page.py)、[分配设置](../src/features/allocation/filter_settings_dialog.py)、[策略选择传递](../src/features/scanning/workflow.py)、[Rust 策略能力限制](../src/integrations/native_allocation_wire.py)、[计算编排](../src/features/allocation/runner.py)、[保存流程](../src/features/allocation/save_workflow.py)、[计算入口](../src/app/facade.py)、[Rust 分配适配](../src/integrations/native_allocation.py)、[分析组件适配](../src/integrations/nte_analysis_core.py)。

### 输入方式与扫描准备 <!-- page: calculation-input; type: 功能区 -->

进入路径：计算 → 第一步“扫描模式”。这里决定库存从哪里来，不是切换本机风险授权。

| 选项 | 作用与限制 |
| --- | --- |
| 直接读取库存 | 使用已保存库存重新计算，不启动视觉扫描 |
| 离线解析 | 解析已有截图；仍需形成完整、可验证的输入，不从缺页截图猜完整背包 |
| 增量扫描 | 录入新增装备；必须满足对应基线与扫描条件 |
| 全量扫描 | 重扫并重建库存；取消、数量异常或输入失败时不提交半成品 |

选择输入方式不会自动提高工作模式权限。全量扫描中的数量、鼠标或虚拟手柄配置服务本次扫描；视觉来源不因扫描完整就获得游戏原生身份或锁／弃置读取能力。

证据：[输入选项](../src/features/allocation/execute_page.py)、[扫描契约](features.md)。

### 扫描后管理与预留规则 <!-- page: scan-management; type: 弹窗; parent: calculation-input -->

进入路径：计算 → 相应扫描方式 → 管理。弹窗包含“评分处理”和“预留规则”。

按所选类型、品质、评估角色和预留规则准备扫描后的处理计划；“新增规则／编辑／复制／删除”修改规则草稿，不是当场锁定或弃置游戏装备。真正执行要求同次完整扫描及界面身份核对，不能把仓库视觉来源的一般浏览权限扩大成任意游戏写入权限。

证据：[扫描后管理](../src/features/scanning/post_action_dialog.py)、[扫描后执行边界](features.md)。

### 分配设置 <!-- page: allocation-settings; type: 弹窗 -->

进入路径：计算 → 第三步“分配策略”旁的设置。

- 分配类型决定哪些类型采用品质筛选；未选择的类型按默认规则处理，不能解读为一律排除。
- 组合数上限限制每个优先级组的求解预算，必须是正整数；增加预算不保证全局最优。
- 确认通过校验并成功保存才成为本账号设置；取消保留原值。
- 改设置不自动重算已经显示的预览，需重新开始计算。

证据：[分配设置弹窗](../src/features/allocation/filter_settings_dialog.py)、[保存设置](../src/features/scanning/controller.py)。

### 保存结果与目标槽位 <!-- page: allocation-save; type: 操作流程 -->

进入路径：计算完成 → 保存装备锁定 → 选择目标槽位。

每个角色明确选择目标槽位，可新建或跳过。保存比较的是同一目标槽位的前后差异；整批验证失败或提交前取消时回滚。保存消费本次预览而非最新库存；被其他角色借走的装备可能使原来未锁定方案变为不完整，锁定方案拒绝借用。保存成功仍只是本地方案，不执行游戏装配。

证据：[保存流程](../src/features/allocation/save_workflow.py)、[槽位与借用规则](features.md)。

## 配装：本地方案与游戏执行

| 按钮或操作 | 实际作用 | 限制与完成条件 |
| --- | --- | --- |
| 计算配装／游戏配装 | 切换查看本地计算方案或已观测的游戏配装 | 切换展示不会执行穿戴，也不会把旧观测变成实时数据 |
| 方案锁定／解锁 | 保护当前账号的具体配装槽位方案 | 锁定后不能覆盖、归档、替换或被其他方案借用真实装备；**这是 Calc 方案锁，不是游戏装备锁** |
| 清空配装 | 确认后从当前配装页移除未锁定的已保存方案 | 保留方案历史、任务记录和锁定方案；不卸下游戏装备 |
| 极速装配 | 先准备批量原生装配预览，再由用户确认执行 | 需要正式原生装备身份、角色实例、有效槽位及对应能力；收到指令不是成功，需后验状态确认 |

保存方案只是保存在 Calc 中。是否已经穿到游戏角色身上，要看实际装配结果；原生装配与普通界面装配的条件分别判断。

## 仓库：筛选、锁定与弃置

| --- | --- | --- |
| 筛选 | 在当前固定库存中选择要显示的装备 | 同组条件为“或”，跨组条件为“且”；只是缩小显示范围，不会删除被隐藏的装备 |

## 战报：采集、结束保存与历史分析

| 按钮或操作 | 实际作用 | 限制与完成条件 |
| --- | --- | --- |
| 开始采集 | 根据生效模式开始记录新战报 | 低风险用抓包，中风险用原生，开发模式作双路对照；需要相应来源就绪 |
| 结束保存 | 停止接收本次采集并处理、冻结本次记录 | 等待收尾和保存结果，不能把按下按钮的时刻当成持久化完成 |
| 放弃重录 | 丢弃本次尚未保存的记录并重新开始采集 | 当前采集中的操作，不是删除已有历史战报 |
| 读取历史战报 | 打开已保存战报并交给计算／分析 Core 分析 | 不要求游戏正在运行；需要兼容的分析组件。采集中该入口受限制 |
| 导出战报 | 导出对应战报包 | 不是导出账号的整个背包或完整本机环境 |
| 编辑副本／反事实比较 | 基于固定战报输入比较假定变化 | 不修改原始实测伤害、时间轴或游戏装备；新背包不会自动改写该次分析输入 |

**当前原生战报开始时会暂停正在运行的背包同步，并记录恢复需求。** 这是真实的共享资源限制；未来解耦前，不能宣称原生战报与背包始终完全独立并行。抓包战报复用采集链路时保留库存解析。重启同步在战报运行时仍被拒绝。

缺少某项角色、Buff 或环境证据时，应显示相应未知或覆盖不足，不能把“能打开战报”理解为全部机制都已得到精确解释。

配套组件支持时，采集期间会自动订阅游戏的半场和重开确认，不需要额外开关。游戏里“重开当前半场”只重置该半场的当前统计归属，另一半场保留；“重开整层”重置两半场。原始逐击仍保留。楼层已知不代表半场已知，重开请求也不等于已确认；普通副本还需等待新的刷怪边界。旧组件继续使用原有可用观测。以上链路已通过离线专项验证，新增通知在游戏里的实际覆盖仍待验收。

证据：[战报功能契约](features/battle-report.md)、[战报按钮](../src/features/battle_report/page.py)、[采集资源协调](../src/features/battle_report/capture/controls.py)、[分析组件适配](../src/integrations/nte_analysis_core.py)。

## 工具：养成、倒带与资料库

| 操作或配置 | 实际作用 | 实际限制 |
| --- | --- | --- |
| 养成计算器：等级目标与已有材料 | 计算当前草稿所需材料、已有扣除和可推定的体力 | 不自动修改角色档案、背包或实际活力；改输入后需要重新计算 |
| 材料合成与体力视图 | 按已确认材料链换算低阶材料，按已知来源估计副本需求 | 不是所有材料都能按三合一换算，也不是所有材料都能折算成副本体力 |
| 倒带：生成方案／重新生成 | 按当前固定库存、角色明确所选槽位及冻结评分生成本地推荐（槽位选择改动待验收） | 推荐结果还没有操作游戏；输入变化后重新生成，不把旧推荐当新状态 |
| 倒带：进行倒带 | 进入倒带执行配置，后续按确认流程操作游戏 | 需要模式和输入条件；停止时释放本次输入，已执行动作不能靠关闭窗口撤销 |
| 游戏资料库 | 浏览随附静态资料 | 静态展示不等于当前游戏账号拥有，也不自动赋予新版本原生采集或伤害分析能力 |

证据：[工具与资料库规则](features/tools-and-catalog.md)、[养成体力范围](reference/progression-stamina-calculator.md)、[倒带入口](../src/features/toolbox/page.py)。

进入路径：养成计算器 → 单角色／多角色。

单角色计算当前对象，多角色汇总所选目标。“选择角色”添加目标，“删除”移除该计算目标，不删除账号角色。分别设置当前与目标等级、突破及技能；选中多个目标不代表它们已经同步到游戏。计算后再读取本次材料和体力结果。

### 已有材料与材料范围 <!-- page: cultivation-materials; type: 配置区; parent: cultivation -->

进入路径：养成计算器 → 已有材料；页头可切换材料范围。

- 修改已有数量后，原结果过期，需要重新计算才扣除并恢复可复制结果。
- “仅体力”只展示本次可按正式副本确定掉落估算的材料，排除方斯等不属于该口径的项目，不代表所有养成成本都已覆盖。
- 合成只适用于已确认的材料链，经验材料不按通用三合一处理。
- “同步材料”读取当前账号已经保存的材料观测，不立即向游戏发起抓取。原生模式读取原生物品归档；低风险模式读取背包同步期间稳定保存的抓包物品观测，停止监听后仍可导入，不用旧原生归档兜底。抓包观测不是完整背包；未观测材料不当成零，已有手填覆盖优先。导入后仍需重新计算。
- “清空”清除本次草稿的已有数量，不修改账号物品归档；材料草稿与结果也不反向写入游戏背包。

证据：[已有材料控件](../src/features/toolbox/cultivation/owned_materials.py)、[材料范围与体力](reference/progression-stamina-calculator.md)、[计算器契约](features/tools-and-catalog.md)。

## 插件：独立开关与就绪条件

| 按钮或配置 | 实际作用 | 实际限制 |
| --- | --- | --- |
| 技能冷却 HUD／敌人状态 HUD 开关 | 分别控制对应功能需求 | 两张卡各自维护状态；关闭一个不会连带开始或停止战报、背包同步及另一个 HUD |

已保存的开启偏好、模式是否允许、游戏内功能是否实际运行，要分别看。功能暂不可用时不能以开启偏好代替成功状态。

### 技能冷却 HUD <!-- page: plugin-cooldown; type: 功能卡片 -->

进入路径：插件 → 技能冷却 HUD。

开关只管理对应显示需求；保存开启偏好与游戏内实际运行分开显示。需要模式与插件业务条件满足，不能以卡片存在推断组件就绪。关闭不连带停止战报或其他 HUD。

Calc 配套 DLL 启动或热重载时默认不显示 HUD。Calc 连接后按已保存开关开启；退出 Calc 或采集连接断开时停止本次显示，偏好仍保留。直接关闭启动用的 PowerShell 可能跳过界面退出清理，连接断开后的关闭由 DLL 兜底。若 Calc 或 Core 仍存活且连接未断，不能仅凭命令行窗口关闭认定已经退出；当前技能／敌人 HUD 尚无控制端卡死的心跳超时保证。

证据：[插件卡片](../src/features/plugins/page.py)、[插件权限](reference/work-modes.md)。

## 设置与账号：配置何时生效、影响谁

### 工作模式是允许范围，不是成功证明

| 生效模式 | 可以尝试的主要功能 | 实际限制 |
| --- | --- | --- |
| 离线 | 本地计算、已有数据、历史战报分析与诊断 | 不连接游戏执行采集或游戏输入；分析仍需兼容的计算／分析组件 |
| 低风险 | 抓包同步／战报，以及允许的鼠标或手柄界面操作 | 不授予 DLL 原生功能；名称不代表游戏运营方认可或风险为零 |
| 中风险 | DLL 同步、原生战报、原生装配与对应插件，以及界面操作 | 各功能分别核对；中风险不启用抓包来源 |
| 开发 | DLL 与抓包对照及相应开发排错 | 正式库存仍只由 DLL 写入，战报固定双路对照；不是两路库存互相补齐 |

| 展开排查信息 | 显示本轮已有的详细检测事实 | 只是展开显示，不会因为展开而重新检测 |

| 切换账号 | 结束旧账号任务，再加载新账号数据 | 本机模式、主题和插件偏好不因此变成另一套；旧任务结果不能写入新账号 |
| 退出 Calc | 收尾程序拥有的任务与 Core 进程 | 不代表游戏进程已经退出，也不等于驻留 DLL 已卸载；必要组件清理看独立结果 |

### 性能监控 <!-- page: settings-performance; type: 配置区 -->

进入路径：设置 → 性能监控，位于“采集排错”上方。

**源码与配套 DLL/Core 已成套纳入当前组件输入，实际二进制的隔离握手及开关验证通过；真实游戏显示和帧统计仍待验收。旧安装目录需配套更新，不能只更新设置页。**

游戏角落只显示四项：FPS、帧时间、1% Low、Calc 耗时（已覆盖）。FPS 和帧时间看整体流畅度，
1% Low 看慢帧；Calc 耗时表示已接入的游戏线程工作耗时，不是整个 Calc 软件的 CPU 占用率或准确的 FPS 损失。
当前覆盖原生事件分发和 HUD；尚未覆盖的独立插件、其他线程、Core、GPU 等不会被算成零。

悬浮窗缺少样本时的示意（不是游戏实测）：

```text
FPS                 --
帧时间              --
1% Low              --
Calc 耗时（已覆盖）  --
```


| 操作 | 实际作用 | 限制与结束条件 |
| --- | --- | --- |
| 显示游戏内性能 | 开启采样，并请求 DLL 显示四项数值 | 首次默认关闭；已确认中风险/开发模式且未暂停时可用；不启动同步或战报 |
| 关闭游戏内性能 | 隐藏四项数值 | 排错仍需要性能日志时继续后台采样；没有日志需求时一起停采样 |
| 性能详情 | 查看服务耗时、覆盖范围及日志位置 | 关闭弹窗不关闭悬浮窗或日志；服务单次耗时不能相加当作每帧总开销 |
| 同时记录性能 | 开启采集排错时同时保存性能记录 | 选项本身不启动日志，也不强制显示悬浮窗；关闭排错后手动显示继续 |
| 退出 Calc | 撤销本次显示和计时，停止本次帧采集 | 不卸载 DLL；连接断开清理，控制端卡死时最多等待 5 秒续期超时 |

本机记住用户主动开启的显示偏好，下次连接与模式满足条件后恢复。账号切换结束旧日志并重置统计，
再使用本机显示偏好及新账号的排错设置。关闭显示和关闭记录是两件事，不互相代替。

开关选中表示用户意图；“等待绘制”表示请求已送达，“已绘制”表示组件确实报告近期绘制。
断连、版本不支持和状态未确认分别提示，不能把开关选中当作成功。

帧时间采用游戏提交呈现的间隔，不能解读成显示器实际显示时间或插帧后帧率；1% Low 使用最近 30 秒慢帧平均，
不足 1000 帧时暂不显示。数据缺失显示 `--`，不会伪造为 0。数值约每半秒更新，游戏内不增加曲线或展开层级。

三项持续显示 `--` 时，在“性能详情”查看帧采集原因：等待有效样本、输出字段不匹配或权限不足。
“悬浮窗已绘制”和 Calc 耗时有数值只证明 DLL 绘制／计时通路可用，不证明 PresentMon 已提供游戏帧数据。

开启显示不自动保存文件。性能日志位于当前账号日志目录的 `performance/`，与 `nte_core/raw_capture/` 相邻。
单次日志上限 16 MiB，写入失败或达到上限时停止本次记录并提示，实时显示继续。

统一指标、覆盖与开关规则见[性能指标契约](reference/performance-metrics.md)，记录字段见[日志契约](reference/logging-events.md#性能排错记录)。

### 入口、插件与两个 Core <!-- page: dll-overview; type: 架构说明 -->

D3D 宿主负责加载、校验、公共调度和窄通信；能力插件负责具体游戏工作。采集 Core 编排读取和业务请求；计算／分析 Core 处理冻结后的本地计算。Calc 负责你的账号、配置与结果保存。
采用一个常驻入口和 User、Combat、HUD、Performance 四个插件。更细的读取、观察、装备、Buff 与环境责任在所属 DLL 内分模块；只有独立发布或启停需求明确时再增加 DLL。
当前还没有通用的第三方手动白名单，也没有“任意 DLL 都可热卸载”的能力。

### 数据读取与装备操作 <!-- page: dll-data; type: 目标分类; parent: dll-overview -->

| 目标能力 | 为你做什么 | 独立后应有的限制与语义 |
| --- | --- | --- |
| 背包快照 | 请求一次背包读取 | “刷新一次”不会停止已有变化监听；读取过程中变动可能使候选失效，旧完整背包仍保留 |
| 背包变化观察 | 接收变化，提供一致性依据 | 缓存还在不意味着需要持续观察；仍有其他消费者时不提前关闭 |
| 角色状态 | 读取已支持的角色永久字段 | 角色与库存任务分别收尾；缺少字段保留原值，不把战斗临时值当永久养成 |
| 装备操作 | 派发已授权的装配、锁定或弃置操作 | 与只读功能分开；等待新状态确认，不把“命令收到”显示成“游戏已完成” |

“背包同步”仍是采集 Core 管理的业务服务，不需要再制造一个重复负责整个同步流程的 DLL。关闭同步释放该会话拥有的需求；已保存数据不删除。

### 战报、Buff 与环境 <!-- page: dll-battle; type: 目标分类; parent: dll-overview -->

| 目标能力 | 为你做什么 | 独立后应有的限制与语义 |
| --- | --- | --- |
| 战斗原始事件 | 保留逐击、战斗阶段与时间证据 | 不直接负责全部采集通信，不因停用它而让背包接口一起消失 |
| Buff 观测 | 为战报、HUD 等提供效果与应用关系证据 | 某项增强缺失时明确不可分析；不把“有 Buff”直接当作“这一击已享受加成” |
| 队伍与环境 | 提供队伍、目标、场景和环境的已知状态 | 观察与用户假定分开；不要求为了读环境先开启战报 |

目标是基础战报与增强能力分开判断。需要 Buff 证据的项目必须有相应来源；只依赖基础逐击的项目可以保留。卸载 provider 仍须先解除真实调用和订阅，不能硬拔。

### 展示与性能诊断 <!-- page: dll-observation; type: 目标分类; parent: dll-overview -->

HUD 负责把数值画出来；Performance 负责服务耗时采样、汇总与有界日志。关闭 HUD 不应停止独立记录；停止诊断也不应停止背包或战报。
FPS／帧时间需要真实呈现来源。现有服务耗时插件不等于帧率采集器，没观测到的数据继续显示未知。
HUD 内部的技能冷却、敌人状态和性能四项分别开关，不因为同属一个展示 DLL 就绑定启停。

### 拆分顺序与验收 <!-- page: dll-migration; type: 开发目标; parent: dll-overview -->

当前工作区五 DLL 包已独立 HUD 和 Performance，并通过构建及隔离验证。后续先取得游戏内业务、资源排空和性能证据，再继续收敛 User 与 Combat 内部的任务和模块，不按旧九插件数量推进。
每阶段都检查停止一个功能是否误伤其他消费者、取消是否真正收尾、未知数据是否被保留，以及性能和实测证据是否等价。
新源码固定白名单识别 User／Combat／HUD／Performance，扩展其他目标插件需要先更新宿主，因此这次 D3D 仍不是永远不变的最终宿主。真正只更新插件的前提是宿主、ABI、签名策略和依赖契约都已兼容。
新的源码、说明或离线验证不会自动替换你正在测试的组件；实际升级按独立部署与验收记录确认。
