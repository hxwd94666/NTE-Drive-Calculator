# 队伍阵容匹配战报：剩余验收

## 当前状态与事实源

队伍页及计算页共用匹配列表、按正式四人阵容核验、显式范围优先、无库存历史发现、异步取消与来源复核已接入源码。
匹配本身未改求解目标、账号 schema、静态数据或组件执行物；简报的实现与剩余验收独立见[队伍简报](team-overview.md)。
已实现的产品规则以[阵容匹配](../features.md#按阵容匹配战报)为准，所有权与缓存以
[系统架构](../architecture.md#队伍管理与战报匹配)为准，正式能力消费见[集成说明](../integrations.md#11-nte-analysis-core)。
旧平铺队伍模块、无过滤战报选择器及其调用方已迁移，不保留第二套选择入口。

已运行的专项与静态检查、失败修复和证据范围集中在[验证记录](../validation/team-report-matching.md)。
源码接通、随附组件合成战报验证、全项目回归、实际窗口操作和正式发布是不同完成状态。
本文不构成扩大测试、真实账号访问、游戏操作、编译、打包、部署、提交或发布授权。

## 剩余验证矩阵

| 门禁 | 本轮证据 | 仍须完成 |
| --- | --- | --- |
| 集合与范围 | 四人乱序、零伤害成员、半场拆分、差异、缺证、冲突与原轴半开时段专项 | 真实保存战报的普通场、上下半场与作废／重开证据核对 |
| 发现与确认 | 无库存发现、分页／场景、手工核验、显式 B 优先于旧 A、同记录两半场 | 用户实际从战报页→选队→取消／应用的完整操作 |
| 冻结与副作用 | 账号代次、队伍修订、来源摘要、静态／语义／组件身份、删除与重试；合成库前后不变 | 实际应用运行中账号切换、静态更新与历史清理的联动窗口 |
| 生命周期 | 控制任务取消、末次请求回填、GUI 线程交付、物理退场；原生联调 | 大量真实历史下翻页／离页／退出，组件中断时有界收尾 |
| 可操作性 | 三主题与两种窄屏几何专项、键盘取消 | 实际窗口键盘全流程、长队名／角色名与混合 DPI 多屏切换 |
| 性能 | 专项命令耗时及正式摘要复用请求数断言 | 代表性历史规模下分别记录发现、首个匹配、可见页全部核验、取消收尾、重复打开耗时与请求数 |
| 回归 | 本轮明确获授权的专项与硬静态门禁 | 另获授权后运行不带 pattern 的 core 和 full；结果按本次新增、既有或环境原因归类 |

在请求、刷新、缓存复用和确认边界重新核对正式输入摘要与资源身份，不依赖数据库 mtime，也不声称已有后台变更监视。
实际窗口与性能验收须验证：旧结果可暂留但有过期提示，应用前仍重验；未知／故障不计成已确认零匹配。

## 完成与后续

剩余验证通过后，将本页收敛为必要的待办或从路线图移除；不重复维护已交付规则。
若逐候选独立进程成本成为实测瓶颈，在独立集成仓库设计批量正式身份查询，覆盖逐项状态、范围、摘要、大小与取消，
成套晋升后再消费；本轮不假定该能力存在，也不直接读取组件私有分析数据换取速度。
匹配结果不自动选择最高收益战报、不自动新建队伍、不开始增强或游戏动作；简报不改变这条发现与执行边界。
