# 养成计算器历史记录与材料录入优化

## 1. 状态与目标

本文是实施中的开发契约，不代表当前功能已交付；实现收尾与完整验证仍待闭合。目标是在当前账号内自动保存养成工作配置及当时的合计结果，支持历史查看、配置复用、多选和全选删除，并减少为录入已有材料而进行的重复求解。

当前行为的事实源为[工具功能](../features/tools-and-catalog.md)，材料、合成与体力算法的事实源为[养成体力规划](../reference/progression-stamina-calculator.md)。本文只定义新增持久化和交互，不复制或改变材料公式。

建议采用以下组合，而不是只选其中一项：

1. 保存完整输入配置和轻量、可独立查看的合计结果快照。
2. 同一工作草稿的连续有效重算更新同一条历史，新的工作草稿产生新记录。
3. 目标确定后提前准备材料输入项，正式计算前即可填写已有材料。
4. 历史支持多选、全选当前筛选结果和批量删除，删除范围在确认时冻结。

生产实现按本文推进；项目测试、静态检查、构建和部署分别按用户明确授权执行，不将源码实现当作验收通过。

### 1.1 三个需求的建议结论

- 保存完整配置与轻量合计结果，而非只保存配置，也不是把当前结果页全部复制进历史。配置用于复用，结果用于查看当时算出了什么。
- 同时实施“同一工作草稿重算更新同一条历史”和“正式计算前准备已有材料输入”。前者解决历史重复，后者解决首次必须完整求解两次；两者不是互斥选项。
- 支持多选、跨页选择和全选当前筛选结果；删除必须确认确切记录集合，不能影响当前编辑内容、角色档案、背包或其他账号。

开发采用本文默认行为：连续计算合并为一条；加载历史原样恢复当时输入；不按天数或条数自动淘汰记录。若需要每一次重算都作为独立历史、加载时自动更新当前等级或自动清理旧记录，应先调整相应契约，不在开发中自行改变。

## 2. 开发前问题与原因

- 养成页只有会话状态：返回工具再进入可继续编辑，重启、账号代次或静态资料身份变化后旧页丢弃。账号库尚无养成历史专用存储。
- 单角色在 `_receive_plan` 接受结果后，`_render_plan` 才调用 `set_materials`；多角色也在完整结果回调后生成已有材料输入项。
- 首次计算同时执行材料汇总和体力求解。玩家看到材料后填写已有数量，再次完整计算，才能得到扣除后的材料和体力。
- 多角色首次计算后，目标变化会触发防抖自动重算。按每次回调插入历史，会产生大量中间记录。
- 当前有效计算请求不是完整编辑器草稿。例如关闭弧盘参与时，请求不带弧盘，但页面仍保留弧盘选择和等级输入。直接序列化请求会丢失这部分复用信息。
- 多角色页面已接近 Python 文件行数门禁。新增历史和恢复逻辑应拆入窄模块，而不是向大文件继续堆叠。

这里的“两次计算”是交互次序造成的重复工作，不代表材料公式应计算两次。材料需求准备可复用现有服务，完整体力求解仍保留在正式计算动作中。

## 3. 保存范围：配置与轻量结果都保留

### 3.0 为什么采用配置与轻量结果组合

| 选择 | 优点 | 代价与风险 | 结论 |
| --- | --- | --- | --- |
| 只保存配置 | 最小空间，易于复用 | 打开历史必须重算才能看材料；资料与算法更新后，得到的不是当时结果；旧对象被移除后可能连重算也做不到 | 不作为默认方案 |
| 配置与轻量合计结果 | 可以直接查看当时需求、抵扣、剩余和体力，也能加载配置重新计算 | 需要维护结果格式与资料/算法身份，空间略多 | 推荐 |
| 配置与完整结果页面、逐模块重复表、求解过程 | 可复刻更多旧明细 | 重复材料表随角色和模块增长，保存与读取成本高，容易附带不必要的数据 | 首版不采用 |

历史主要解决“找回这次养成方案”，不是保存每一次求解过程。原始已有数量保存在配置里，合成后的有效抵扣保存在结果里：两者各有意义，不能只保存剩余值后反推输入。详情中的历史结果始终只读；加载后重新计算生成新结果，不能原地改写旧结果来假装它适用于当前资料。

### 3.1 完整输入配置

保存可恢复到编辑器的显式输入，而不是整个控件对象或计算请求对象：

| 字段组 | 内容 |
| --- | --- |
| 模式 | 单角色、多角色 |
| 角色集合 | 正式 `character_id`、稳定 `line_id`、页面顺序和用于历史展示的名称 |
| 人物 | 当前/目标等级、突破阶段、参与开关 |
| 技能 | 正式 `skill_id`、当前/目标等级、参与开关 |
| 弧盘 | 正式 `fork_id`、名称、当前/目标等级与突破、参与开关；关闭时仍保存编辑值 |
| 公共体力设置 | 猎人等级、生效鉴别等级 |
| 已有材料 | 正式 `item_id`、原始数量、是否手工覆盖、来源类别和必要观测时间 |
| 展示偏好 | 全部/仅体力；不保存滚动坐标、焦点或控件地址 |

保存当前草稿中的全部材料数量，包括暂时被显示范围隐藏的材料。未填写与显式手填零分别表达；手填零也是手工覆盖，后续同步材料仍遵循现有覆盖优先级。只保存本工具使用的必要材料草稿，不附整份账号物品归档。

### 3.2 历史结果快照

历史详情应能在静态资料变化、对象改名或删除后查看当时的合计，推荐保存：

- 按正式物品 ID 合并的总需求、按既有合成规则得到的有效抵扣、仍需数量，以及当时的名称。
- 原始已有数量从输入配置读取；有效抵扣与原始库存不是同一概念，界面明确区分。
- 每种材料当时是否属于“仅体力”投影，历史切换范围使用这个冻结标记。
- 合并体力的完整/部分/不可用状态、已知值、完整值，以及缺口码。完整值未知保持空值，不填零。
- 合并副本建议的正式档位 ID、当时名称、次数、单次体力、总消耗和来源类别。
- 每角色的简短状态、体力解释值和缺口摘要。跨角色合并体力仍是权威值，不由逐角色值相加得到。
- 静态 dataset 的可携带身份、schema/importer、算法版本与结果格式版本。

第一版历史查看只承诺上述合计和摘要；不保存每个角色每个模块的重复材料表、完整来源账本、求解过程、完整静态库、图片字节或所有候选副本。需要完整当前明细时加载配置重新计算，界面不显示一个似乎齐全却缺内容的历史明细入口。

示例：需求为高档材料 2 件、原始持有可上合低档材料 6 件，历史保留原始持有 6、有效抵扣高档 2、仍需高档 0。不得使用 `2 - 6` 或对原始不同档位件数直接相减生成结果。

### 3.3 结果与配置一致性

输入配置与结果快照来自同一计算信封，一次事务写入。后台开始前冻结草稿、账号、generation、资料身份、工作草稿 ID 和请求修订号；结果到达后先复核，再将相应冻结输入与接受的输出保存。不得在结果回调时重新读取已经变化的控件。

历史摘要是当时的派生结果，不是当前背包或角色事实；历史查看只读冻结值，加载与重新计算才消费当前资料。

## 4. 空间评估与体积控制

当前格式尚未完成体积验收，不将旧格式的估计字节数当作现实现的测量结果。以下只是容量换算假设，单条大小不是对角色数量或真实玩家输入的承诺：

| 假设每条配置与结果正文合计 | 1,000 条正文约占 | 10,000 条正文约占 |
| --- | ---: | ---: |
| 10 KiB | 9.8 MiB | 97.7 MiB |
| 25 KiB | 24.4 MiB | 244.1 MiB |
| 100 KiB | 97.7 MiB | 976.6 MiB |

实际数量、名称、缺口及格式字段会改变体积。验收需分别测量单角色、常用多角色和当前完整正式角色目录的配置、结果与数据库增量。SQLite 页、摘要、索引、WAL 和空闲页会另外占用空间，因此不声称数据库文件等于正文总和，也不承诺无限保留记录仍占很小空间。

首版空间措施：

1. 同一工作草稿更新同一记录；完全相同的计算信封和输出不重复写入。
2. 保存合计及必要摘要，不复制静态、图片与重复明细；保持 JSON 可审计，不引入专用压缩格式。
3. 列表分页，默认每页 20 条，读取行级摘要及本页有界配置的角色/弧盘名称投影；无搜索时不读取列表之外的配置，也不加载整页结果正文。搜索按 §7 在 DAO 内逐条有界读取名称，先匹配再计数、分页或全选，不把全量配置带到界面。选中后才读取该条完整详情。名称投影只用于展示与检索，不重写历史摘要或原输入。
4. 首版不按数量或天数自动删除历史，避免用户配置被静默淘汰；提供批量删除。
5. 配置和结果序列化正文合计初始保护预算为 4 MiB/记录。实施时证明当前完整正式角色目录的正常输入可保存；它不是角色数量限制。超预算保留计算结果并报告历史保存失败，不截断角色、材料或缺口，也不只保存一半。
6. 删除后 SQLite 可复用空闲页，文件大小不一定立即变小。功能不对运行中的账号库执行 `VACUUM`、删除 WAL 或直接重建文件。

## 5. 历史保留逻辑：按工作草稿合并连续计算

### 5.1 工作草稿身份

每种模式拥有自己的运行时 `draft_session_id`，首个有效计算为它创建历史 ID。该身份不同于账号 generation、角色 ID 或计算请求序号。

| 操作 | 记录规则 |
| --- | --- |
| 当前工作草稿第一次有效计算 | 新建一条 |
| 填写/同步已有材料后点击重新计算 | 更新本草稿对应记录，配置与结果一起替换 |
| 本草稿编辑目标、技能、弧盘或档位后完成自动/手动重算 | 更新本草稿对应记录 |
| 连续重复计算且输入、资料、算法与输出相同 | 保持一条，不重复写入 |
| 仅编辑、尚未得到新有效结果 | 保留上一份已保存配置与结果，不用新输入配旧结果 |
| 重置当前模式、单角色改选角色、多角色清空后重新创建目标 | 开始新工作草稿，原历史保留 |
| 单/多角色模式切换或返回工具再进入 | 原模式会话草稿仍可继续，不因导航创建记录 |
| 从历史加载配置 | 克隆到新工作草稿；源记录保持原值，新计算时建立新记录 |
| 重启、账号或静态资料身份变化导致旧页结束 | 原历史保留，新页从新工作草稿开始 |
| 取消、异常、失效账号/资料/草稿结果 | 不保存该结果 |

加载历史后的新计算即使输入相同，也不通过跨历史内容哈希覆盖源记录；去重只用于同一工作草稿。加载与重置的工作草稿语义遵循本节，历史页不常驻展示重复解释。

多角色工作草稿中增加、移除或修改部分角色也更新本条；全部清空后重新添加才开始新条。这是避免编辑途中积累历史的首版建议，不等于将不同工作草稿按角色集合合并。材料范围切换、展开明细和浏览历史不发起求解或单独写历史；下次有效计算保存相应展示偏好。相同信封去重不刷新计算时间，列表按最后有效计算时间、记录 ID 稳定倒序。

### 5.2 两次计算示例

第一次在尚未填写已有材料时得到需求 100、抵扣 0、仍需 100，保存历史 H1。玩家填写已有 30，再计算，H1 更新为需求 100、有效抵扣 30、仍需 70。历史列表最终是一条，不把用于发现材料的结果当成额外方案。

若第二次求解失败，H1 仍保留第一次已验证的输入和结果；当前页面明确处于结果过期/重算失败状态，不宣传 H1 已更新。若玩家只填写 30 就退出，这些未计算修改不覆盖 H1；未计算草稿自动保存不是本期能力。

材料数据存在正式缺口但生成了可展示的有效计划时允许保存，并记录具体状态。进程崩溃、求解异常或半成品输出则保持旧记录。

### 5.3 保存失败

历史失败不撤销已经有效的计算结果，提供“本次计算已完成，历史保存失败，可重试保存”的窄提示。重试绑定原计算信封；若草稿或账号变化，旧重试入口撤销。更新失败的事务保留旧行，首条写入失败不创建空白行。

### 5.4 保存时点与方案比较

| 阶段 | 页面含义 | 历史动作 |
| --- | --- | --- |
| 目标编辑或材料目录准备 | 只有输入草稿/需求预览，尚无完整计算结果 | 不新增，不覆盖 |
| 正式计算运行中 | 已冻结输入，结果尚未被接受 | 不预先写入成功历史 |
| 结果被当前账号、资料和请求修订接受 | 输入与输出组成一份有效计划；明确缺口的计划也可查看 | 原子创建或更新对应历史 |
| 结果已经展示，历史保存排队或执行中 | 计算完成不等于持久化完成 | 显示正在保存，成功后再标记已保存 |
| 保存失败、页面退出或进程中断 | 最近一次已提交的历史仍有效；当前结果是否保存以状态为准 | 保留旧行，不用新配置配旧结果 |

例如 H1 原来是人物目标 60 级，玩家在同一草稿中改到 70 级并成功计算，H1 更新为 70 级，60 级旧版本不另存。这是“连续编辑一个方案”的规则，不是不可变的每次计算流水。若玩家要比较两个独立方案，先从历史加载 H1 得到新草稿，再改到 70 级计算生成 H2；H1 保留 60 级，H2 保存 70 级。首版复用已有加载/重置入口开始新草稿，不追加一个含义重复的版本管理系统。

“保存历史”和“保存未计算草稿”分别属于结果归档和编辑持久化。本期只归档有效计算：填写已有材料后未重算就退出，不把未求解输入写进旧结果，也不承诺重启后找回这一段未计算编辑。

## 6. 使用流程优化：材料输入提前准备

只合并历史可以解决重复记录，却仍让用户为看到材料而求解两次；只提前展示材料也解决不了用户继续编辑/重算产生的重复记录。因此推荐两项共同实施。

### 6.1 拆分材料准备与正式求解

现有材料计算已经能返回 `totals` 和 `owned_inputs`。将共用准备阶段抽出为 Qt 无关的服务输出，不新增平行公式：

1. 角色、模块、目标选择稳定后，在现有异步 owner 内防抖准备材料需求及可上合材料输入目录。
2. 多角色逐角色复用相同材料服务并合并目录；此阶段不做逐角色或合并体力优化。
3. “仅体力”从当前同一冻结 dataset 的正式副本及合成关系取得分类，不能依赖跑完体力求解才知道输入项。
4. 输入项出现后，玩家填写数量或主动同步材料。
5. 点击正式计算，一次完成抵扣、合成、共享材料分配及完整体力求解，成功后保存历史。

准备阶段显示“材料输入准备中”；目录准备完成可以显示总需求，但不能显示为已完成的最低体力结果。准备阶段不写历史。

### 6.2 性能与复用

- 防抖、队列合并、末次请求有效性沿用现有 Controller 机制；同一模式不并发运行多个正式求解任务。
- 缓存本工作草稿最近一份不可变材料准备结果，键至少包含账号/代次、dataset 和完整有效目标；不维护无限增长的全局缓存。
- 仅修改已有数量时复用需求与输入目录，重新执行抵扣和必要体力优化，不重复读取和投影相同角色成本。
- 改变人物/技能/弧盘目标或参与开关会使相关需求失效；改变猎人/鉴别设置复核副本条件；dataset 变化全部失效。
- 正式计算期间目标变化、取消和材料编辑仍遵守原有过期规则；准备结果和正式结果各自绑定修订号。
- 继续通过既有独立求解进程运行 SciPy/HiGHS，不向 GUI 进程搬求解器。

### 6.3 输入数量与旧结果边界

材料目录刷新只更新展示项，保留按正式 ID 缓存的数量、来源和手工覆盖；新增项保持未填写，消失/隐藏项不得顺手清零。准备阶段不启用复制完整计算结果。

当前单角色换角色会清除该模式旧材料草稿，历史恢复须通过专用原子恢复接口处理，而不是模拟点击角色再依赖信号顺序补值。材料导入缺失项仍为未知，不填零；同步只更新已观测且允许覆盖的项。

如果需要分步交付，先完成工作草稿合并历史，再接提前准备材料输入；两步行为都由本文定义，前一步不宣称已解决首次两次求解的交互问题。

### 6.4 优化后的完整例子与异常处理

以某目标需要材料 A 100 件为例：玩家选好目标，后台准备阶段列出 A 及可参与上合的同族材料，玩家先填写 A 30 件，再点击计算；正式阶段得到有效抵扣 30、仍需 70，体力规划以这份剩余需求计算，最后只创建 H1。准备输入目录不是第二次完整体力求解，也不创建一个“抵扣前历史”。

之后只把 A 改成 40，目标和资料未变：复用需求 100，重新计算抵扣、合成与体力，H1 更新为仍需 60。若把人物目标改高后需求变为 150，旧需求缓存失效，新的准备目录仍保留 A 40 的输入；用户确认并计算后，H1 更新为仍需 110。不能用旧缓存 100 算出 60 并把它配上新的目标。

- 玩家连续改目标只接受最后一份准备结果，旧目录回调不得覆盖新目录；准备目录变更造成的程序性控件更新不当作用户数量编辑。
- 材料数量和目标变化后旧正式结果立即标记过期，完整结果复制入口失效；材料准备完成不解除这一状态。只有新正式结果被接受才恢复。
- 正式计算按钮不依赖提前准备一定成功。若用户在准备结束前点击，交给同一个任务 owner 串行处理最新正式请求，复用匹配准备结果或重新执行同一材料准备入口，再进行求解；不同时启动第二套成本计算或平行体力任务。
- 提前准备失败时报告具体阶段，保留已填数量；手动正式计算仍可以通过同一服务重新尝试。必需静态字段确实缺失时按既有材料缺口语义处理，不能伪造材料总量或把未知体力填成零。
- 准备键采用完整有效目标而不是仅角色 ID，包含技能/弧盘/参与开关；账号、generation 和 dataset 也是键或接受门禁。已有数量不是需求缓存键，但属于正式计算冻结输入；猎人/鉴别变化仍触发新的体力求解。
- 新草稿、账号切换或资料身份变化撤销旧缓存与任务。隐藏的材料数量作为草稿保留，但合成及抵扣只按当前目标和当前冻结资料执行，不因为保留输入就消费无关材料。

## 7. 历史界面与加载

计算页的“历史记录”入口位于“重置”和“复制清单”之间；历史页按时间倒序展示单/多角色记录，支持模式及角色/弧盘名称搜索。历史页顶栏为返回计算、全选、取消全选、删除所选与已选数量，模式与搜索位于右侧；不另放“养成历史记录”小字或第二行选择工具栏。列表列顺序为选择、最后计算时间、当时体力、角色配置；最后计算时间按本机时区完整显示到秒，选择列和时间列保留必要宽度，体力列紧凑且不拉伸，角色配置占剩余空间。角色按原顺序显示为“角色甲（弧盘甲）、角色乙”：选定弧盘即加括号，未参与的弧盘仍是保存配置的一部分；等级、突破和技能目标不再堆入列表。不固定截取前三个角色，名单采用紧凑单行并省略溢出，悬停与详情可看完整名单，行高随字体适配。

搜索使用共享的纯名称匹配规则，角色和弧盘均支持原文、全拼与首字母，忽略大小写；例如“阿德勒 / adele / ADL”和“勿忘伞 / wuwangsan / WWS”。名称来自该记录的冻结配置，弧盘未参与养成也可检索，不读取当前角色页来改写历史。旧记录不必重新计算或迁移索引即可搜索弧盘和拼音：DAO 使用有界的逐条名称投影及连接内有界匹配缓存，列表数量、分页和全选采用相同条件；不读结果正文，不缓存账号完整 payload 到全局，不更改配置、修订、哈希或时间。畸形配置仅按有界的旧角色检索字段匹配，不猜弧盘名称，仍保留无筛选浏览和删除能力。

详情为可滚动的只读配置卡、当时材料图片卡和合并体力摘要。列表与预览初始约为 45% / 55%，仍可拖动调整；首次展示以后不因选记录、切范围或再次进入而覆盖用户拖动的比例。预览工具栏左侧显示蓝色合并体力，右侧保留显示范围与加载配置；未选记录、筛选改变或删除后清空体力，不保留上一条数值。删除“历史预览”、当时配置时间、猎人/鉴别等级及历史只读的小字；这些原输入仍完整保存并供加载恢复，不改变正文格式。

每个角色配置卡始终占整行，与材料合计和刷本建议同宽，折叠后也不缩成并排小卡。首个角色默认展开，其余默认折叠。人物、技能和弧盘配置紧凑展示，保留当前/目标等级、突破和模块开关，未参与项明确标注。各技能等级一致时合并为等级范围与项目数，不一致时按保存顺序逐项显示；技能名称没有冻结证据时不读取当前资料猜测旧名称。

材料卡在空间足够时一排五个，窄屏或大字体下自动减少列数，避免水平滚动和数量遮挡。卡片包含图片、名称和纵向的总需求、有效抵扣、仍需，仍需加粗；长名称省略时可悬停查看完整名称与三个数量，键盘可选择材料，全部数值只读。展开材料合计后按当前显示范围一次铺开全部行，不设三行限高或内部滚动条，滚轮由历史预览外层统一处理；键盘跳到末项时也由外层滚动使该项可见。保留模型/委托绘制和有界图片缓存，不为每件创建子控件。图片只按正式材料 ID 从当前受管材料资源目录解析；旧资料缺图、图片读取失败时使用通用占位，保存的名称和数量保持不变。不从历史正文读取图片路径，不复制图片进账号历史，也不通过图片补造历史材料事实。

材料保留全部/仅体力切换。完整体力只显示一份合并值，未知时明确标为合并已知体力与完整体力未知；刷本建议默认折叠，缺口摘要保持可见。不再渲染“查看原始已有材料”和“更多信息”分区，也不显示底部常驻加载解释；原数量、来源、资料身份及缺口仍保存在记录中。底部仅在读取、加载、删除进度、具体失败或操作结果需要说明时出现，正常浏览不占一行。展开与范围切换不重算或写库。

已有记录从原配置取得弧盘名称，只添加运行时列表投影；原摘要、正文版本、指纹、修订号与计算时间均不变，避免展示改版让旧记录被误判损坏。

历史详情提供“查看当时合计”和“加载配置”，两者不混淆：

- 查看只读配置和结果快照；即使当前目录缺角色或副本，也能使用保存的名称和数字展示，图片缺失使用通用占位。
- 推荐加载原样恢复当时人物/技能/弧盘当前值、目标、数量、来源及手工覆盖，不自动读取角色页或同步材料；提供“已加载历史配置；当前状态与材料数量请确认”的简短提示。
- 自动获取最新当前等级或最新材料属于另一个显式更新动作，具体入口待确认；不得在恢复过程中静默混入新状态。
- 恢复到新工作草稿后清除当前结果，等待点击计算；停止原待提交重算并屏蔽恢复中的控件信号，避免半份配置触发求解。
- 多角色按记录顺序恢复，原 `line_id` 只属于历史快照，克隆到当前草稿时建立新行身份并保留对应关系，避免与当前控件或新请求冲突。
- 恢复先做结构与正式 ID 校验，再整体替换。角色、技能、弧盘、材料缺失或等级范围变化时列出问题，原页面保持不变；首版不自动跳过角色、猜名称匹配或夹取新等级范围。
- 资料不同但配置仍合法时允许加载，重新计算使用当前同一完整 dataset，历史旧结果仍只在历史详情中展示。

## 8. 多选、全选与删除范围

### 8.1 选择行为

- 每条记录有复选框；支持跨页保留选择、取消全选和显示已选数量。
- 按钮简写“全选”：全选当前展示条件下的全部匹配记录，包含跨页结果而非仅本页。未筛选时指当前账号全部已有历史；筛选后只选该模式与搜索条件的结果，绝非所有账号。列表与全选使用同一 DAO 条件，按钮帮助说明分页范围。
- 切换筛选条件时清空选择并更新计数，避免隐藏的旧选择被一起删除；单纯分页不清空。
- 全选时从 DAO 获取匹配记录的 ID 与修订号快照，不依靠已经渲染的本页控件，也不只传一段查询条件。
- 全选后新保存的记录不在已选集合；数量旁不堆叠长说明，冻结范围放在悬停说明中。自动更新仍按正式记录 ID 跟踪。

### 8.2 删除确认与事务

点击“删除所选”后冻结当前账号、generation、全部已选 ID/修订号与数量。确认框显示“删除当前账号所选 N 条养成历史？”，注明会删除历史配置和当时结果，但保留当前页面草稿、角色档案及背包；默认取消，使用既有警告样式和提示音。

确认后由账号绑定 Service 再复核身份，再经 DAO 参数化 SQL 和单一事务删除确切集合。大集合分块执行以适配 SQLite 参数上限，但所有块仍在同一事务内。不得执行无条件 `DELETE`，也不得在确认后重新按筛选条件扩大集合。

- 某条在确认期间已被删除：按幂等语义计入“已删除”，剩余明确 ID 在同一事务完成，不把缺失当其他记录。
- 某条在确认期间完成新的计算更新、修订号不匹配：整批不提交删除，刷新并要求重新确认，防止删除用户尚未确认的新版本。
- SQL、账号代次或数据校验失败：全部回滚，保留未提交删除前的状态；按钮恢复并显示可重试原因。
- 成功后按实际删除结果刷新列表、清空选择；不因行号变化删除下一条记录。

### 8.3 防止删除后重新出现

删除可能与当前草稿的后台重算/保存回调重叠，必须单独处理：

1. 首次成功结果采用一次明确插入；后续保存采用绑定 ID/预期修订号的条件更新。更新命中零行不执行通用 upsert 或补插入。
2. 删除成功后关闭该历史 ID 的运行时保存绑定，撤销排队写入和保存重试；已经持有旧 ID 的迟到结果只能继续显示有效计算结果，不能重建已删除历史。
3. 删除当前工作草稿对应记录不清空输入或当前计算结果。自动重算保持历史写入抑制，直到玩家下一次主动点击计算，此时开始新的保存绑定及新历史 ID。
4. 删除前已经保存的记录属于冻结删除集合；删除确认后首次出现的新计算记录保留，不假称“全选删除”包括尚未保存的未来结果。
5. 新 ID 永不复用。历史写入、删除及关闭绑定的操作通过同一账号窄服务按确定顺序协调，DAO 条件更新作为最后防线。

主动计算与自动重算的来源在请求提交时冻结。删除后到达的旧主动计算也属于旧绑定，不能因回调发现记录缺失而当作“下一次主动计算”补建；只有删除完成后新提交的明确主动计算才能解除抑制。

示例：H1 已选，后台重算还在运行。删除 H1 后，旧结果到达仍不插回 H1。玩家主动重新计算可生成 H2；这个 H2 是明确的新计算记录，而不是被删记录复活。

### 8.4 删除的用户预期与资源边界

- 首版采用明确确认后的直接删除，不设回收站或静默自动淘汰。确认框说明历史配置与历史结果一起删除；已有导出与升级备份是独立副本，不随本次删除改动。
- 搜索结果的“全选”不是“本页全选”。例如筛选出 83 条、每页 20 条，全选应选中 83 条；随后新增的第 84 条保留。分页、排序或行号改变不改变所选正式 ID。
- 选择 ID/修订号可以跨页保存，但历史正文仍按需读取，禁止为全选加载全部结果 JSON。大规模选择的读取和删除放在后台 owner 中，显示忙碌并阻止重复提交；资源不足时保留原记录并说明操作未提交，不偷偷退化为只删本页。
- 确认删除以后开始事务，不能在等待用户确认期间持有数据库写锁。事务开始后按块删除但只提交一次；途中取消或账号代次失效在提交前触发整批回滚。已成功提交的删除不因为关闭弹窗或晚到取消而恢复。
- 删除完以后页码重新限位，例如最后一页被删空时回到最后一个有效页；当前详情和加载入口同时清理，过期详情回调不能再显示为当前选中项。坏记录详情读取失败时仍可按合法记录身份删除。
- 若所选记录在确认期间从修订 2 更新到修订 3，整批保留并要求刷新重选，避免自动刷新把确认对象悄悄换成新版本。记录在确认期间已被其他操作删除则按幂等处理，完成提示采用实际删除数量。

## 9. 数据模型与分层

新增当前账号库中的 `cultivation_history`，不借用角色、配装、同步设置或完整背包表。建议字段：

- `history_id`：不可复用的正式记录 ID；`mode`；`revision`。
- `first_calculated_at_utc`、`last_calculated_at_utc`：同一草稿更新保持创建时间。
- `payload_version`、完整 `configuration_json`、轻量 `result_snapshot_json`。
- 列表需要的 `summary_json` 或必要摘要列；模式/时间/ID 索引。

历史不建立指向静态角色、库存快照或物品归档的级联删除外键。角色档案、库存快照过期或资料替换均不自动删历史。

职责按现有依赖方向：

| 层 | 新增/调整职责 |
| --- | --- |
| 公共模型 | 完整草稿、计算信封、结果快照和列表摘要；JSON 显式字段与版本 |
| DAO | 追加迁移、原子插入/条件更新、分页、选择集合、事务批量删除 |
| Service | 账号冻结、保存绑定、结构校验、资料兼容校验、快照投影和失败重试 |
| Controller | 准备/求解任务、修订号、取消、迟到结果丢弃、历史读写 owner |
| UI | 列表选择、确认、配置投影、历史合计展示；不实现 SQL、合成或体力公式 |
| 组合根 | 显式注入当前账号历史服务，切账号时关闭旧 owner 并重建 |

候选新增模块为 `cultivation_history_models.py`、`cultivation_history_service.py`、`cultivation_history_dao.py`、工具页历史 Controller/View 和草稿恢复适配器；实际归属按仓库现有层次决定。先收缩或拆分接近行数门禁的页面，所有新增/触及 Python 文件遵守 800 行门禁。

## 10. 数据安全、迁移与回滚

- 只写当前账号的私有历史；generation 是运行期写入门禁，不把旧 generation 持久化成以后加载的账号绑定。
- dataset 保存可携带的正式身份；本机绝对路径属于运行上下文，不序列化到历史的可导出 payload。
- 输入与输出统一事务；数据库忙采用有界等待/重试，重试不改变冻结输入，也不阻塞 GUI 或跨账号兜底写共享库。
- 序列化使用显式白名单字段，不直接 `asdict` 整个含路径/图片字段的现有计划，也不使用 pickle、对象反序列化或动态执行。
- 校验 JSON 总字节、深度、数组规模、重复 ID、整数类型/范围、未知字段与版本；材料显式零和未知值分开，负数、非整数和身份冲突均报具体错误。
- 大小检查在解析前执行，解析后的嵌套与集合检查有界。恢复值只作为已验证的输入数据，不将名称、路径或文本变成 SQL、文件名或可执行内容。
- 迁移按实施时的实际 schema 追加新版本，旧迁移不改义；验证新建、旧库升级、失败回滚和重试。
- 升级前账号库使用 SQLite 一致性备份，活库不复制 WAL/SHM；迁移失败事务回滚，旧有效数据保持。
- 升级备份由 DAO 的明确迁移备份策略管理，不混入默认账号导出或发行包；禁止为新增历史功能批量清理既有备份。备份恢复与历史删除是不同操作。
- 迁移成功后的旧程序可能拒绝新 schema，代码版本回退不等于数据库回退；需要回退时停止账号任务，并以升级前一致性备份恢复。单条历史删除不靠删库或回退 schema 实现。
- 账号导入/导出沿用当前用户库的一致性备份与校验，历史随该账号库携带；不新增独立共享 JSON，不附图片、日志、截图、采集原文、凭据或整份观测归档到历史。
- 导入新版或畸形历史时有明确版本/结构处理；坏记录只影响该条历史的读取，账号有效业务数据不被覆盖。详情解码失败仍可按正式历史 ID 删除。
- 分页列表摘要也按版本、字段、数值类型与体力状态校验；损坏摘要只显示该条异常提示，仍保留可勾选删除的记录身份。完整体力零与完整体力未知分开，异常数值不能阻断整页操作。
- 日志只记录保存/删除的生命周期、数量、错误码及耗时，不倾倒配置、角色名称集合、材料列表或结果正文。
- 删除是数据库逻辑删除，不宣传介质级擦除；空闲页、WAL 和既有导出/备份可能保留旧字节。运行时不为本功能直接清理账号库文件。

## 12. 验收清单

### 保存与空间

- 单角色及多角色配置、关闭模块输入、正式 ID/顺序、显式零与来源完整往返。
- 第一次总需求计算与填写已有后重算保持一条；记录配置和结果同时变为新版本。
- 自动重算、重复点击、加载历史后新计算、重置、模式切换遵守表中规则。
- 仅输入变化、半成品、错误、取消、迟到回调不覆盖上一份有效历史；保存失败保留计算结果及旧行。
- 三合一有效抵扣、经验材料不参与三合一、共享材料只消费一次、合并体力不按角色求和。
- 部分/不可用的完整体力保持空值，历史状态与缺口可见。
- 用真实正常规模及当前完整正式目录测量 JSON/账号库/WAL 体积；合成估算不冒充生产验收。

### 输入准备与加载

- 正式计算前材料输入可出现，准备阶段不运行体力求解或产生历史。
- 仅改已有量复用需求；目标/资料变化失效；准备迟到回调不覆盖较新的目录。
- 材料隐藏、目标变化和目录重排保持按正式 ID 录入的数据；未观测项不归零。
- 历史原样恢复后原结果清除，恢复过程中零次完整求解，点击计算后恰好一个有效任务。
- 旧资料结果可查看，角色/技能/材料 ID 缺失或范围变化在替换前提示，当前草稿完整保留。

### 批量删除与账号安全

- 多选、跨页选择、全选筛选结果、取消全选、筛选变化及数量提示。
- 默认取消，确认时冻结确切 ID，之后新增记录保留；同名记录/排序变化不误删。
- 选中行被更新要求重确认，已被删除幂等处理；分块删除中途故障整批回滚。
- 删除当前保存绑定后，自动重算、迟到保存和旧重试均不复活记录；下一次主动计算可产生新记录。
- 在准备、求解、历史加载、确认删除和写库期间切账号，旧操作不写新账号、不刷新新账号页面。
- 新建库、旧库迁移、迁移失败回滚、升级前备份恢复、账号导入导出与坏记录隔离。
- 三主题、键盘选择/确认、屏幕/DPI 限位、大列表分页、长角色列表和求解期间滚动可操作。
