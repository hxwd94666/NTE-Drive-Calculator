# 第一次架构重构后复审开发方案

**状态：本轮源码整改与本机已授权集成验收已收口；没有按既有清单确认而尚未处理的源码整改项。集中 core/full 的原失败及定点修复分别保留，不改记为全绿；外部组件契约差异、具体性能未达标记录与独立发布门禁仍单列。完成范围见[本轮复审收口](../validation/architecture-renewal-day1.md#30-本轮复审收口)。**

初步重构已经形成新的项目基础。本轮在此基础上细查隐藏缺陷，重新审视模块边界、完整业务实现、
测试价值和维护体验，并补做上一轮为赶进度而遗漏、浅审或只完成局部的原定任务。
目标不是再次推倒重写，也不是给已有结论补更多证明，而是让功能保持正确、结构真正清晰、
低配运行更稳定，fork 开发者更容易理解和扩展。

## 1. 范围与方案关系

本文合并承接初次架构重构的完整目标、仍待完成的门槛与本轮复审步骤，是当前唯一开发计划。
旧四日排期、固定时长与额度预算不自动延续；初次实施结果保留在原验收记录，稳定事实归对应领域文档。
复审以实施时 `test` 的实际提交和工作区增量为起点，不回退初步重构，也不从旧工作区覆盖当前成果。

本轮保留全部原定方向：基于成熟功能补足实用框架、全局功能模块化、合并散乱补丁、主动删减低价值测试、
补齐关键中文注释、改善低配流畅性和稳定性、发行瘦身、语言及识别语言预备、OCR 可拆卸、fork 路线与版本更新 skill。
框架可以补、可以合并、可以删减；是否保留取决于它是否承接真实责任并降低开发和运行成本，而非抽象名称或层数。
同时将长期有效规则沉淀到 `AGENTS.md`、更新 NDC 游戏版本维护 skill、主动删减合并 `docs/`，作为复审正式交付，
不只留作建议。其他低成本改进按第 7.5 节酌情纳入，避免增加开发负担。

以下范围保持：

- 成熟功能及数据语义优先保持；前端只修具体交互、文案、可读性和布局问题，不重做菜单与视觉体系。
- 真正的伤害分配策略另行开发，本轮核对设计与未就绪边界，不借复审实现新求解器或第二套评分事实源。
- 语言仍是扩展预备，不扩为全量翻译或新语种识别发布；版本更新 skill 的维护不自动启动游戏数据晋升。
- [仓库契约](../../AGENTS.md)及[项目用途声明](../../RESPONSIBLE_USE.md)继续有效。个人数据、正式组件及已发布迁移保持各自边界。
- 实施、专项及集成检查按用户的启动指令和已有有效授权执行，测试范围见第 5 节；提交、推送、打包、安装、部署及真实游戏操作仍分别确认授权。

## 2. 复审起点与遗漏处理

### 2.1 已有事实与本轮应回答的问题

[初次验收记录](../validation/architecture-renewal-day1.md)已保存领域整改、专项、集中检查和性能代理结果，
也明确保留了历史失败、暂挂集合以及真机、长期运行和发行验证缺口。它是复审输入，不是“全项目已无问题”的证明。
源码修改、静态检查、专项通过、完整产品可用和正式发行通过，继续分别判断。

工作区迁移曾因宽泛的 `build/` 忽略规则漏掉战报源码包和相应测试，导致启动导入失败。
该问题已经通过补回文件并将规则限定为 `/build/` 修复；复审关注的是同类交付遗漏与发现机制，
不是再将这次修复重复实施。仅比较 Git 可见文件、仅通过导入或仅复现一个参考页面，都不足以证明完整交付。

对于“后半程加速可能留下质量缺口”，应核对实际实现与原任务，而非预先认定后半程全部有问题。
已经清楚、稳定且有适用证据的代码可以保留；只搬了目录、补了文件头或取得 AST 等价的记录，
也不自动证明业务边界、职责划分和关键注释已经审到位。

### 2.2 对原任务只做一次完整对账

复用原领域清单和消费者映射，以“原目标 → 当前落点 → 已有证据 → 复审决定”建立一份简短的工作清单。
记录领域和问题即可，不给每个函数重新建档，不逐轮重建全仓清单。

| 原任务状态 | 本轮处理 |
| --- | --- |
| 已实质完成，当前实现与证据仍适用 | 纳入当前领域语义复审；确认后保留，复用原检查结果，不重做相同改动或无变化运行 |
| 因时间或效率暂缓、只完成局部，或仅有形式性审查 | 重新进入实施清单，写明尚缺的具体责任、消费者、删除项或关键检查，补到原出口 |
| 标为完成但源码、消费者、失败记录或实际交付互相矛盾 | 撤回该项完成判断，定位真实原因；修复代码或补必要验证，不靠改措辞消除缺口 |
| 用户明确暂挂，或需要尚未授予的独立操作权限 | 单列范围与影响，保持原限制；进入对应工作前取得明确授权，不把它混同于赶进度跳过 |
| 新功能或明显扩大工程的新改造 | 单列后续建议，不占据本轮主路径；用户允许的低成本维护改进按第 7.5 节随批实施 |

优先级为：**启动与交付阻塞、数据安全 → 计算与保存正确性、生命周期与卡顿 → 结构、测试和可读性完善 → 有依据的界面小修**。
优先级只决定顺序，不把模块化、删测或中文注释降为可做可不做的收尾工作。

用户已明确指出：**测试代码仍庞杂、许多用例并非核心；部分目录仍有大量业务文件缺少细分归属。**
这两项是首批整改重点，不只作为可能风险记录。完成判断看实际删减、夹具收敛和细化后的责任归属，
不是补一句“已经审查”，也不是只挪动文件或象征性删除少量断言。

## 3. 全项目逐域复审

复审覆盖自有运行代码、开发与发行工具、保留测试和夹具，以及影响运行的配置、清单和资源引用。
第三方源码、生成文件和本机产物不机械重写；资源按用途和引用关系核对，不扫描个人数据凑覆盖率。

每个领域至少走完一次“入口 → 冻结输入 → 规则与编排 → 持久化或外部调用 → 展示 → 取消与关闭”，
同时反查动态入口、其他消费者及测试发现。已有模块清单用于导航，仍须阅读当前实现与关键分支；
可合并审查职责相近的模块，不用一个成功页面代替其他领域。

| 领域 | 本轮重点排查 |
| --- | --- |
| 启动、组合根、源码交付 | 导入副作用、循环及聚合导入；路径是否依赖原工作区；普通导入与真实就绪是否分开；忽略规则、跟踪文件、动态引用和构建输入是否一致 |
| 账号、配置、工作模式 | 切账号顺序、代次失效、草稿归属、权限撤销、失败保留旧事实；本机配置与账号数据是否仍混用 |
| 角色、面板、权重与蓝图 | 正式身份、有效面板和评分入口是否唯一；旧字段迁移是否完整；页面、计算、配装是否解释同一组输入 |
| 库存、计算与配装 | 完整快照、冻结请求及预览、UID 与槽位约束、锁与历史评分；同分恢复、单项失败和保存是否沿用当前正式 contract |
| 扫描、鉴定、倒带与输入 | 共用识别流程是否真正接管；完整结果提交、识别配置身份、取消/异常释放、临时文件与失败重试；输入设备驱动沿用用户确认结果 |
| 战报、编辑与分析适配 | 原始事实与派生结果是否分开；离线辅助代码是否误入正式入口；独立组件能力、缓存身份、结果未知和页面 owner 是否一致 |
| 同步、组件、环境与更新 | 文件、进程、连接、能力和业务就绪是否混淆；权限、后验确认、物理退场和幂等边界；避免通用重试重放外部动作 |
| DAO、Integration 与公共设施 | 事务、迁移、连接、原子写入和一致性备份；重复缓存/轮询/任务设施；错误是否被吞掉，资源是否只有一个明确 owner |
| 工具、静态资料、UI 与发行链 | 只读工具边界、候选及正式晋升、公共素材；三主题与键盘/窗口可操作性；依赖收集、OCR 选择、skill 和 fork 命令是否仍消费真实入口 |

每域只留一份可执行结论：已确认的责任边界、要修的问题、要合并/删除的实现、要保留的关键测试、
要补的中文说明、必要检查与余项。领域负责人同步完成这些工作，避免“源码已结束，测试和注释以后再说”。

## 4. 模块划分与完整实现

### 4.1 模块化看责任而非目录数量

继续采用“外层表达架构职责，内层表达业务领域”。检查范围是全局，不限于 `services/`：
`features/`、`domain/`、`storage/`、`integrations/`、`ui/`、`models/`、`scanner/`、`solver/`、`optimizer/`、工具与测试均按实际责任判断。

- 检查层根目录是否仍混放大量单领域业务；跨域模块应有明确职责和消费者，而不是仅因为历史上位于根目录就保留。
- 检查业务大目录内部是否仍混放多个子领域或完整子流程。仅从层根目录搬进一个大领域文件夹不算细化完成；
  按真实职责继续组织成 `<层>/<领域>/<子领域或流程>/`，让开发者直接定位相关实现，而不是在长文件列表中猜前缀。
- 检查新子包是否只是旧文件的集中搬家：规则、owner、数据流和调用关系是否仍散落、循环或跨域访问私有实现。
- 检查过度拆分：同一短流程跨多个只转发参数的小文件时，应合并到合适的责任模块；分层不是跳转越多越好。
- 检查公共入口与共享设施：避免包级全量重导出、万能 Context、无 owner 的 `common/utils`、平行调度器和重复状态源。
  新抽象须说明接管的真实消费者及删掉的重复实现；成熟领域无需为了对齐目录外观增加包装层。
- 迁移须连同静态/动态 import、测试 patch 目标、工具、资源定位及构建入口一起完成，随后删除被替代入口和临时桥接。
  `__file__.parents`、当前工作目录、环境变量和导入顺序的偶然成立应重点核对。

已满足这些要求的模块保留，不为统一命名、凑层数或降低单文件行数制造新的碎片。
Python 文件继续遵守仓库行数门禁，拆分依据是职责，不是机械切块。
首轮逐个核对层根与业务大目录，对仍混放的职责列出简短的“保留在本层、下沉到子包、合并、删除”清单并实际执行。
目录深度和文件数量只作定位线索，不设每目录固定文件上限；内容单一且便于理解的小目录无需强行再分层。
完成时应能说明重点目录原来混放哪些职责、现在分别由哪里负责，而非只汇报新增多少文件夹。

公共任务与读取设施推广前，保留两类真实消费者的原验收门槛：基础权重流程，以及规模或取消特征不同的读取业务。
沿已有入口核对逻辑关闭与物理释放、反复生命周期回归有界资源、同一连接事务和默认测试发现；
冷启动、热态及结果应用不出现明显退化。复用适用的原证据，不为这一门槛新增推广平台或重复审查链。

### 4.2 将补丁链合成完整业务

对重复校验、保存后补刷、多套 dirty 标记、窗口转发、异常兜底和延时重试，先恢复其共同服务的业务流程，
再统一状态与责任。完成状态应是正常路径、失败路径、取消和兼容规则能从一个正式流程解释，而非在旧补丁外再包一层。

合并后核对所有消费者并移除无消费者 helper、旧修复入口和重复状态。已发布迁移、有效旧数据升级以及
结果未知时的保护不是“旧代码”，按正式契约保留。减少行数以删除重复责任为主，不以压缩表达或吞异常换数字。

### 4.3 中文说明应能帮助 fork 开发

新增、迁移及保留模块都核对关键中文说明。重点解释职责边界、输入身份与单位、未知值、线程/资源 owner、
事务和缓存、取消与迟到回调，以及看似可删但有业务原因的分支。
文件头有中文不等于注释完成；重复签名、逐行翻译和与实现矛盾的说明应删改。

接口关键说明沿用 [Fork 开发路线中的模板](../reference/fork-development.md#6-接口关键说明模板)和已有真实参考业务，不逐函数粘贴大段模板。
复审者应能沿一次普通修改找到页面、规则、保存与验证入口；需要靠多个历史报告猜流程时，继续收敛代码或说明。

## 5. 测试代码的再次精简

测试是本轮需要主动优化的代码，不默认守住初步重构后的规模。按本节价值规则，
先确定本领域少量关键保护点，再决定保留、合并、重写或删除。
对本轮全部纳入集合逐文件、逐用例组做实际价值筛选，文件内只有少量核心保护时只保留必要部分，不因一项重要就整文件留下。
非核心测试即使曾经通过、执行很快、名为 regression 或具有独立小行为，也不自动获得保留资格。
本轮要求清理大量非核心保护形成的维护负担，避免只挑几条最明显的装饰断言交差。

1. **直接删非关键项。** 废弃入口、私有结构、固定源代码片段、装饰样式、无风险转发、普通 getter/setter、
   无真实后果的参数穷举，以及已经由同责任行为用例覆盖的重复断言，按价值判断删除，无须逐项再请求许可或先造替代测试。
2. **合并重复保护。** 相同输入和结果在 helper、Service、UI 层重复验证时，保留最贴近正式责任的用例；
   清理仅服务被删用例的夹具、模拟器和兼容支架，不把冗余藏进参数化或慢测目录。
3. **保留关键后果。** 计算结果、冻结保存、账号隔离、事务/迁移、来源完整性、UID 唯一、权限、取消与物理退场、
   外部后验确认及未知结果不重发等关键保护继续有效。一次写入的调用次数可属业务约束，普通内部调用布局则不是。
4. **只补确实缺的关键点。** 不按生产函数数量配套测试，不要求新增量等于删除量；关键但脆弱的测试改到公共行为，
   测试工具出问题优先修最小原因或复用成熟入口，不改生产设计迎合夹具。
5. **核对留下的集合。** 统一经现有质量入口发现，检查嵌套目录、函数/TestCase、参数化、子进程和 `core` 选择。
   零用例、漏发现、子进程失败及缺前置条件须有明确结果。

每次删测只回答“它保护哪个关键后果、是否已有有效保护”。答案清楚即可做决定，不逐断言写审查报告。
不要求先把所有待删除旧测试修到绿色；但当前仍有效的关键行为失败，应修真实缺陷，不以删断言求绿。

用户已在本轮明确解除上一轮 51 份暂挂测试及 7 份依赖测试的限制，全部纳入阅读、删减、迁移与必要执行。
历史排除集合的检查结果仍按当时范围保留；本轮集中验收覆盖当前保留集合，不把旧补充运行改写为正式通过。

规模与耗时采用同一基线、非重叠口径统计：文件、测试函数/节点、夹具、代码行和运行时间分别表达。
移动、改名、跳过、退出发现和缩减采样均不算删除；不设删除百分比，也不以覆盖率或绿色数量作为优化目标。

## 6. 隐性缺陷与低配体验

重点检查只在重复操作、慢 IO、任务交错、首次使用或失败收尾时出现的问题：

- UI 主线程中的同步 IO、等待、解析和批量控件创建；后台查询完成后一次性投影造成的长停顿。
- 快速切页、筛选、换角色、切账号、取消后立即重试时，过期结果、草稿、缓存及 worker 是否串用。
- 已接受写入、逻辑取消和物理结束是否分开；关闭是否阻塞 GUI，或提前销毁仍运行的任务。
- 循环刷新、重复订阅、无界队列、重复解码、重复查询和缓存未失效；优化是否以持续增长的内存换速度。
- 缺组件、缺资源、空/坏配置和权限错误是否保留旧事实并给出具体下一步，避免假成功、空结果或无限等待。
- 延迟导入是否只是把启动停顿移到首次计算/识别；需要同时观察首次使用和热态，不只报冷启动更快。

测量复用[响应性口径](../validation/ui-responsiveness.md)。固定输入规模、环境、依赖和时间边界，
区分首次可交互、业务真正就绪、结果应用、取消反馈和物理收尾。
选择能暴露问题的小/中/大输入与一段有界重复操作序列；没有持续增长迹象时不扩成任意时长的耐久测试。
优先观察最大停顿、响应长尾、峰值/稳态内存、线程/句柄/控件回收和空闲成本；样本不足时不报不稳定的 P99。

已有测量适用于当前输入时复用；改动影响热路径或出现回归线索时再做同条件前后比较。
比较阈值和噪声范围先确定，不在后测失败后放宽。真实低配、资源受限代理、离屏 Qt 和真实窗口分别给结论，
不把单次离屏启动当作滚动、绘制、混合 DPI 或长期稳定证明。手柄驱动不重复验收，只检查本次触及的应用输入和取消行为。

#### 鉴定与扫描的功能内语言预备

UI 语言、游戏/截图输入语言和资料显示名独立。图片鉴定与扫描复用既有识别管线，手工及剪贴板入口另核对分类、品质和名称别名。
未来识别配置至少冻结输入语言/版本/dataset、模型与字典、别名到正式 ID 及数字规则、布局/模板与来源哈希；
UI 语言补丁不加载识别模型或改变规则，后端和设备选择也不代表语言。缓存和增量按这组身份隔离，运行中不重绑；
配置变化需要重新解析，不清理已保存库存。单任务按需初始化，额外语种资源不默认打包、全量预热或自动下载。

本轮核对当前入口责任与默认中文路径。新语种发布另验 UI/输入语言组合、正式 ID/数值等价、歧义/缺资源、布局、
运行中偏好变化、取消/换账号和增量身份漂移，并核对耗时、内存及体积；未验证项保持预备状态。
图片识别全链失败恢复、真实低配及窗口验证缺口继续保留，不由单个解析器通过替代。
OCR 拆卸沿现有集成入口核对仅 OpenVINO、仅 ORT CPU/DirectML、选中库缺失及全部缺库，覆盖实际消费者；
CPU/GPU 与发行包矩阵分别记录，复用适用证据，不因本次文档合并重跑。

### 7.2 将有效规则沉淀到 AGENTS

本轮实施时同步整理根目录 [AGENTS.md](../../AGENTS.md)，让之后的开发默认遵守已经证明有益的规则，
而不是再次依靠维护者逐次提醒。先对照现有条款，已有规则直接完善原位置，重复和失效表述合并或删除。

适合沉淀的内容包括：

- 按层与业务/子领域归包、共享代码有明确归属，避免平铺混放和只转发参数的过度拆分。
- 同流程补丁合成正式实现，消费者与资源引用一起迁移，替代入口和孤立夹具及时退出。
- 新增及保留实现维护关键中文说明；测试按核心后果筛选，直接删除非关键或重复保护，不等量补测。
- 源码交付同时核对实际项目文件、跟踪/忽略规则、动态入口及构建输入，避免构建目录规则误伤源码包。
- 延续单一资源 owner、冻结身份、失败保留旧事实等已有硬边界，以及按风险选择验证、复用适用证据的协作规则。

只有已落实、经复审确认且具有长期跨功能价值的要求进入契约；尚未实现的目标留在路线图，
具体公式、领域细节和命令引用其权威文档。模型档位、临时排期、批次流水账、本机路径与单次故障处理过程不塞进 `AGENTS.md`。
规则应短、明确、可执行，不为每条规则新增测试、审批或强制模板，也不将所有优化经验升级为全局限制。
完成时核对条款与实际实现一致、与原数据安全边界一致，并保持新开发者能快速读懂的体量。

### 7.3 更新 NDC 游戏版本维护 skill

沿用 `skills/nte-game-update/`，不另建平行 skill。同步检查 `SKILL.md`、`references/`、`scripts/` 和调用元数据；
旧模块名、构建参数、目录定位、功能适配落点及示例要按当前代码改正，职责变化也要重写，避免只替换路径字符串。

维护流程应覆盖：输入新版解包与版本/来源身份 → 差异盘点 → 主静态或独立图鉴候选 → 数据与公共素材更新
→ 新角色及改动机制逐功能接入 → 必要校验 → 在授权范围内正式晋升与回退。
逐功能接入至少区分角色面板/养成、评分与配装、鉴定/扫描相关资料、分享及技能素材、战报与组件能力；
“角色行已导入”不代表所有功能已适配，未知机制或组件缺口须有明确落点和状态。

使用者应能提供解包位置和本次更新目标后，沿既有真实入口推进，无需重新翻历史聊天或猜维护者机器路径。
参数、schema、版本与能力名从正式代码和清单读取；公共技能 ID、别名及素材来源/哈希随同版内容维护，
数据候选、代码接入、正式晋升和实机表现分别报告。流程复用已有维护工具，不扩建通用更新平台。

验证只覆盖变更后的引用、真实命令参数和确有必要的最小合成流程，不为维护 skill 重跑完整解包、构建或真实游戏更新。
仓库版本是编辑事实源；明确个人安装副本的更新/调用方式，并在相应范围获准后同步核对，避免新指令实际调用旧副本。
仓库维护完成、本机可调用和真实新版更新通过分别交付，执行版本更新本身仍遵循当次授权。

### 7.4 主动精简和重写 docs

`docs/` 也是本轮需要实质整理的内容，不只修链接或追加新说明。按读者任务与事实所有权判断保留、合并、重写或删除，
复用 [文档索引](../README.md) 的组织方式，不为每个小主题再建文件，也不把所有内容合成一本难以定位的大文档。

- **删除无当前价值内容。** 淘汰已被替代的方案、失效操作步骤、重复解释、纯阶段汇报和无使用场景的教程；
  完成计划的有效结论进入当前事实文档，尚未完成的内容留路线图。历史演变由 Git 追溯，不在正文反复保留旧版。
- **合并同一责任的内容。** 同一功能分散的补充说明归回对应章节，一个事实只留一个权威位置；
  架构、用户行为、协议、开发步骤和验收结论各司其职，其他位置简短引用，不整段复制。
- **重写需要保留的文案。** 先写读者要做什么、入口在哪里、何时生效、影响与限制；删除长篇过程叙述和重复免责声明，
  只保留会影响正确使用、开发或判断能力范围的信息。用户帮助简洁，开发细节归开发文档。
- **保留必要事实与证据。** 数据格式、历史数据兼容、协议/许可、关键限制、未解决缺口及必要复现依据保持明确；
  压缩批次流水账不改写失败为成功，不删除仍支撑当前结论的唯一记录或回退依据。
- **合并与引用同批完成。** 先把必要内容落到唯一归属，再删除旧文件/章节，更新 README、索引、AGENTS、skill、
  代码中的相关链接和锚点；不长期保留只写“已迁移”的空壳文档。短表记录合并去向即可，不逐段建档。

完成判断看新开发者能否迅速找到启动、普通修改、必要检查、产品边界和版本更新入口，
以及原有重复/失效内容是否真正退出。文件数、有效正文与重复内容的变化分开说明，不追求固定删减比例。
文档收敛随领域整改进行，最后统一收口，不等全部代码结束才再开一个庞大的文档工程。

### 7.5 可自主追加的低成本改进

用户允许实施者酌情加入有实际收益且不拖慢主路径的改进。准入条件是：问题或维护成本明确、
能随当前领域批次完成、复用现有工具与依赖、没有新增长期维护设施和额外验证链。
符合条件的小项写入同一工作清单即可，无需逐项重复确认；代价不明的新框架、新功能或独立外部操作另列，不借优化扩张范围。

可优先考虑：

- 清理已经确认无消费者的开发脚本入口、过时配置项、重复常量和专属依赖，避免 fork 需要理解已退役的选择；
  动态消费者、旧数据兼容和发行输入一起核对，依赖变动同步锁文件，不按名字或年龄直接删除。
- 将日常开发、针对性检查和故障定位命令收敛到现有少量入口及准确示例；对反复出现且后果明确的漏包/漏发现问题，
  只在现有流程中补低成本检查，不新增平行运行器或每文件审查关卡。
- 顺手修正触及路径上的吞异常、含混状态和缺少行动建议的提示，复用既有结构化事件与必要耗时记录；
  不另建遥测系统，不记录原始账号数据或识别内容。

这些改进只在发现真实需要时落地，不为凑“额外优化”制造改动；第 7.2 至 7.4 节则是明确要求的正式交付，不作为可选小项省略。

## 9. 必要验证与效率约束

**全项目细查与大量重复运行是两回事。** 阅读当前业务并做价值判断是本轮主体，测试只回答具体风险问题。
开始每个批次时写明要改变什么、可能破坏什么、哪项既有检查足够，以及还缺哪一项证明；几句话即可。

| 改动类型 | 默认验证范围 |
| --- | --- |
| 文档、准确注释、已确定的机械引用 | 相关链接/引用、适用静态检查；不因此重跑业务全集 |
| 单领域规则、模块合并或测试精简 | 差异 Ruff、受影响入口/发现核对及少量关键行为专项；未改变的上层全集复用既有证据 |
| 账号、DAO、冻结、权限、取消、资源寿命、外部副作用 | 实际触及的失败/回滚/隔离/后验反例；关键 diff 独立复核；涉及多消费者时补相应集成检查 |
| 跨域公共机制和最终收口 | 公共消费者组合验证；集中一轮当前保留集合 core/full，必要启动与业务烟测；新增风险使原结果失效时才增补相关检查 |

统一使用 `tools/quality/run_tests.py` 与现有入口；Ruff 硬门禁沿用仓库契约。
一次集中运行失败后，先分类并修复真实原因，再复测受影响范围；不机械整仓重跑到绿，也不把重复失败当成允许带缺陷交付。
保留集合的 `full`、排除暂挂集合的补充运行、打包烟测和真实 Windows 验收分别命名。

执行纪律：

- 同一逻辑批次共用原件/哈希、差异、一个验证记录与受保护回退；已有 Git 基线及有效工件优先复用，
  数据操作才增加对应数据回退证据，不逐文件发布、回退、再发布。
- 不建设验证器自证链、通用诊断平台、重复镜像和多层证据包。脚手架阻塞时优先使用成熟入口取得同边界业务证据。
- 独立审查只追实际新风险；修完相关问题后定点复核，没有新反例就结束，不重复全文定稿。
- 同一种诊断连续两次没有新增定位信息时，更换更直接的方法或推进独立工作；真实启动、计算、保存及数据问题仍须解决。
- 性能测量与重型测试避免互相争抢资源；同输入、依赖和实际消费路径未变化时不重复测量、全量哈希或来源包装。
- 原始失败、命令和退出状态留在唯一记录。测试业务通过而包装失败要分别解释，绝不静默改写历史结果。
