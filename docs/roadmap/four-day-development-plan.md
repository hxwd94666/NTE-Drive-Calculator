### 0.2 必要验证与额外诊断的区别

- **取消验证设施的串行自证链。** 不新增“建设验证器 → 证明验证器 → 重建同内容镜像 →
  复制多份交接 → 审查每份证明”的阶段，不把测试脚手架本身扩展成新的开发项目。
- **先分清产品故障和验证工具故障。** 产品启动、计算、保存、账号/事务/取消等真实缺陷必须修复。
  若仅自建导入器、观察器或诊断包装阻碍验证，优先使用现有成熟质量入口或更直接的同边界业务检查；
  保留同等输入、来源、授权和数据保护，不改供应商代码、伪造模块/结果或绕过必要边界来求绿。
- **取消无新增风险的重复前后测试与审查。** 适用基线和已审决定直接复用，只补差异影响的行为；
  普通机械迁移不逐文件请求 Astra 审查，不为每个小修重复整仓检查。
- **按业务批次合并工件和回退核对。** 原件/hash、diff、验证记录和可运行回退仍保留，同一逻辑批次共用一套。
  不为每个文件或单行引用修复另建整套镜像与发布—回滚—重应用证明；涉及迁移、持久化、来源或外部副作用时，
  仍核对对应实际失败/回退边界。正式组件、来源及生产生命周期的必要身份检查保留。
- **取消重复证据包装。** 同一批次一份记录，引用原始命令、输入、字面输出和退出状态，不复制为多层报告。
  无变化不重复全量哈希、不重做有效隔离证明；回退证据不以循环润色为结束条件。
- **手柄驱动沿用用户已确认的安装与使用正常结果，不重复安装、设备、服务或游戏实测。**
  新改动若影响应用自身输入/取消流程，只验证该差异，不扩大为驱动重验。

同一诊断方法连续两次没有新增可定位证据时停止扩展该方法，保存终态并换直接定位路径，
或并行推进独立的原定开发；关键问题仍须解决，不以换目录/报告名称重新计为新问题。
不设到固定分钟就放弃关键问题的规则，不把必要门禁悄悄改成可选。

### 0.3 精简频率，保留关键门禁

| 改动 | 保留的必要动作 | 删除的额外阶段 |
| --- | --- | --- |
| 普通归包、合并、中文注释和已定引用迁移 | 同批迁完消费者、删旧入口与非关键测试；触及文件的 Ruff、必要导入和相关公共行为检查；复用适用基线 | 逐文件整套镜像/回退证明、每批机械 full、全仓重审、无变化重跑 |
| 账号、持久化、迁移、冻结输入、取消、资源寿命或外部副作用 | 直接对应的失败/隔离/回退/后验专项；Astra 只审实际高风险 diff | 无关整套检查、同证据多次审查、验证器自证平台 |
| 公共接口或跨领域生命周期改变 | 受影响消费者的集成检查；确有联动风险时提前 core | 按批次编号而非风险重复全量回归 |
| 原定开发闭环后的收口 | 当前冻结输入的一轮 core/full、全范围 Ruff、必要启动烟测与同条件性能核对 | 无变化重跑到绿、另建验收系统、为包装齐全拖延开发 |

- “一轮收口”是取消机械重复，不是限制必要修复：新增关键回归必须解决，修改后复测受影响范围；
  实际变动使全局证据失效时再做必要集成验证，不为缩短时间保留缺陷。
- 主动删测按架构方案第 4.7 节执行，删除过时、非关键、私有结构及重复保护，合并孤立夹具；
  账号隔离、计算/保存、事务、迁移、UID 唯一性、冻结/取消及资源释放等关键保护保留。
- 原暂挂旧失败沿用既有集合和授权，不自动追修或删掉求绿。正式 full 的失败保留真实分类；
  排除暂挂集合的运行只称补充验证，不替代正式通过，也不循环重跑同一已知失败。
- 输入、实现、配置和依赖身份适用时复用既有证据；实际变化补相关验证，不用历史绿色冒充当前源码。
  不因精简记录丢失原始失败、退出状态和未覆盖项。
- 不把无独立风险的报告排版、自证或证据复制设为下一独立领域开发的前置条件；
  公共依赖及真正影响正确性的门禁仍先闭合，避免只搬目录的半批。
- 性能测量与资源竞争大的测试串行；代理与低配真机、离屏与真实窗口分别记证据。

### 0.4 以闭环决定验收，不以固定时点决定交付

1. **接续当前未完动作。** 复用候选、消费者映射和剩余清单；工具先有界收尾，
   产品修复与验证设施状态分开，不将后者当作重构产出。
2. **完整剩余开发放在主路径。** 按独立领域并行归包、合并修复、迁完调用方、
   删除旧入口/低价值测试、补中文注释；同一领域一个写入 owner，共享接线由集成 owner 接管。
   机械工作不反复设计；新复杂切片由 Astra `xhigh` 实施，Sol 正常实施与在途收尾，共享接线仍由集成 owner 统一处理。
3. **同时收口原定预备能力与性能缺口。** 语言、OCR、瘦身输入、fork 路线和更新 skill 只补已登记缺口，
   不新增平台或教程框架；修已复现卡顿、重复初始化与资源堆积，前端不扩大整改。
4. **合并后集中必要验收与修复。** 留出实际收口余量，按第 0.3 节执行，不预设某小时强制冻结；
   不省集成、启动或关键业务检查，未通过的必要门禁继续修复。
5. **及时暴露时间风险，不改变完成定义。** 按具体剩余开发、必要验证、真实阻塞和最近可比耗时判断，
   不从“约 70%”线性推导时长。若窗口内完成有风险，立即列明缺口、依赖及直接解决路径，
   不等到临近截止才说明，不自动延过 10 月 15 日下午前或删掉原定开发；换模型不代替解决工具/I/O/共享接线瓶颈。
6. **完整完成才交付为完成。** 原范围、关键门禁和回退闭合才称重构完成；候选准备好、局部专项通过、
   验证工具恢复或“已改待验收”均非整体完成。之后再做真正伤害策略的独立任务。
   构建、安装、部署、真实游戏、提交和发布仍按原独立授权，未运行项不写通过。

进度报“实际完成 / 剩余原定开发 / 验收缺口 / 下一未完动作”，附关键路径与真实阻塞。
百分比必须说明分母与估算范围，区分候选、落地和验收；不把旧入口移除率、测试数或文件数当整体完成率，不为统计新建平台。
本次压缩的是重复验证阶段和组织成本；完整范围、必要验证与真实质量不随窗口缩短而降低。

## 2. 开工准备与基线

开工指令先明确允许修改的范围，以及专项测试、Ruff、`core/full`、隔离 Qt、临时数据库和性能测量的执行范围。

   说明每层改什么、为什么放这里、怎样显式接线；直接链接真实实现，不另建演示框架或保留第二套业务入口。
3. **可落地的修改配方。** 至少覆盖修改角色资料/默认权重、调整评分规则、接入一个页面、
   接界面语言补丁和更新游戏静态资料五类路径；每类列出实际文件入口、输入输出、正式 ID/快照边界、
   最小改动示例及已有关键验证。公式只经 ScoringEngine 权威入口，静态数据经候选与晋升链，语言仅改其负责的显示或识别资源域。
   新语种识别和新伤害求解仍只说明未来接入责任，不作为本轮实现。
4. **可复现而非仅有目录图。** 使用已有合成数据、临时数据库和关键行为用例，不复制真实账号库、
   截图/OCR 原文或本机路径。示例至少能完成一次输入、业务处理和结果检查，并演示一个失败/回退分支。
   核对新进程实际导入来源来自该检出，不因旧 editable 安装或其他工作区补读而伪通过；测试执行仍按用户授权范围。
5. **公开范围和验收状态清晰。** 主程序可开发的离线能力、需要执行物的集成能力和需维护者协作的组件分别说明；
   协议替身验证、真实组件和游戏验收分别记录。实际复现后的命令、输入、输出、退出状态和资源身份保留证据，
   未运行部分标待验收；让一位未参与重构的开发者可按步骤找到入口并完成约定修改，不只证明作者自己能运行。

路线设计与跨层/资源边界核对由 Astra `xhigh`，参考业务与修改配方的实际闭环由 Sol `max`，
已定入口的文字整理与引用迁移由 Sol `xhigh`；
最终用新审查上下文和真实复现证据核对。先完成前两项的关键热点，不为写教程重新改已清晰的业务。
路线交付从 `docs/README.md` 和根 README 的开发入口进入，依赖/启动命令只保留一处权威说明；
分层、公式、静态更新、语言与组件细则链接现有事实源，覆盖式更新引用，不额外堆积同义教程。
当前这段是交付要求，路线本体须按重构后的实际入口完成并复现后再标为交付。

大库存展示仅在前两项证明为热点时做精准减负，保留现有筛选、选中、键盘和主题语义，不成为独立 UI 改造项目。
失败提示优化等其他建议不作为本轮新增顺带任务；原计划已有的必要缺陷修复、
关键中文注释、公开开发路线及文档收口继续完成。
伤害求解、全量翻译、导航/视觉重设计、新插件平台和新下载分发系统保持原范围。
实际交付仍归 features、architecture 或 integrations 的对应责任章节，避免另建重复事实源。

## 5. Fast 怎样用

标准速度为默认：夜间运行、无需人工等待的实现、批量中文注释、测试执行和文档整理保持标准。
Fast 用于用户正在等待且确实卡住后续的模型推理，如 Day 1 框架定稿、跨层失败定位和 Day 4 阻塞修复。
普通本地测试、磁盘 IO 和编译的耗时不因提高模型速度而直接缩短，先区分等待发生在哪里。

按核对时官方规则，同模型 Fast 的订阅内用量为 Standard 的 **2.5 倍**；购买积分的计费倍数为 **2 倍**，
二者分别计算。官方没有据此承诺本项目端到端快 2.5 倍。四日开工时再次核对选项和倍率。
[Fast 适用范围](https://learn.chatgpt.com/docs/agent-configuration/speed)、
[订阅用量与购买积分倍率](https://learn.chatgpt.com/docs/pricing)

建议先把 Fast 限于约 10%～20% 的标准等效模型工作量，而非按任务条数算。
若同模型、同思考、相同上下文与工作量都不变，20% 工作使用 Fast 的理论用量系数为
`0.8 + 0.2 × 2.5 = 1.3`；这是预算示例，不含重试、缓存及模型混用变化。
Fast 超额消耗包含在上述日预算/储备中，不额外凭空增加额度。验证瓶颈已解除后切回标准。
Ultrafast 不纳入默认计划，避免将未确认的访问条件或高倍率作为完成四日工作的前提。

6. 核对旧 owner 的实际释放，以及迁移后关键测试的默认发现、模块身份和子进程导入；
   保留集合真正进入长期门禁后才锁定推广模板。

**日末出口：** 当前和目标结构及领域目录可对应；首个完整链路可验证；首批旧入口、非关键测试和孤立夹具实际删除；暂挂失败与新增回归分开；
低配/代理样本及指标目标已冻结；Day 2 消费者清单明确。首切片未通过，Day 2 先修闭环，不盲目推广。
框架讨论以能否落地现有功能为停止标准，不花整天争论术语和目录名。

全景输出使用[架构方案的覆盖状态与参考切片](architecture-renewal.md#44-用一个完整业务校验框架而非只展示新目录)：
完整追踪每个领域的主要链路，高风险分支逐项展开；其余细节仍待核实时直接标注，不用文件扫描代替人工分析。

发行体积在 Day 1 同步登记构建参数和已有流程：Astra `xhigh` 审依赖/动态加载/候选清单，

OCR 可拆卸预备在 Day 2 随依赖与打包输入收敛落实：Astra `xhigh` 审选择/回退、原生加载与生命周期边界，

[架构方案第 5.6 节](architecture-renewal.md#56-ocr-后端可拆卸与单库实验预备)执行，Day 3/4 在获准条件下验收。

性能测量单独串行，避开测试并发造成的资源干扰。

## 7. 验收目标与判定

### 7.1 结构和代码的硬出口

- 每个新增/补足的框架责任有实际消费者；公共机制至少用两类不同现有业务验证适用边界。
- 本轮迁移的正式链路只剩一个有效入口；旧修复链和无意义桥接的删除有消费者核对。
- 合并以完整规则和失败行为为单位；遵守分层与 800 行门禁，不做万能类；删除低价值测试、保留关键门禁。
- 各层业务目录、共享 owner 与窄公共入口明确；静态/动态/工具/打包引用及资源定位迁完，旧平铺入口与过渡壳删除，导入无新增副作用或循环。
- 每个已审领域的非关键测试与孤立夹具已实际删除，重复关键保护合并；保留的少量关键点明确，规模与耗时变化可核对。
  不设等量补测、逐用例审批或覆盖率指标，不用移组/改名/跳过替代删除；删除结论与缺陷修复分开。
- 全项目关键中文说明有领域覆盖清单并完成原定保留模块的关键说明；保留模块不被遗漏，未补齐项不自动顺延为完成。
- 默认中文、评分、预览保存与数据兼容保持；伤害求解未启用；界面可见改动逐项对应原问题。
- 本轮交付链路的获准关键验证及 Ruff 硬门禁通过；未运行、暂挂失败、外部缺口单独说明。
  暂挂失败影响关键判断的链路保持待验收，整体 full 仍有失败时不写“全部通过”。
- 默认质量入口完整且不重复地发现保留集合；嵌套模块、串并行导入、`core` 选择与失败退出状态正确。
  账号隔离、旧数据升级、事务、UID 唯一性、取消/迟到写入及外部副作用边界持续受必要门禁保护，而非只运行一次专项。

### 7.2 低配体验的验收卡

Day 1 为每个场景填写机器/代理、输入规模、基线、目标、波动范围与检查命令，之后保持同条件。
以下是**待基线确认的候选工程预算**，不是已测结果，也不是适用于所有硬件的产品承诺：

| 项目 | 初始目标/判定方式 |
| --- | --- |
| 点击、开始任务、取消的界面反馈 | 热态反馈 P95 以 100 ms 为候选目标；完成耗时另计，反馈不伪装完成 |
| 主线程卡顿 | 目标场景中自有代码单次阻塞以 200 ms 为候选上限，关注最大值与超预算次数，而非只看平均值 |
| 窗口稳定性 | 固定回归序列无可复现的应用未响应、异常退出或死锁；出现任何一次均定位归因 |
| 总任务时间 | 可更快或保持冻结误差范围；为响应性采用的额外调度成本明确报告，明显退化须处理 |
| 取消与退出 | 反馈与实际收尾分别测，每类 owner 有预先声明的有限收尾预算；无遗留输入或失控后台任务 |
| 内存/线程/句柄 | 预热后多轮相同操作不持续累积；上限与基线差异有解释，缓存容量可核对 |
| owner 生命周期 | 无任务时反复代次切换，仅保留当前活动 owner；有任务时旧 owner 仅留到读/写物理终态，随后回到上限 |
| 正确性 | 同冻结输入的业务事实保持一致，未知和失败仍按正式语义表达 |

冷启动、正式进程等待、系统资源争用分别设场景预算，不拿热态指标套所有步骤。
若候选数值不适配 Day 1 机器，实施前记录理由并冻结可检验目标；事后遗漏项视为未验收，而非悄悄调低标准。
没有低配真机时，只报告代理验证与已消除的原因，不宣称低配实机体验已通过。
真实滚动和绘制在窗口里核对，离屏测试不替代视觉流畅度。

### 7.3 语言预备、占位与交付门禁

| 检查 | 通过条件 |
| --- | --- |
| 默认中文 | 未选择补丁时，示范切片的动作、含义和默认行为与基线一致 |
| 缺项与命名参数 | 缺 key 回退中文；正常参数正确替换；多余/缺失参数与不支持格式被明确识别 |
| 坏包与恢复 | 重复 key、格式/兼容身份错误、超限和路径越界不激活；失败保留有效目录；恢复默认不动账号数据 |
| 实际接入 | 公共提示和一个真实设置切片消费同一解析入口，伪语言长文本仍可操作，无全界面重做 |
| 版本更新 skill | 可从提供的解包定位唯一 Content，核对已登记来源差异；静态/素材/逐角色功能接入与晋升责任可追踪，引用和脚本验证通过；随全域重构维护接入索引，不把只读审计当完整更新 |
| 功能内语言预备 | 鉴定与扫描的输入配置独立于界面语言；模型/字典、别名到正式 ID、布局/模板、任务冻结与增量基线责任可追踪，默认中文保持；未验证语种不标支持 |
| 可选识别资源 | 额外语种模型不默认进入 EXE、不全量预热；沿用资源身份与安装验证，本轮无自动下载或新语种能力交付 |
| 伤害占位 | 备忘与未就绪语义一致；既有评分/边际功能保留；没有新增搜索器、伪结果、空注册器或数据库占位列 |
| fork 与回退 | 最小公开依赖/合成夹具的参考操作可复现；diff 和本批回退可核对；回退不覆盖其他未提交工作 |

实施后的每项结论附输入、确切命令/操作、输出、退出状态和未覆盖范围。按实际获准范围复用现有入口，例如：

```powershell
uv run python tools/quality/run_tests.py core
uv run python tools/quality/run_tests.py full
uv run ruff check main.py src tools tests --select E9,F63,F7,F821,F401
```

依赖先按锁文件与公开开发说明准备；专项选择对应已核对的测试模块，Qt/临时库使用隔离配置。
以上命令与性能、真实窗口、组件和发布验证分别记证据，任何一个绿色结果都不替代其他门禁。

### 7.4 发行体积验收

- 以[架构方案第 5.5 节](architecture-renewal.md#55-最终-exe-与发行包瘦身)为唯一措施事实源，四日计划只维护排期与验收。
- 同版本/依赖/dataset/组件/模式记录主 EXE、安装包、完整发行目录与安装后占用；明确净减少和保留成本。
- 实际依赖、必要 OCR/计算/展示能力、图片路径与许可齐备，低配启动、内存和临时解包成本无显著回退。
- 精确删减可解释且可回退，升级/安装与必要打包烟测通过；没获准执行的项目保持待测，不写已瘦身。

### 7.5 OCR 可拆卸与单库实验验收

- 以[架构方案第 5.6 节](architecture-renewal.md#56-ocr-后端可拆卸与单库实验预备)为唯一责任事实源；维护者从一处选择后端，无须逐个消费者修 import。
- 未选库真正缺失时应用、同步、评分/保存照常工作；所有 OCR 消费者延迟加载同一选择，单后端实验没有隐藏回退。
- 验证仅 OpenVINO、仅 ONNX CPU、ONNX DirectML、选中后端故障及全部 OCR 库缺失；前端提示与失败状态准确。
- 依赖分组、模型来源、DLL/hidden import、裁剪、许可与打包校验随选择一致；单库独立环境及恢复步骤简短可复现。
- 预备完成不等于已决定删库；CPU/GPU 兼容、识别结果、性能与体积在真实实验后比较，未执行项不标通过。

## 8. 每批与每晚怎样衔接

每批交接固定六项：当前 ref/差异；已完成领域/消费者；删测决定及保留集合的命令/结果；性能与资源变化；风险/回退点；下一步。
使用本机记录保存原始输出，公共文档只维护稳定约定与未完成目标，不附账号数据或私有地址。

每晚结束时形成一张简短交接卡，不新造任务管理系统：

```text
已验收：业务范围、源文件身份、消费者、确切命令及终态。
待验收：已改但未验证的内容；已知失败与真实前置条件。
待审查：Astra 尚未复核的设计或高风险 diff。
性能：同条件样本、退化与未覆盖的真机场景。
剩余额度：当前窗口及可用重置状态；下一批预算与收尾储备。
下一步：第一个未完成动作、对象、完成条件；恢复时先核对文件变化。
```

本轮已进入实施，交接只接续真实断点，不重新等待方案定稿；侧聊计划更新由用户通知主线程生效，文档本身不派发代码任务或扩大执行授权。

主线程沿用现有 Sol Ultra 编排及第 3 节职责，不为重复调查或证据包装增加 agent。
并行按独立文件/领域分工，一个负责人接管公共框架和集成，审查者优先只读；共享上下文、DAO、协议、
组合根与锁文件不由多个写入者同时改。并行测试的资源占用须与性能实验隔离。

夜间以已确认的边界继续下一个可闭环批次；不反复启动全景调查、不自行新增产品功能。
出现数据风险、未知外部结果、连续两次无新证据的同类失败，先保留现场和最后有效边界，改做独立可验证工作或交接。
停机前不启动预计来不及验证的跨功能迁移；额度耗尽也保留准确 checkpoint，后续从真实文件和证据继续。

## 9. 本轮计划的维护方式

实际剩余窗口、开发优先级和删去的验证阶段，以第 0 节为唯一执行口径。
主线程 Sol Ultra 编排与第 3 节新分工为准；本次侧聊只改计划，不直接切换模型/加速配置或现有 owner，由主线程读取后落实。
剩余工作沿[架构方案](architecture-renewal.md)与现有清单接续，不重新定稿、重做已闭环批次或扩大范围。
用户通知主线程读取后生效，工具先有界收尾；侧聊不改源码、checkpoint、分支或现有 owner。
实际交付事实进入架构/功能文档，风险及时报告；本文不累积逐夜流水账。
