# 免安装发行与平台覆盖更新开发方案

状态：稳定数据根、清单更新、ZIP 构建及已审旧发行的首次接管已实现并通过独立审查；最终两类候选包已生成，本机升级、覆盖、旧目录接管及外部数据保留检查通过。真实窗口交互、正常退出及平台动态验收仍未完成，不作为正式发行已通过。目标是供游戏工具平台收录的解压即用版本，同时支持用户手动解压使用。平台更新以原目录覆盖为首要适配场景，正式程序路径保持稳定；自带更新助手不是平台收录的前置条件。

本方案只规划免安装交付，不改变计算、账号、工作模式或游戏组件权限。公共边界沿用 [AGENTS](../../AGENTS.md)、[外部集成](../integrations.md)和[游戏组件契约](../reference/game-component-bundle.md)。平台实际更新、删除及退出协议尚待对接确认，以下兼容条件是交付要求，不是对平台现有能力的断言。

## 1. 交付目标与非目标

- 与安装版共用一份目录式程序构建，增加独立 ZIP 包及发行清单，不维护第二套业务实现。
- 首次解压后从固定入口启动；后续由平台在同一目录覆盖发行文件，账号、配装、配置和语言补丁保留。
- 保持主 EXE、组件工作区及已登记部署路径稳定，不要求每次升级迁往新目录或重做注册。
- 升级前后分别验证程序整包与数据结构；更新中断、组件占用、迁移失败有明确恢复路径。
- 首版不做差分下载、多版本启动器、自研平台、全面权限改造或重复的驱动安装验证。免安装仅指 NDC 本体，不承诺全部系统依赖免安装或启动免提权。

## 2. 现有基础与明确缺口

| 当前入口 | 已有基础 | 本次工作 |
| --- | --- | --- |
| `build_exe.py` | 默认目录式构建，包含运行库、静态资料、独立组件及清单 | 复用同一产物生成干净 ZIP，沿用组件、OCR 和许可校验 |
| `build_installer.py` | 安装器额外复制配置、处理旧文件和保留旧静态基线 | 审查哪些步骤仍被运行链依赖，必要步骤抽为共享入口，不把安装器流程直接照搬到启动 |
| `src/integrations/application_runtime_paths.py` | 区分发行资源和运行数据；目前优先程序目录，失败后尝试 LocalAppData | 增加明确发行模式与稳定数据根，避免权限变化导致数据位置悄然变化 |
| `src/app/context.py` | 路径由组合根注入 | 复用，不让业务自行拼接便携路径 |
| `src/storage/sqlite/user_data_base.py` | 顺序事务迁移，拒绝更高版本用户库，部分迁移有专项备份 | 补齐升级前一致性恢复点，保留已有版本检查和事务边界 |
| `src/app/shared_data_seed.py` | 当前会复制随包共享库到运行数据域 | 核清默认资源和可变兼容数据的所有权，再确定首次初始化、版本更新策略，避免覆盖需保留的状态 |
| `src/features/settings/updates/`、`src/integrations/updates/mirror.py` | 更新检查、下载、取消及安装器派发 | 区分安装版、平台托管便携版和手动便携版，不让便携版误启动安装器 |

上表是源码核对结果，不代表 ZIP 或真实平台验收已完成。旧静态基线、核心配置、环境依赖和权限必须按真实消费链检查，不能以“目录构建成功”代替安装器独立性验收。

## 3. 发行目录与数据归属

建议新便携版目录：

```text
NTE_Drive_Calc/
  NTE_Drive_Calc.exe       固定启动入口
  _internal/              完整发行运行时、组件、静态资料
  distribution.json       发行类型、包身份及兼容声明
  release-files.json      发行文件相对路径、大小及 SHA-256
  userdata/               首次运行生成，发行 ZIP 中没有此目录
    accounts/
    config/
    data/
    maintenance/          已接受发行清单、升级恢复点与中断记录
```

具体文件名在实施时与现有构建入口统一；这些是目标结构，不是当前既有格式。

### 3.1 数据路径规则

1. 便携版默认固定使用根目录下 `userdata`；读取或写入失败时说明位置与原因，不自动选择另一数据根创建空账号。
2. 不改变安装版已有路径策略；已有用户转便携版时，通过显式迁入流程处理旧根目录数据或 LocalAppData 数据。确认来源、完成一致性复制与校验后再切换，保留原始数据；不合并身份冲突的账号。
3. 平台保留目录能力决定数据策略：若保留 `userdata`，使用默认布局；若平台更新会清空整个应用目录，必须使用平台承诺保留的外部数据根，并在首次启动明确该位置。它属于平台托管免安装，而非“整个目录拷走即带走数据”。
4. 外部数据根是显式、持久的配置，不按当前工作目录、临时权限或随意同名目录推断。已有数据根记录缺失或冲突时先恢复选择，不静默初始化替代账号。
5. 若平台既清空目录又不提供数据保留位置，则不满足有状态工具更新要求；先解决平台适配，不能宣称更新保数据。
6. 运行数据与只读发行静态资料严格分离。日志、扫描临时图片、账号库、配置及更新恢复点都不进入发行包。

### 3.2 固定位置与机器绑定

覆盖更新不改变主程序路径，也不因更新自动重写注册表、重新登记组件工作区或清空游戏侧部署记录。真实注册表键及工作区消费者在实施时定向核对，不虚构统一注册机制。

用户主动迁移目录或换电脑另行处理：账号数据可迁移，机器路径、驱动就绪和部署记录需重新校验，原记录不能直接提升为新机器上的业务成功。

## 4. 平台覆盖更新契约

### KoKodayo 已确认的收录边界

目标平台为 [KoKodayo](https://www.kokodayo.me/)。2026-10-15 核对其[开发者页面](https://www.kokodayo.me/developer/)及[公开本地应用填写示例](https://www.kokodayo.me/developer/examples/native-application-submission-example.md)：ZIP 顶层要求单一目录，启动入口相对压缩包根填写，包体上限标为 1 GB，版本使用三段数字。

因此平台包采用固定 `NTE_Drive_Calc/` 外层目录，入口为 `./NTE_Drive_Calc/NTE_Drive_Calc.exe`；发行清单仍相对该应用目录。外层名称不带版本号，不将新版展开到新版本目录。体积门禁在单位未进一步确认前取保守的 1,000,000,000 字节；不为通过门禁删除必需功能。测试版标签不悄悄改写成正式三段版本；提交平台前需明确正式版本。页面与示例对同版本重交的表述不一致，按版本严格递增准备，正式发布动作仍由维护者执行。

公开客户端 0.1.7 的静态调用链进一步显示：本地安装任务在解包前解析应用目标目录，存在时递归删除，再重建目录并解压；这不是承诺保留包外文件的逐文件覆盖。该结论来自官方客户端执行文件的路径构造、调用顺序和 Windows 删除 API，不是仅凭提示字符串。客户端来自[官方更新元数据](https://kokodayo.oss-cn-shanghai.aliyuncs.com/kokodayo/KoKodayo-setup/latest.json)，本次仅隔离解包与静态分析，未安装或运行平台及其他工具。

因此 `kokodayo` 构建配置要求 `platform` 更新通道、`external` 数据策略和稳定 `data_root_key`。账号、配置、恢复点及组件工作区放在已明确选择的应用目录外数据根；程序入口仍固定在同一安装位置。不得把目录内 `userdata` 方案作为当前 KoKodayo 包的保数据方案。独立手动免安装包仍支持目录内数据，不把平台限制扩散到全部发行方式。

客户端包含运行中应用更新拦截及树状终止命令，但尚未闭合对 NDC 提权进程、自有子进程和退出落盘的实际覆盖；安装失败是否恢复旧包也尚待平台实测。上述静态结论按 0.1.7 留档，不作为未来平台版本或完整接入验收的保证。开发者入口有访问门禁，本次只使用公开资源，不登录、不提交、不上传。

### 4.1 平台对接先确认的五件事

| 问题 | 最低要求或处理方式 |
| --- | --- |
| 解压根层级 | 确认 ZIP 是直接展开到应用根，还是平台创建外层目录；避免升级后多嵌套一层 |
| 覆盖还是先删除 | 明确 `userdata` 和恢复点的保留规则；清空型平台使用显式外部数据根 |
| 更新前如何退出 | 等待主程序及相关自有组件停止，更新期间禁止新启动；仅关闭窗口不算进程退场 |
| 是否删除旧包遗留文件 | 支持时按发行清单清理；不支持时由应用维护入口执行受限退役清理 |
| 校验与失败恢复 | 明确平台对包身份、完整下载、失败回滚和旧包留存的保障，不把“解压完成”当成功 |

平台托管标识必须是明确配置，缺失时按手动便携版处理，不猜测平台进程或目录名。平台更新期间 NDC 不并行启动自己的更新动作。

### 4.2 支持直接覆盖，但不承诺任意覆盖都可靠

推荐平台时序：停止应用与相关子进程 → 下载并校验完整 ZIP → 原目录覆盖发行文件 → 清理明确退役文件 → 启动并验收。

- ZIP 不携带用户数据，即使平台使用普通覆盖解压，也没有同名空库或默认配置覆盖用户事实。
- 程序退出前停止任务、撤销外部副作用、关闭数据库及 worker。平台在应用运行中直接替换属于不支持的更新方式，须有明确提示和接入约束。
- 主 EXE 和 `_internal` 按同一发行身份校验；缺件、损坏或混版时停在修复提示，不先迁移数据或执行组件部署。
- 启动自检置于可行的最早边界；若入口 EXE、Python 或 Qt 运行时已经损坏，应用内检查也可能没有执行机会，因此恢复须依靠平台重解压完整包或外部更新入口，不能只靠 GUI 自救。
- 普通覆盖解压是多文件操作，不等于原子切换。若平台没有程序回滚保障，保留旧包下载或离线恢复方式；首版不虚称自动还原旧程序。
- 包内哈希用于文件一致性；发行真实性由可信平台渠道、可信清单或签名验证支撑。与文件一起被任意替换的哈希清单不是独立信任根。

### 4.3 旧文件清理和首次接管

最近一次成功启动的发行清单保存在不被覆盖的维护目录。新包清单与旧清单求差，只处理本应用拥有、已明确退役的精确路径。

- 限定在发行文件域，不触碰 `userdata`、外部数据根、游戏目录、注册表或用户自行放置的未知文件。
- 校验相对路径、大小写冲突、目录边界、链接与重解析点；不按模糊扩展名或递归扫描结果删文件。
- 本地改动、归属不明或文件占用时保留并提示；若存在运行时加载风险，则阻止启动并要求修复，不能带着混版运行。
- 首次从旧安装目录或无清单旧 ZIP 接管时，使用经过审查的确切旧发行路径清单；不推测整个目录都是发行文件。
- 退役 DLL 可能在 Python 维护逻辑执行前被加载。因此影响引导链的旧文件必须在启动前由平台或窄更新入口清理；普通应用启动清理仅覆盖不影响引导链的文件。平台无此能力时，版本接入需提供前置修复步骤。

新包包含版本、构建身份、架构、发行类型、文件清单及相关数据/组件兼容信息；同版本重打包也使用不同构建身份。清单元数据不取代现有静态、组件协议与哈希门禁。

## 5. 数据升级与恢复

### 5.1 两条升级链分开

- 程序链：EXE、运行库、静态 dataset、图鉴和随包组件整体变更，由平台或更新入口负责。
- 数据链：账号库、共享兼容库、账号索引及配置按各自版本升级，由现有 DAO/配置 owner 负责。

先验证完整程序包，再准备数据恢复点，最后迁移。账号库继续顺序追加迁移，不重写历史 SQL；静态资料按当前整包读取，不覆盖账号数据库。不同账号迁移状态分别记录，不把当前账号成功写成全部账号已升级。

### 5.2 恢复点与并发

1. 引入数据根级跨进程互斥，协调接入同协议的新旧版、维护和迁移；未接入协议的旧程序须在迁入前明确退出。平台更新另需进程退出约束，数据锁本身不阻止第三方覆盖程序文件。
2. 只有数据结构或配置确需变更时创建对应恢复点，不在每次启动复制全量战报。
3. SQLite 使用一致性备份 API；配置和索引在写入已停止时形成同一恢复记录。备份写完、校验并登记成功后才开始迁移，禁止直接复制活动 WAL/SHM 充当备份。
4. 空间不足、备份失败或数据身份冲突时不迁移。各迁移事务失败保留可恢复状态；多步升级的整体恢复依靠升级前恢复点，不假设所有已提交步骤会自动回滚。
5. 恢复点记录版本、账号身份、schema 和对应程序构建，不包含敏感数据到公开日志。恢复点在新版本验收前保留，后续按明确保留策略有界清理，不无限膨胀磁盘。
6. 保留拒绝旧程序打开新 schema 的门禁；审查本次涉及的共享库和配置是否有等价保护。降级恢复需匹配旧程序与旧数据，不能只替换 EXE。
7. 新版已经产生新数据时，不自动用旧备份覆盖；先保留新版数据副本并说明恢复影响。原始战报、装备快照及历史评分不因程序升级而被重算覆盖。

首版复用现有账号导入导出、SQLite 备份和事务能力，只补确有缺口的升级编排。初始化共享库的覆盖行为是实施前必须解决的数据归属项，不以包类型变更掩盖它。

## 6. 游戏组件和系统依赖

- 随包采集/分析组件随程序发行清单更新；已部署到游戏目录的组件仍走现有正式部署契约，二者成功状态分别判断。
- 更新应用不自动改变工作模式、启用自动同步、触发游戏操作、重新注册或清理外部工作区。
- 文件被游戏加载时沿用等待退出后的升级安排，不强关游戏，不热替换正在使用的 DLL。
- 明确免安装包仍可能需要已有系统运行库、抓包或输入依赖。复用检测和用户引导，缺少某项时按实际能力表达，不误报整个程序损坏。
- 当前管理员启动要求先保持语义一致；平台须确认其启动链是否支持。降低提权范围不是本次交付的附带重构。
- 驱动既有安装验证直接复用，本次不重测安装；新增验证仅覆盖便携包缺依赖提示与路径稳定性。

## 7. 构建与更新界面接入

### 7.1 构建

从同一份已核对 onedir 产物分别制作安装器和 ZIP。增加窄的便携包入口，复用组件、OCR、资源和许可校验；把确需共用的校验从安装器入口抽出，不复制两套实现。

构建在隔离暂存目录只收集发行白名单，拒绝账号、运行日志、截图、私有源码、PDB、缓存和本机配置。ZIP 校验成员重复、路径穿越、链接、展开大小和清单一致性；产出包大小、展开大小、构建身份和摘要。不为了缩包删减必需组件，不将 onefile 作为便携化前提。

### 7.2 更新入口

| 发行方式 | 用户操作 |
| --- | --- |
| 安装版 | 保持现有安装器更新流程 |
| 平台托管便携版 | 展示当前版本及平台更新提示；只有平台提供正式跳转协议时才跳转，不启动竞争更新 |
| 手动便携版 | 提供对应 ZIP 下载说明，退出后原目录更新；不把安装器地址当 ZIP |

平台名称、跳转协议和托管能力由已确认的适配信息提供，不散落硬编码。现有 Mirror 若只提供安装器资源，则便携版使用明确的便携下载入口，待服务端有对应产物契约后再接入。

自带独立更新助手为后续可选增强：仅负责退出等待、暂存校验、发行文件切换及恢复，不替代数据库迁移，也不成为平台覆盖解压的强制依赖。

## 8. 实施顺序与职责

沿用用户指定的 Astra high，按本方案开始实施。每个切片单写入 owner，实施与独立审查分开，不并行修改同一领域。

| 批次 | 交付 | 完成条件 |
| --- | --- | --- |
| P0 平台契约 | 确认解压层级、保留目录、退出、旧文件清理、恢复及提权能力 | 明确支持的更新方式；未知项不写成已适配 |
| P1 路径与数据 | 发行标识、稳定数据根、已有用户迁入、互斥和必要升级恢复 | 保留用户事实，失败不切到空数据根；安装版不回归 |
| P2 覆盖更新边界 | 清单生成/核对、退役清理、引导链前置条件、更新界面分流 | 原目录更新保持身份，混版不进入业务，不误派发安装器 |
| P3 ZIP 交付 | 复用构建输出、干净压缩包与发行元数据 | 无私有运行数据，脱离安装器完成启动和必要功能 |
| P4 集中验收 | 真实 Windows 与平台更新试用 | 下表必需项通过；平台条件缺失明确单列 |

优先完成平台保数据契约和原目录路径适配，不先建设通用更新框架。共享库归属、依赖安装器的初始化步骤、引导链旧 DLL 清理和平台删除策略是关键路径。

## 9. 必要验收与交付门槛

| 场景 | 必须观察的结果 |
| --- | --- |
| 全新解压 | ZIP 无用户数据；固定入口启动，发行组件与静态资料身份正确 |
| 旧版原目录覆盖 | 主 EXE 路径不变；账号、配装、语言补丁和设置保留；合法发行文件更新、明确旧文件退役 |
| 平台保留/清空模式 | 分别验证所声明支持的数据策略；清空模式有外部数据根，或明确不支持该接入方式 |
| schema 升级 | 当前与一个确有迁移的旧版输入均覆盖；备份有效，迁移后计算、保存和战报读取正常 |
| 中断和故障 | 截断包、混版、占用、磁盘不足、迁移失败能阻止危险继续；平台重解压或既定恢复路径有效 |
| 降级与多进程 | 旧程序拒绝不兼容数据；同数据根第二写入进程被阻止；恢复不静默丢弃新版数据 |
| 路径与环境 | 中文/空格路径、不同工作目录、不可写目录提示正确；外部部署路径及登记不随应用更新漂移 |
| 渠道与隔离 | 平台版不拉起安装器；安装版更新行为保留；切换账号不串数据 |
| 发行检查 | 无账号/日志/截图/凭据/私有源码；许可、清单、ZIP 内容及所需组件完整 |

普通改动只运行受影响的路径、迁移、打包和更新专项；按最终改动风险决定集中 core/full 范围，不重复镜像、证据复制或验证器自证。真实包必须在 Windows 解压与覆盖更新一次；平台实际行为须在对应平台确认，本地模拟不等于平台收录验收。

完成后将已交付行为分别整合进 features、architecture、integrations 和 Windows 验收说明，本文件只保留未完成项。首版通过前保持“待实施/待验收”状态，不宣称任意平台覆盖更新均已兼容。
