# 全项目架构重构、框架补足与语言扩展预备

方案已定稿；按用户明确指令恢复 Day 1 实施，允许专项、Ruff 与 core/full。现有未提交改动保留，
已取得的局部证据及其范围见[首批架构验收](../validation/architecture-renewal-day1.md)。
全域语义审查、模型复审、第二类消费者和低配真实验收仍是完成门槛，参考切片专项不代表全仓完成。
以已经成熟的功能与用户体验为基线，反推并补足适合本项目的应用框架，系统重组臃肿实现、合并散乱补丁，
使低配置电脑运行更流畅稳定，也让 fork 开发者能通过中文关键注释和清晰骨架学习、修改项目。
开发边界见 [AGENTS.md](../../AGENTS.md) 与[项目用途声明](../../RESPONSIBLE_USE.md)。
四日工作顺序、模型分工与阶段验收集中在[四日开发与验收计划](four-day-development-plan.md)，本文拥有架构目标与实现边界。

## 1. 核心决定：基于成熟功能补足框架，而非只做局部修补

功能逐步成熟的过程中，临时接线、修复分支和历史兼容不断累积；现在应从完整业务流程反推框架责任，
将实际共性组织为统一实现。账号上下文、不可变库存、冻结预览、独立分析组件、DAO 事务和公共展示是基础，
但保留基础不等于保留每一处旧结构。实现可以系统重组，已有功能语义、数据兼容与打磨过的交互保持。

本方案明确要**加框架、补框架、收敛框架**。衡量标准是：框架是否承接真实功能、统一规则和生命周期、
减少重复实现与维护跳转、改善低配资源使用，并形成 fork 开发者可模仿的骨架与模板。
DI、任务调度、事件或其他抽象不按名称排除；选用前说明实际消费者、现有缺口、迁移方案及可验证收益。
只有多一层包装、保留全部补丁入口却没有统一行为的“框架化”，不算完成。
功能成熟是保持现有产品语义的基线，并不将路线图中尚未验证的边界故障认定为已经通过验收。

| 工作方向 | 本次目标 | 控制边界 |
| --- | --- | --- |
| 应用框架 | 全项目审查，补足组合、Feature 接线、任务、冻结上下文、规则与错误投影、公共展示及语言边界 | 继承和合并现有设施，不平行建设另一套体系；小功能按实际责任接入 |
| 功能目录模块化 | 各层按业务领域组织子包，相关功能有明确目录与公共入口，保留测试按领域归组 | 清理 `services/` 等平铺目录；保持分层，不把 SQL、UI、协议揉进一个功能万能模块 |
| 完整业务实现 | 主动合并同流程的零散修复与重复分支，迁移消费者并删除旧入口 | 不按 `legacy` 等字样删除有效历史迁移，不合并成万能大文件 |
| 测试主动瘦身 | 全仓审查同步删除非关键、过时及实现细节测试，合并重复业务用例和夹具 | 只保留少量有效的核心业务与关键不变量验证；不等量补测，不把删除变成慢测或跳过 |
| 中文关键注释 | 覆盖全项目自有代码，包括保留的已有代码，形成可学习的实现说明 | 技术标识保留原名，不逐行复述语法、不保留失效说明 |
| 低配流畅与稳定 | 启动、切页、滚动、筛选、读写、计算等待和取消保持响应，资源有界 | 不以开发机平均耗时或算法吞吐替代交互与长尾验收 |
| 大众适配 | 对现有界面做有依据的交互、文案、可读性和布局修复 | 保持菜单、信息架构、操作习惯、主题和视觉风格，不借重构重画前端 |
| fork 开发 | 公开可复现的小闭环、明确扩展路线和真实业务模板 | 私有组件保持独立，不引入第二套 Python 生产求解器 |
| 发行体积 | 在保留成熟功能与低配体验的前提下，最终 EXE 与完整发行包尽量小 | 依赖闭包、运行库、静态资料与素材审查；不能仅把内容移出 EXE 或漏装必要组件 |
| 语言与未来目标 | 语言目录可用切片；[伤害分配](damage-allocation.md)只保留研究及接入边界 | 不要求本轮全量翻译、热切换或新伤害算法 |

架构设计看全局，实施按业务批次闭环；不是只修几个耦合点，也不是同一批改完所有代码。
**领域归包与主动删测是每批必做项，不是收尾建议。** 已满足目标的实现可保留，仍须核对目录归属、消费者、
关键说明及对应测试价值；不为统一外形重写成熟功能，也不预设一晚完成全项目。

实施优先级固定为：**数据与业务正确性 → 流畅性和稳定性 → 框架与代码收敛 → fork 可读性 → 有依据的前端小修**。
中文关键说明随上述每批同步完成，语言预备占用有界批次，伤害求解保留研究备忘。
这不是五个彼此割裂的工程：一次完整流程重组应同时减少隐式依赖、合并补丁、明确资源归属并补齐解释。

“有模板参照的重写”指**所有自有模块接受同一套职责、接口、生命周期、失败行为和中文说明标准的审查**，
有问题的实现按完整流程重组；不是为了统一外形机械重写已经清晰稳定的函数。
对保留模块同样核对调用方与关键说明，留下保留理由；对重组模块迁完实际消费者后删除旧实现。
最终得到的是基于现有功能的统一开发骨架，而非一组漂亮但尚无业务接入的新目录。

## 3. 给 fork 的第一项交付：最小开发闭环

公开源码可读，不等于新开发者已经能复现一个修改。应先让贡献者在不接触真实账号、不启动游戏组件、
不依赖维护者本机目录的情况下，完成“安装依赖 → 运行指定隔离用例 → 修改 → 验证”。
这是一项待验收目标，不宣称当前公开 checkout 已经可完整启动或打包。

### 3.1 把环境要求拆清楚

在[开发文档入口](../README.md)维护一份简短、可复现的开发说明，不再新增平行安装指南：

- Windows 10/11、Python 3.11 与锁文件是桌面基线；依赖以 `pyproject.toml`、`uv.lock` 为准。
  当前多数桌面依赖带 Windows 条件，纯逻辑可单独验证不等于支持其他桌面平台。
- 当前 README 要求先确认协作基线，且安装示例同时包含 dev/build 组。应把可复现的公开 ref、资源前置与协作要求写清，
  分开最小开发和发行构建依赖；私有协作确认不应成为理解一个公开隔离用例的隐式前置。
- 分清纯规则/DAO、隔离 Qt 页面、正式分析组件、真实采集/游戏操作、发行构建各自所需输入。
  不让修改普通页面也必须准备游戏、DLL 或全部打包环境。
- 列出可公开获取的必需资源、版本/哈希清单和缺失时的具体表现；受独立许可或交付约束的资源明确来源。
  依赖安装成功、页面夹具启动、真实组件接通和安装包构建成功分别记结论。
- 给出至少一个已验证的现有专项命令和对应夹具入口；后续更新示例时一起验证，避免给出不存在的命令。
  正式质量入口继续使用 `tools/quality/run_tests.py`，不另造一套测试调度。

### 3.2 夹具只服务开发验证

先整理 `tests/fixtures/` 及已有 fixture 模块，复用最小合成库存、临时 SQLite、固定 dataset 和响应样本。
缺少的样本再补，公开夹具不包含真实 UID、账号内容、抓包或私有数据。
`tests/test_nte_analysis_core.py` 已包含临时目录、`ProcessStub` 和进程替身，也包含真实执行物用例；
先整理清楚测试分层与前置条件，不笼统宣称现有全部测试都脱离组件。

正式接口的替身由测试或独立开发入口显式注入，覆盖成功、缺组件、协议不匹配、超时、取消、旧代次结果等情形。
它只证明 Calc 如何处理该响应，不证明真实算法、采集完整性或游戏行为。
生产组件失败仍走正式错误路径；替身仅操作隔离测试数据，不注册为真实能力，不进入发行默认入口。
需要真实执行物的契约测试独立标识前置条件，缺组件时如实列出未验证项，不用替身冒充通过。

一个设置/只读页面的开发宿主已经足够验证第一批接线；暂不建设全产品模拟器、通用 mock 服务或插件 SDK。

### 3.3 常见修改应有明确落点

| fork 想改什么 | 首先改哪里 | 应避免的捷径 |
| --- | --- | --- |
| 页面展示、交互或新只读工具 | 对应 Feature 的 View/Controller、组合根的窄接线 | 挂新 MainWindow 字段、跨页读取私有控件 |
| 评分或角色面板 | 公共 `ScoringEngine`、面板服务及行为样本 | 在卡片、工具、求解适配层复制公式 |
| 配置或持久化字段 | 归属明确的 Service/DAO、追加迁移或原子 JSON 写入 | 页面直写数据库；把本机配置放入账号导出 |
| 静态资料与图片 | 正式候选构建、清单校验和晋升入口 | 运行时抓取补齐、直接覆盖发行资源 |
| 新组件能力 | Integration 的正式协议与能力门禁、对应契约测试 | 根据文件存在或进程存活假定业务就绪 |
| 文案或社区翻译 | 本文语言目录边界与对应功能 key | 翻译业务 ID、协议字段或数据库键 |

新增依赖须说明现有问题、Windows/打包成本和维护成本；框架抽象须对应真实消费者及其共同责任。
框架交付应包含职责图、一个完整业务参考实现和常见扩展步骤。开发者先理解小而清晰的接入约定，
再能从入口追到规则、写入和外部调用；不要依靠跨多个补丁模块猜测一个操作的完整行为。

## 4. 目标框架与全项目重构方法

### 4.1 从完整功能反推框架责任

按启动与账号、角色与配置、库存与扫描、计算与配装、战报、同步与插件、环境与工具建立全景清单，
追踪从用户输入到结果展示、持久化和关闭的完整链路，反查动态导入、脚本、资源及打包引用。
记录“继承／补足／重组／合并删除／历史兼容／待核实”及依据，不要求为普通函数重复填写架构档案。
框架设计覆盖全局职责和依赖，批次详细记录实际触及的数据身份、副作用、失败与验证方法。

沿用仓库分层方向，在其中形成一致、可学习的应用骨架：

```text
main.py → 显式启动准备 → src/ui/app.py 组合根
                              ├─ 应用/账号生命周期与共享资源
                              └─ Feature 接线 → View / Controller → Service
                                                      ↓              ├─ 统一纯规则
                                                任务与结果投影       └─ DAO / Integration
```

| 应补足的框架责任 | 继承基础 | 补足、合并与真实消费者 |
| --- | --- | --- |
| 显式启动与 Feature 接线 | `ApplicationPaths`、`AppContext`、现有组合根 | 统一创建/注入/关闭约定，将导入副作用移到启动；迁出 MainWindow 的功能接线，服务所有页面和隔离开发入口 |
| 任务读写、取消与生命周期 | `PageTaskLane`、`PageCommitLane`、既有 owner 和 token | 明确读取合并、已接受写入不重放、过期结果丢弃、关闭顺序及并发上限；收敛角色、配置、库存等重复 worker 控制，保留外部操作特殊语义 |
| 冻结业务上下文 | `AppContext.generation`、`WeightedAllocationDependencies`、冻结请求/预览 | 统一任务创建与提交前的身份复核接入，减少各页面临时拼账号/快照/dataset；按用例保留必要字段，不制造包含全项目状态的巨型 Context |
| 统一规则与错误投影 | `ScoringEngine`、面板服务、来源能力 helper、已有结构化结果 | 把同一规则的修复分支合成完整实现；统一状态、原因和下一步的投影约定，Service 保留业务错误，展示层负责文案 |
| 公共展示与页面更新 | `EquipmentPresentation`、现有页面模型及主题设施 | 统一评分/装备/差异展示和必要的增量更新约定，去掉各功能重复投影；保留现有外观与操作流程 |
| 语言扩展 | `ApplicationPaths`、本机配置、既有结构化状态 | 补充目录、解析、校验、回退和命名参数，随实际消费者迁移，不建立平行配置系统 |
| 持久化与组件边界 | DAO 事务、追加迁移、正式 Integration/组件协议 | 将散落的写入编排、能力门禁和异常收尾归回 owner；保留不同操作的幂等边界，不用通用重试掩盖结果未知 |

View 管控件与展示草稿，Controller 管任务和投影，Service 冻结并编排，DAO 管 SQL/事务，Integration 管 IO/协议。
框架统一这些责任和接入方式，而非要求每个功能生成同样数量的类。需要 DI 或调度设施时，优先扩充现有组合和任务机制；
若确需新抽象，指出它接管哪些重复实现，迁移后删除什么，以及如何用行为、资源或维护成本证明价值。

每项新增框架机制在编码前回答六个问题，写在所属章节或本批记录即可，不另建审批系统：

1. 现在哪两个真实用例存在相同责任或缺口？尚只有一个用例时，先用窄接口解决，不预设通用平台。
2. 继承哪个现有设施？新增部分接管哪个 owner、什么状态与资源？
3. 哪些实际入口、窗口字段、重复判断和转发链会被删除？未迁调用方如何在一个短批次内收口？
4. 哪些业务差异必须保留？例如读取合并和已接受写入、内部事务和外部后验确认不使用同一种取消/重试。
5. 如何证明正确、资源有界且没有明显新增开销？使用行为用例及同条件测量，而非接口数量。
6. fork 开发者新增同类功能时，能否沿一个实际模板完成接入、测试和关闭，而非同时修改大量隐式字段？

这些问题用于控制抽象的实用性，不排斥有价值的框架。框架的价值由接管和删除共同证明。

先用**基础权重设置的读取、编辑、保存/重置与离页处理**验证框架，再用读取较重、取消特征不同的第二个现有功能
验证共性，避免为一个页面量身造通用体系。显式启动单独成批。切片是框架落地顺序，不是缩小全项目目标。
过渡适配仅放组合边界，标明余下消费者和删除条件；整条业务迁完就移除桥接，不长期保留双入口。

### 4.2 主动合并散乱修复，形成更精简的完整实现

不止搜索重复代码，而要追溯“这些小函数和小模块原来在共同修复哪个流程”。对同一业务，
先整理正常路径、状态转换、边界与失败策略，再合成有唯一正式入口的完整实现。
比如多处保存后补刷、重复 dirty 清理、异步结果额外校验，应按统一提交与结果应用流程表达，
而不是再抽一个 helper，仍保留原补丁链和层层转发。

首切片的示范是把“按钮入口 → 窗口转发 → 提交 helper → 多次独立写入 → 补刷/清草稿”收敛成
“页面冻结草稿 → Controller 接受一次提交 → Service 完整校验 → DAO 单一事务 → 当前页面应用结果”。
合并的是同一提交的责任；事务失败、提交成功后展示失败和迟到结果分别保留其语义。
如果只是把旧链条原封不动搬进新的类，或为删行数把这些失败全部捕获成成功，不算合并完成。

具体闭环：问题样本与当前行为 → 完整业务规则 → 明确 owner → 合并实现 → 迁移全部消费者
→ 删除旧修复函数、重复判断、无意义包装和桥接 → 核对失败、取消与兼容行为。
同职责可合并模块，跨层责任仍通过窄接口协作；遵守 Python 文件 800 行门禁，不把“减少文件”变成万能类。

保留已发布迁移及有效旧格式升级。旧战报差分代码先确认正式接管、提取仍使用的 DTO，
再将必要反例转为测试；动态入口、工具及打包资源同样核对。关键字和文件年龄不是删除证据。

每批及总体按一致统计口径记录：自有源码总行数、有效代码行、中文注释/说明行、测试代码行的变化，
同时说明重复入口、分支和维护跳转的减少。排除生成物与第三方代码；注释增加导致总行数上升应如实拆分。
目标是完整业务实现更精简，不是行数竞赛；保护关键行为验证，同时主动删除低价值测试，
具体判定见第 4.7 节。压缩可读性或遗漏必要异常处理不属于有效减量。

### 4.3 全项目中文关键注释是完成项

范围包含新增、迁移以及决定保留的自有运行代码、工具和测试关键逻辑，不只给难懂的新代码补几句。
按模块/领域确认以下关键处已经用中文说明，并与实际代码一致：

- 模块职责、边界与主要流程；新 Python 文件首行中文摘要继续遵守仓库契约。
- 公共接口的输入输出、身份要求、线程约定及副作用；关键单位、空值和未知语义。
- 业务约束、算法取舍与理由，尤其是看似可简化却必须保留的分支。
- 状态转换、并发、取消、过期回调、资源释放和关闭顺序。
- 缓存键/失效条件、事务边界、迁移兼容与失败回滚。
- 兼容保留原因、异常策略、结果未知为何不重试，以及相应测试要保护的行为。

技术标识和外部协议名保留英文；注释解释责任与原因，不逐行翻译语法，不重复类型签名。
旧英文关键说明改为中文，过时说明删除或重写；决定保留的模块也须完成此项，最终覆盖包含尚未发生结构迁移的模块。
用关键入口与流程审查确认覆盖，不以中文字符比例代替质量。业务事实只在权威文档维护，代码注释链接必要依据。

每个领域的完成记录列出关键入口、规则、状态与异常路径及其中文说明位置，既有说明准确时直接保留。
第三方源码、生成代码、许可证原文和协议原文不做批量翻译。关键逻辑尚未厘清时先标明待核实，
不让注释编造设计意图；普通赋值、标准属性访问等没有独立业务语义的行也无需凑注释。

给 fork 的关键说明模板如下；只填与该接口有关的项目，不在每个短函数复制整块模板：

```text
模块摘要：本模块负责什么；哪些责任交给其他层。
接口约定：输入/输出、单位、正式身份与未知值；调用线程和副作用。
关键原因：这个约束或分支为何存在；删除会破坏什么行为。
生命周期：状态如何推进；取消、失效、关闭时由谁收尾。
一致性：事务范围、缓存失效、失败保留什么；为何允许或禁止重试。
验证依据：对应公共行为用例，必要时链接权威领域文档。
```

例如保存接口应解释“先校验全部角色再提交；事务失败保留全部草稿；提交后投影失败只重载，不重新写入”；
异步回调应解释“账号代次失效即丢弃展示结果，不用新账号上下文补齐旧请求”。
说明随实现审查，错误注释本身就是缺陷；禁止依靠轻量模型批量猜测并发和业务意图。

### 4.4 用一个完整业务校验框架，而非只展示新目录

首个参考切片以基础权重设置为默认对象，开工前核对真实消费者并固定以下行为：

| 环节 | 框架应承接的责任 | 切片出口 |
| --- | --- | --- |
| 读取与快速切换 | 固定账号/代次和读取身份，后台读取，应用结果前复核 | 旧读取不覆盖新选择，加载失败不把已有数据清空 |
| 编辑与刷新 | View 保留草稿，Controller 协调展示；同一权重规则只有一个入口 | 无关刷新不覆盖编辑，重复刷新不反复建立完整控件树 |
| 保存与重置 | Service 校验并编排，DAO 原子写入；已接受的提交按其身份执行 | 成功后清理对应草稿，失败保留草稿；快速点击不产生无界任务或静默丢掉已接受写入 |
| 离页、切账号与关闭 | 统一取消/关闭及迟到回调处理，明确尚未提交草稿的既有策略 | 不误写另一账号，不产生悬挂 worker；保持原有离页交互 |
| fork 参考 | 显式接线、合成数据、公共行为用例及中文说明 | 开发者可沿一次操作追到持久化，旧窗口字段和补丁链已被接管 |

第二类业务优先选已有库存读取/筛选，验证大结果投影、读取合并和取消边界；实际瓶颈不在此处时，
由基线选更合适的现有功能，并记录差异。两个切片不强行共享业务规则，只共同验证接线、任务和生命周期约定。

全景审查按领域维护“已定位／链路已核对／迁移已完成／验证已通过／保留／待核实”的覆盖状态，
每项附责任入口、当前消费者与依据。文件数量、搜索命中和目录图只是定位证据，不算完整链路审查；
静态核对也不等于运行验收。其余范围有明确余项，避免用一个成功切片代表全项目完成。

### 4.5 首轮接入的推广门槛

当前接线事实由[系统架构](../architecture.md)维护，本方案只规定模板推广的出口。
独立页面、窄 Service 和统一事务只是必要条件；下列检查齐备后，才将它作为全仓迁移模板：

| 检查 | 必须证明的行为 |
| --- | --- |
| owner 的逻辑关闭与物理释放 | 关闭后拒绝新任务；迟到读取不应用；正在运行的读线程与已接受写入收尾后释放对象，既不留存也不提前销毁 |
| 重复生命周期 | 连续切页、账号代次变化与关闭再进入后，存活 Controller、worker、连接和缓存回到声明上限；只测一次关闭不够 |
| 保存完整性 | 多字段、多角色先完整校验，再使用同一连接的单一事务；写入终态确认与展示失败分开，避免重复提交 |
| 默认回归覆盖 | 专项中的关键公共行为确实进入质量入口；pytest/unittest 不漏发现、不重复递归运行，失败保留退出状态 |
| 性能归因 | 特性导入、构造、首次读取、热读取和结果应用使用相同计时边界；首次变慢也如实报告，热态更快不抵消冷态退化 |
| 第二类消费者 | 以不同数据规模或任务特征的真实业务验证共同责任；仅复用接线和任务约定，不共享权重领域规则 |

推广前的缺口先在参考切片闭合，不用扩大迁移掩盖它们。尚未迁移的功能保持原有效 owner，
明确下一批接管对象；公共机制修改后复核已接入消费者，避免为第二页面修好却让第一页面回归。

### 4.6 各层按业务领域模块化目录

目录模块化是恢复实施后的必交付项，不是仅给现有平铺文件改名。`features/` 已有的功能区域继续复用；
`services/`、Domain、DAO 和 Integration 中不同领域的代码逐批归回自己的子包。
采用“**外层表达架构职责，内层表达业务领域**”：贡献者能直接找到某功能的实现区域，
又能辨别哪些部分是页面、编排、计算、持久化或协议适配。按领域贯穿链路，不把各层重新揉进一个 `features/` 大包。
目录归组是职责整理，不是新增公共抽象；单一领域即可独立成包，无须凑两个消费者或再加一层 API 转发。

以下是**目标设计示意，不是已迁移状态或预建空目录清单**；只有实际保留代码需要时才落相应包：

```text
src/
  app/                         # 应用上下文、生命周期等共性；GUI 组合根仍在 ui/app.py
  features/<现有功能>/           # 页面、Controller 与功能接线
  services/
    accounts/                  # 账号与账号设置
    characters/                # 角色面板、权重与养成配置编排
    inventory/                 # 库存读取、来源与状态编排
    equipment/                 # 槽位、配装保存与变动对比
    allocation/                # 计算请求、预览与分配流程
    battle_report/             # 战报业务与分析请求
    catalog/                   # 静态目录与只读资料
    environment/               # 本机环境、工作模式与组件管理
  domain/<业务领域>/            # 该领域的纯规则与数据模型
  optimizer/                   # 现有纯计算边界，按算法职责组织
  storage/sqlite/<业务领域>/     # 领域 DAO；连接、事务基础及已发布迁移保持统一所有权
  integrations/<集成能力>/      # 按外部组件/IO 能力归包，复用已有成熟子包
tests/<业务领域>/               # 精简后保留的关键行为测试与局部夹具
```

具体包名与文件归属根据当前职责和消费者确定；成熟功能目录优先保留，不为统一单复数或页面名称机械搬迁。
基础权重编排的目标区域为 `services/characters/`，配装保存归装备领域；页面名不必与业务包逐字一致，
但在责任图中给出对应关系。按责任而非文件名前缀归属，战报专属角色规则不因含 `character` 就搬进角色包。
既有 `models/`、`scanner/`、`solver/`、`optimizer/` 及 `ui/` 中的业务代码同样审查归属：已有清楚边界就复用，
遗留混放则随所属链路收敛，不另建同职责平行包。测试按业务保护点组织，不逐层镜像生产树并重复测试同一事实。

**公共入口与共享代码先明确所有权，再决定位置：**

- 领域公开入口采用少量职责明确的 Service、数据模型或协议模块；调用者显式导入所需符号。
  不要求每包新增 `api.py`、注册器或包装类，也不靠 `__init__.py` 全量重导出伪装公共 API。
- 仅一个领域使用的 helper 留在本领域；真正跨域的纯规则归其权威 Domain，任务/生命周期共性归现有应用设施，
  数据库基础归 Storage，IO 共性归 Integration。不为消除两个 import 就创建无 owner 的 `common`、`utils` 大包。
- 跨领域流程由一个明确的 Application Service 冻结输入并编排，调用各领域窄公开接口；跨表原子性仍由 DAO
  在同一事务中保证。不得让领域相互调用私有实现、各自偷偷提交，或借共享 Context 绕过依赖方向。
- 目录位置不改变资源 owner、正式 ID、持久化格式和组件协议；只整理内部路径时不顺带修改对外 contract。

每一迁移批次按“**归属与消费者 → 删除无须保留的代码/测试 → 合并有效流程 → 归包并迁完引用 → 核对 → 删除过渡入口**”闭环：

1. 每个自有功能文件有明确领域或应用级共性归属。层根目录只留下包入口和确有跨域职责的少量模块，
   不在新建几个子目录后继续让大多数业务文件平铺。暂未迁移领域保留原有效入口并列入下一批，不创建空壳占位。
2. 相关修复按完整流程合并，低价值测试先删再迁，避免花费预算搬运随后要删除的内容。
   纯搬文件可以是必要步骤，但不冒充补丁合并；不借目录批次重写已经清楚稳定的业务。
3. 同一批更新生产 import、字符串/动态入口、测试与替身 patch 目标、工具和打包引用；
   特别核对 `__file__.parents`、相对资源路径及默认路径，包下沉后仍须解析到同一正式资源，不按新目录层级碰巧取值。
   迁完后删除旧平铺模块；短暂桥接仅用于该批组合边界收口，不把逐文件重导出壳、别名或双入口列为交付状态。
4. 普通导入保持无账号读写或进程启动等副作用，依赖不出现循环；公共接口保持窄而显式，
   不用聚合导入一次加载全部领域，也不为查找方便引入额外常驻注册或反射扫描。
5. DAO、连接与已发布迁移的所有权和语义保持；迁移文件的编号、内容和既有执行链不因目录整理重排。
   本机数据、静态目录、组件清单与用户配置路径也不是源码重排对象。
6. 保留测试随领域迁移，复用 `tools/quality/run_tests.py`，核对嵌套包发现、模块限定名、`core` 选择、
   串行及并行子进程导入、专项入口和退出状态。防止子目录漏发现、重复发现、零测试假通过及旧 patch 路径失效；
   测试目录成功创建不等于门禁已经接管。所需修正纳入同批质量入口维护，不另造运行器。

稳定后在现有架构文档记录领域职责、主要公开入口、上游/下游及一个真实用例即可；
批次用旧位置到新位置/删除决定的简表核对消费者，不为每个文件建立档案或额外“模块框架”。
完成看实际归属、唯一入口、引用与保留门禁是否闭合，以及导入成本和原功能是否保持；目录名和移动数量不是完成证据。

### 4.7 随全仓审查主动删减测试

测试同样是需要重构的项目代码，不因已有文件、历史补丁或“可能有一天有用”而默认保留。
**长期集合只保留能说明具体核心业务或关键数据不变量的少量有效验证；非关键用例直接删除。**
审查一个生产领域时同步完成保留、合并、重写或删除，不把删测留到全项目重构末尾。
无需逐用例重新审批、先造等价替代或等量补测；“也有一个独立行为”并非保留非关键测试的理由。
实际删测随获准实施的领域批次执行；本次文档改写不执行删除。

按以下规则筛选，不默认守住原有测试数量、全行覆盖或每一处防御分支：

| 判定 | 处理方式与例子 |
| --- | --- |
| 核心业务 | 保留少量代表性评分、合法分配、冻结预览保存与方案来源用例，验证结果而非内部调用布局 |
| 关键数据与副作用不变量 | 保留旧数据升级、账号隔离、单一事务/失败回滚、完整库存与来源能力、真实 UID 唯一性、取消/迟到写入、外部派发后验确认及未知结果不重发等必要验证 |
| 关键用户流程与资源 | 用代表性流程保护失败不丢数据或草稿、切页/切账号/关闭收尾、资源有界，以及必要的键盘可达性和内容可操作性；不逐页复制整套同类测试 |
| 同一事实重复保护 | 合并到最贴近责任 owner 的行为用例或少量参数化场景，删除 helper、Service、UI 层的等价断言及重复夹具；各有独立关键后果的边界分别保留 |
| 已废弃行为或旧补丁入口 | 直接删除；有效旧数据升级行为另按正式 contract 验证，不为废弃函数或兼容壳保留测试 |
| 仅固定实现细节 | 删除类/私有字段存在、具体函数调用顺序、源代码片段、目录布局或旧 import 等没有公共行为价值的断言 |
| 装饰与低价值防御 | 删除颜色、像素、边距、装饰图、普通 getter/setter、无风险转发，以及无实际场景且低后果的畸形参数穷举 |
| 脆弱或昂贵但确属关键 | 只留下必要反例并改成稳定行为验证，共享有界夹具；需要真实组件/窗口的验证标明前置条件，不以慢测名义保留非关键用例 |

重要性看“失败是否破坏核心结果、持久事实或关键操作边界”，不看名字含 `boundary`、`regression`、代码年代或模型的担心。
低频但会串账号、损坏用户库、重复外部写入的场景仍关键；普通实现细节不因用了 mock 或曾经修过一次就升级为 contract。
调用次数若实际保护“一次写入、未知结果不重发”，属于业务边界；若只是固定内部 helper 的调用方式，则应删除。

处理顺序：保留已有基线与失败记录 → 列出本领域少量关键保护点 → 选取有效用例 → 直接删除其余非关键用例、
合并重复保护并清理无消费者夹具 → 只对缺失的关键点补最小验证 → 核对保留集合的发现、执行与失败传播。
记录按领域列出保留的关键点、删除/合并类别与涉及文件即可，不逐断言写报告，不要求先把旧全集修到绿色才能删测。

删测的交付是维护负担实际下降。用现成统计记录测试规模、同条件运行耗时及维护依赖的变化，
不建立测试行数或覆盖率竞赛，不设删除百分比，也不要求新增量抵消删除量。
移入 `optional`、慢测组、改名避开发现或加 `skip` 均不算删除；这些测试源码及仅为它服务的夹具应从仓库移除。
`full` 表示精简后保留集合的完整发现与执行，不隐含恢复历史全集；`core` 仍覆盖关键边界，不因目录迁移漏项。
新实现同样只为明确的关键保护点增加必要验证，不为每个私有分支重新长出一套测试。

**用户暂挂的既有报错测试单独保留。** 本轮不追修，也不因失败删除、弱化断言、改名避开发现或加跳过；
原始命令、输出与失败身份留在已有本机记录。必要的纯路径迁移只更新引用并保留身份映射，不改测试含义来转绿。
该约束只作用于用户明确暂挂的集合，不成为保留其他非关键测试的理由；本轮新增回归仍须处理。
暂挂失败若阻断某条链路的关键正确性判断，该链路停在待验收，其余独立批次继续，不以全量绿色为名扩大本轮任务。

其他测试按价值规则正常精简。测试删除、真实缺陷修复、暂挂失败和环境缺口分别记结论；
删测后的绿色结果只证明保留集合，整体仍有暂挂失败时如实报告，不宣称此前所有失败均已修复。
公开行为约束、数据库约束、正式协议和 Ruff 硬门禁仍成立，测试数量减少不替代正确性证明。

## 5. 低配电脑的流畅性、稳定性与资源预算

### 5.1 不变的可靠性边界

账号代次、固定库存、方案来源快照、冻结评分、稳定槽位和 UID 唯一性继续成立。
取消、账号切换、退出和模式降级先撤销新副作用权限；旧回调不更新新账号。
外部操作区分派发与后验确认；结果未知不自动重发。原始战报不可改，未知不转成零。
这些规则以 [AGENTS.md](../../AGENTS.md)、正式协议和各领域文档为准，不在新抽象里重新解释。

故障处理也属于大众可用性：保存失败保留草稿，加载失败不显示空库存，缺组件指向具体修复入口，
后台任务有可理解的状态和停止反馈。诊断沿用现有结构化日志，禁止为“可观察性”额外记录敏感 payload。

### 5.2 以持续响应为目标，而非只追求计算更快

复用[响应性治理](ui-responsiveness.md)与[测量口径](../validation/ui-responsiveness.md)，
先确认已有优化仍成立；框架应把有效措施变为各功能都能正确接入的共同能力，并补足实际缺口。

1. 清理 UI 主线程上的长同步 IO、数据库等待、解析和大计算，包括完成回调里一次生成海量控件的停顿。
   仅把查询挪到 worker，结果应用仍卡顿，也算未完成；UI 对象创建及更新继续遵守 Qt 主线程边界。
2. 消除重复查询、反复解析资料、整页重建和无关变更失效；对大列表优先按需加载、增量更新、可视项复用。
   批次应用结果时保持投影身份一致，不显示混合版本的半成品。
3. 读取队列、worker、缓存、图片解码与常驻数据有明确上限。快速切页/筛选合并过期读取，已接受的写入仍按
   原有事务完成；单个功能的提速不以抢占全部 CPU、堆积线程或持续扩大内存为代价。
4. 查询慢先核对范围、索引与查询计划。CPU 密集的 Python 工作先测 GIL 与调度影响，按实际瓶颈选择批处理、
   既有进程边界或合适的执行方式；更多线程本身不等于更多响应能力。
5. 重任务有及时反馈、合理进度和可用的取消入口；取消先反馈，再按 owner 契约收尾。
   UI 线程不阻塞等待 worker 退出，超时保留明确状态，禁止随意杀进程或重发结果未知的外部操作。
6. 分别测 Calc 准备、序列化、组件求解、结果恢复和 UI 应用；外部组件保持冻结身份，瓶颈归因到正确仓库。
   与游戏同机时关注后台 CPU、内存和 IO 竞争，四日内没有真实共存测试就明确保留这一缺口。

缓存仅在重复成本已确认时引入，键包含实际账号、dataset 与配置依赖，中文说明容量、失效条件和 owner。
引入公共调度或缓存能力时以多个真实消费者验证，不将未量化的抽象层开销转嫁给低配用户。

### 5.3 低配验证与资源受限代理分开报告

选择小、中、大库存及代表性角色/历史记录组合，冻结样本、组件、预算和环境。逐项测：

| 场景 | 优先观察 |
| --- | --- |
| 冷启动、首次开页 | 首次可交互时间、最长主线程停顿、资源初始化峰值 |
| 切页、滚动、筛选、重复输入 | 反馈延迟、事件循环 P95/P99/最大延迟、过期工作量与控件复用 |
| 读取、保存、刷新 | 主线程响应、完整就绪耗时、事务一致性、草稿保留与重复提交 |
| 计算等待、取消、退出 | 交互持续可用、取消反馈与实际收尾分别计时，worker/进程最终释放 |
| 重复操作和长时间空闲 | 内存/句柄/线程数量是否持续增长、后台轮询及 CPU 占用 |
| 账号切换、慢 IO、组件异常 | 过期结果丢弃、故障隔离、无界面未响应、旧事实保留 |

真实低配机器记录 CPU、可用内存、存储、电源模式、分辨率/DPI 和后台负载；没有机器时使用明确配置的
资源受限代理与慢 IO/长任务夹具，结论标明“代理环境”，不将降低线程数当成完整低配真机证明。
Qt offscreen 用于隔离行为与事件循环测量，真实滚动、绘制和显示体验另做窗口验收。

记录相同条件下的 P50/P95/P99、最大停顿、超预算次数、总耗时、峰值/稳态内存和结果一致性。
单独报告冷/热样本与异常样本；P99 样本量不足时报告全部样本及最大值，不用不稳定分位数装作尾延迟证据。
优化前冻结交互预算、允许退化范围和噪声口径，超出时定位、修复或退回，不在结果出来后悄悄放宽标准。
本轮优先改善可重复的未响应与卡顿，不承诺消除操作系统或游戏占满资源造成的所有停顿。

### 5.4 前端保留成果，只修有证据的问题

现有信息架构、导航、操作流程、主题和视觉风格作为基线。Controller、数据流和渲染实现可以大幅重整，
但这不构成重新设计页面、改菜单或新增操作步骤的理由。

允许的可见修复限定为：明确的交互不一致或重复点击无反馈；状态混淆与过长帮助文字；三主题可读性、
控件遮挡、长文案/混合 DPI 越界；确有问题的间距、对齐或焦点反馈。
每项列出原问题、最小改动和可复核效果。说明文案坚持“当前状态、必要原因、下一步”，详细诊断留详情与日志。
无问题依据的重排导航、换色、全站组件换肤或交互重做不进入四日计划；若确有新产品诉求，另行确认。

### 5.5 最终 EXE 与发行包瘦身

用户新增目标：**最终打包的 EXE 尽量小，并同步减少实际下载和安装占用**。这是本轮重构的正式目标，
不是只整理源码；但正确性、必要功能、兼容性、低配启动与稳定性仍优先。删掉测试或缩短 Python 源码
不直接代表发行体积下降；目录模块化时同步核对真实打包输入与依赖闭包。

沿用 `build_exe.py`、`build_installer.py` 及 `tools/release/` 的现有流程，补足其审查和验证，
不另建打包框架。审查顺序与措施：

1. **同条件基线**：冻结版本、锁定依赖、dataset、组件清单和构建参数，分别记录主 EXE、安装包、
   完整发行目录及安装后占用；按运行库/Qt/OCR/分析组件/数据库/图片列出主要占用。单目录与单文件分别比较，
   不以主 EXE 变小掩盖旁置文件增大；先量出基线再提出 MB/比例目标，不预先保证压缩百分比。
   EXE 按文件字节数直接读取，目录按文件汇总；构建日志已统一此测量入口并报告 MiB，
   合成文件/目录已验证，真实发行前后大小仍待同条件构建；不将测量修复视为体积已经下降。
2. **打包输入收敛**：核对 hook、hidden import、资源收集与实际静态/动态消费者，精确排除开发工具、
   专用测试依赖、缓存、历史无消费者资源和重复运行库；源码环境保持可开发，裁剪仅作用于隔离发行候选。
   账号数据、日志、抓包、私有源码与调试产物按现有发行门禁排除，不能将其作为发行资源。
3. **运行库精确裁剪**：扩充前先审计已有 `runtime_pruning.py`，避免重复裁剪或扩大清理范围。
   现有裁剪仅在 onedir 构建分支调用；onefile 须单独核对构建输入与产物，不沿用单目录结论。
   PySide6 平台/图片/主题与软件渲染、OCR 实际后端、数值求解所需库和正式组件及许可保持完整；
   是否使用以真实依赖闭包和打包烟测为准，不靠扩展名、目录大小或静态 import 缺席判断。
4. **资源与静态数据**：复用 `installer_asset_dedup.py` 做字节相同的素材去重并恢复清单规定路径，
   安装包输入去重后仍恢复各原路径，不自动减少安装后占用；不同指标分别报告。
   不降图质、不删可分享技能图、不改变资源身份。静态库重打包只在候选中做，逐表核对逻辑等价、
   schema/索引、外键、来源与清单后经正式入口晋升；不直接改发行库或账号库。
5. **体积与低配共同验收**：压缩/布局方案同步比较冷启动、重复启动、峰值内存、临时解包占用及更新成本；
   单文件、UPX 或高压缩均不是默认答案。若只省少量空间却显著拖慢低配启动，保留更稳妥方案并记录取舍。

完成证据为同输入前后体积明细、候选删除/保留清单、实际恢复路径与功能烟测、升级及回退。
必要覆盖启动、三主题、图片与分享、评分/保存、OCR、正式分析组件、同步/装配所需组件及其缺失提示；
具体发布门禁复用 [AGENTS.md](../../AGENTS.md) 与 [Windows 验收](../validation/windows.md)，不复制另一套标准。
当前仅获准源码开发与测试，**打包、安装、部署及真实游戏操作仍须用户另行授权**；在此之前交付输入审查、
候选措施与待验收项，保持体积数据未测状态，不宣称 EXE 已变小。

### 5.6 OCR 后端可拆卸与单库实验预备

本轮新增开发要求：OCR 后端的依赖、初始化与打包必须可以独立选择，让维护者通过一处明确配置，
就能在独立实验环境中移除某个 OCR 库，应用和未受影响功能仍正常工作；无需逐处修 import、资源校验与打包脚本。
本阶段先完成可拆卸结构，保留现有默认与兼容行为，不在重构中直接删除后端或宣称单库兼容已经验证。
最终以一个满足需要的 CPU 路径和一个可选 GPU 路径为候选目标，具体取舍在重构稳定后的真实实验中决定。

必须区分推理运行库与执行设备：OpenVINO 是当前 CPU 候选；ONNX Runtime 同时可提供 CPU 与 DirectML GPU 路径。
DirectML 不是脱离 ONNX Runtime 的独立 OCR 库；若保留 DirectML，必须携带匹配的 ONNX Runtime 变体。
因此 OpenVINO 与 ONNX Runtime 的 CPU 路径可比较取舍，但不是把两库机械分成“一个 CPU、一个 GPU”。

初始化责任已从 `ocr_engine.py` 收拢到 `recognition/backend_runtime.py`，默认路线无无关设备探测，
模型私有参数/前后校验、取消与 DLL 句柄持有已经接入。单库支持声明、依赖选择、消费者及打包输入现已接管，
四个独立 OCR 环境已按锁同步，并验证所选组、collector、冻结资源与 CPU 合成推理；详见
[OCR 验收边界](../validation/architecture-renewal-day1.md#23-质量引用收口与-ocr-支持集合)。
这些证据不等于完整产品独立环境、真实 GPU 或冻结 EXE 验收；构建仍须另获授权。

实施边界与实际接管：

1. **按后端归组，延迟导入**：复用现有 OCREngine / BatchProcessor 业务入口，推理与原生库加载职责归
   `src/integrations/vision/recognition/` 的后端模块与后续具体适配器。共享选择入口不在模块导入时加载所有第三方库，不扫描未启用后端的
   provider、DLL 或设备。只有本次选择或明确回退到某后端时才初始化；迁完删除被接管的旧分支，不建设插件 SDK。
2. **一个选择来源**：维护者在一处声明允许的后端、默认候选及有序回退；显式单后端实验不被扫描 worker 的
   固定参数、环境变量或其他调用方偷偷覆盖。扫描、鉴定、装配识别和倒带等消费者沿用相同选择约定，
   不必逐处修改。发行构建依据同一支持清单决定依赖与资源，运行时只在实际随包支持的后端中选择。
3. **统一现有结果与生命周期**：后端适配器保持既有文字、框、数值解析输入与错误语义，说明初始化、
   预热、取消和释放的所有权。CPU/GPU 由实际使用设备或 provider 表达，不沿用“检测到显卡＝已加速”
   或“OpenVINO＝核显”的文案；已安装、初始化成功与真实推理成功分别验证。
4. **可选库缺失不拖垮产品**：区分未启用、未安装、加载/初始化失败和推理失败。
   未选中的库缺失不影响模块导入、窗口启动、账号、同步、评分和保存；请求 OCR 时仅按已声明的可用后端回退。
   明确单后端实验不自动换引擎掩盖失败；全部 OCR 后端缺失时仅 OCR 操作给出状态、原因和安装/选择建议，
   不导致整应用退出，也不把依赖失败解释成识别成功但结果为空。日志保留实际选择与回退原因，不记录截图或 OCR 原文。
5. **依赖与打包同批收敛**：pyproject/锁文件中的 OCR 依赖分组、PyInstaller 的 hidden imports、数据/DLL
   收集、许可证、运行库裁剪和产物校验均按所选后端执行，不要求所有库同时存在，不把缺失提示吞掉后继续发布坏包。
   共享模型仍只携带一套经校验的资源；模型来源与模型校验不强制导入或验证被移除后端的包内副本。
   ONNX Runtime CPU/DirectML 变体使用互斥的实验依赖选择和独立环境，避免同名模块相互覆盖；公共图像/数值依赖
   先核对其他功能消费者，不随某个 OCR 后端盲删。
6. **便于单库验证，不扩前端**：提供简短的维护者配置与依赖安装/移除、构建选择及恢复步骤。
   模拟缺库用于快速边界测试，真实单库验证必须使用确实未安装另一运行库的独立环境，不能只改一个布尔值。
   常驻界面不新增复杂引擎管理器、下载商店或强制联网步骤；本轮不建设分发渠道，不保证体积或识别效果的数字。

后续验收矩阵至少包含：

| 实验配置 | 必须确认的行为 |
| --- | --- |
| 仅 OpenVINO CPU，未安装 ONNX Runtime/RapidOCR ONNX 适配器 | 应用与同步正常启动；OCR 按声明只使用 OpenVINO；没有未选库导入或校验阻断 |
| 仅 ONNX Runtime CPU，未安装 OpenVINO/RapidOCR OpenVINO 适配器 | 应用与同步正常启动；CPU OCR 可执行；不依赖 DirectML provider 或 OpenVINO DLL |
| ONNX Runtime DirectML 变体，未安装 OpenVINO | 支持硬件上确认实际 GPU 推理；不支持/失败按明确配置使用同运行库 CPU 或报告失败，不偷偷依赖 OpenVINO |
| 默认与兼容/低负载路径 | 所选清单内回退与线程限制保留；所有 OCR 消费者使用一致配置，既有业务结果不变 |
| 未选库缺失、选中库初始化失败、所有 OCR 库缺失 | 非 OCR 功能保持；单后端失败可辨识；无启动崩溃、伪成功或隐藏回退 |
| 单目录/单文件发行候选 | 被排除库及其专属模型副本不进入产物，已选后端依赖与许可证齐备；另获构建授权后做真实包烟测 |

结构预备、独立环境推理、真实硬件 CPU/GPU 性能与识别结果、实际发行体积分别记录完成状态。
重构阶段可以先验证依赖隔离与选择行为；尚未执行真实扫描、硬件或打包的项保留待验收。
按已有授权范围运行专项与静态检查；侧面讨论只更新方案，不自行安装/卸载库、运行测试、构建或操作游戏。

## 6. 语言扩展：界面与功能输入分开预备

### 6.1 界面语言预备之后的覆盖

目录校验、字段合并、坏包回退、本机安装、下次启动偏好、公共提示与实际语言设置切片已有实现；
当前行为及 fork 格式唯一说明见[界面语言补丁](../features/localization.md)，结构见[本机偏好分层](../architecture.md#24-本机偏好与文本目录)。
专项与静态检查属于预备证据，不代表全部页面完成翻译或真实 Windows 验收。

后续功能整改时逐页登记语义 key、参数与译文覆盖，优先迁公共错误、进度和确认提示；
不把文案抽取作为账号、性能或组件治理的前置工程。现有前端保持，不增加全界面即时重建、语言商店、自动下载或插件 SDK。
实际复数、数值/日期及区域规则有需求和样本时再选择实现，正式 ID、协议枚举、数据库键和日志事件码继续与显示文本分离。

完成度分别记录：**预备完成**为目录/校验/回退/偏好/切片可运行；**文案覆盖完成**为目标页面全部接入；
**新语言发布**为实际翻译、审校与布局验收。当前只交付第一项，其他两项及功能内语言识别保持独立待办。

### 6.2 鉴定与扫描的功能内语言预备

**界面语言、游戏或截图输入语言、游戏资料显示名是不同维度。** 未来具备对应识别资源后，
中文界面可以处理其他语言截图，其他语言界面也可以处理中文游戏；当前支持范围仍以已验证配置为准，
不从界面语言推定。
自动扫描的输入来自当前游戏界面，鉴定的输入也可能是他人分享或历史截图，应允许未来按本次输入明确选择。
本轮保持现有中文识别行为，只固定扩展责任和接入点；不同时开发海外语言 OCR、翻译全量资料或加入空注册框架。

当前代码中的实际依赖与整改落点：

| 环节 | 已核实的现状 | 重构应保留的扩展边界 |
| --- | --- | --- |
| 共用图片识别入口 | 鉴定 Controller、扫描 worker 均创建 `src/integrations/vision/recognition/batch_processor.py` 的 `BatchProcessor` | 两类图片入口复用一条识别管线，当前显式传入冻结的静态/词条资料；其他输入配置逐步接入，不各自加语言分支 |
| OCR 模型与执行后端 | `src/integrations/vision/recognition/model_resources.py` 校验固定 `ch_*` 模型；`backend_runtime.py` 选择执行后端，`ocr_engine.py` 共用文本与框投影 | 模型、配套字符字典与语言能力是一组资源；执行后端另选，不把 CPU/GPU 切换当作语言支持 |
| 套装和词条解析 | `parser.py` 的套装/卡带匹配会过滤非中文字符，套装候选取 `name_zh`；`src/domain/stat_catalog.py` 含中文别名与属性规则 | 按输入语言归一化词条、名称和数字格式；别名映射到正式 ID，再用必要的现有模型适配层连接评分，不翻译或批量改写旧存量键 |
| 类型与场景 | `src/integrations/vision/recognition/equipment_classifier.py`、`screenshot_parser.py` 用中文关键词判定驱动、卡带和奖励场景；`identification_parser.py` 过滤说明文 | 物品分类、场景与排除规则也随输入配置核对，不只替换 OCR 模型和词条词库 |
| 截图与模板 | `config.py` 按批冻结基准裁切区；实际形状模板字节/布局随图片确认与提交；`new_tag.png` 扫描标记尚独立 | 布局、字体或按钮改变时单独验证；几何形状模板经验证可共享，不假定所有图片都需逐语种复制 |
| 视觉结果与增量 | `src/services/inventory/vision_snapshot.py` 用本批中文套装目录关联 ID；`file_lifecycle.py` 用解析值构造对比签名 | 同语言别名解析成统一身份后再比较；不同识别配置的旧解析缓存和增量基线不直接互用 |
| 任务依赖 | `src/features/scanning/dependencies.py` 已冻结账号、代次及路径 | 未来沿用任务冻结机制携带识别配置，不在执行中读取全局语言开关或切换模型 |

手工及剪贴板文本鉴定另有 `src/features/identification/manual_parsing.py` 入口，未全部经过图片处理器；
未来同步核对它的类型、品质和名称别名，不为预备强制合并两种输入框架。

**未来识别配置的最小内容**为：输入语言、配置版本、游戏资料身份、OCR 模型/字符字典身份（模型内嵌或独立文件）、
词条及套装别名表、数字解析规则、所需布局/模板配置及其来源与哈希。这里只规定责任，字段在真实切片接入时固定。
已有路径、清单、静态资料晋升与 worker 生命周期继续复用，不为预备另设数据库列、抽象工厂或插件系统。

- **资源归属**：界面文本补丁仅改显示；识别词库、模型和模板按正式数据/组件清单校验和成套安装，
  不借纯文本 UI 补丁加载模型或替换数值公式。声明的语言名称不等于实际识别能力。
  配套字符解码顺序须在两个 OCR 后端间验证一致；真实第二配置接入时，沿用不可变资源身份，不重新引入可变模型参数或永久路径缓存。
- **剩余冻结接管**：静态/词条获取、图片确认、匹配评分与视觉事务授权已接管，责任见
  [识别架构](../architecture.md#25-视觉输入与共用识别)，不重复建立第二套读取入口。
  初始化资源校验、未选路线探测、图片形状模板/布局及模型/字典的确认和提交身份已接管；
  两后端实际字符顺序已核对并在构造/预热/推理检查，资源错误贯穿离线及流水线消费者；增量 NEW 标记、
  冻结 worker 交接和最终文件授权已接管，首图比对复用后台解析器，不覆盖取消原图。装配与倒带已采用
  单任务 OCR owner；独立 OCR 环境的单库选择及依赖闭包已验证，分别见[执行 OCR 验收](../validation/architecture-renewal-day1.md#22-执行-ocr-与倒带输入单任务所有权)
  与[支持集合验收](../validation/architecture-renewal-day1.md#23-质量引用收口与-ocr-支持集合)。初始模型校验不替代完整识别资源冻结。
  输入配置可由默认游戏设置派生或按本次截图覆盖，但运行中不重绑；不同配置的旧解析与增量基线不混用。
- **截图链剩余范围**：前置删除已由独立暂存、后台完整提交与结构化文件结果接管，责任见
  [识别架构](../architecture.md#25-视觉输入与共用识别)及 [文件契约](../integrations.md#截图暂存与发布)。
  原暂存继续解析及已保存后的文件专用重试已由实际 GUI 提交 owner 接管，不重新截图、不重放数据库。
  仍需真实游戏/低配验证及全链进程中断恢复；局部恢复证据不等于全链崩溃恢复。
- **补录草稿**：当前失败保留旧背包及未后处理的输入截图，不承诺已关闭补录弹窗的草稿可再次打开。
  后续按账号代次和原识别身份明确草稿 owner/失效规则，不静默把旧数值套到新词库；避免扩建通用草稿框架。
- **错误语义**：缺少相应模型、字典或资料时报告未就绪；识别歧义进入现有失败/人工修正流程，
  不用中文模糊匹配替代其他语言结果，不把未知词条变成零或凭默认品质制造成功。全量扫描仍只提交完整结果。
- **缓存与增量**：身份包含识别配置及资源版本；输入语言、模型、词库或布局变化时重新解析或重建增量基线，
  不因此清空已保存库存和方案。识别成功后的业务身份不携带翻译文本作为主键。
- **低配与体积**：保持单次任务仅使用所需配置，模型按需初始化并有界持有，不在主线程同时预热所有语言。
  优先复用经验证适用的模型/模板；额外模型未来作为明确的可选资源成套安装，不默认塞入 EXE，
  安装与分发方式另做验证，不在本轮增加自动下载。

本轮的验收是两类识别入口、语言相关解析、模型/模板、结果 ID 关联与增量身份的责任清单完整，
重构不新增 UI 语言驱动识别的隐式耦合，默认中文功能保持原有关键回归。
下一语种实施时再以脱敏/合成样本验收：不同界面与输入语言组合、正式 ID/数值等价、歧义与缺资源、
布局差异、运行中改偏好/取消/账号切换、增量身份变更，以及耗时、内存和新增资源体积。
没有该语种样本、资源和结果证据时，状态只记为预备，不发布该语种识别能力。

### 6.3 版本更新 skill 与全局审查联动

[版本更新 skill](../../skills/nte-game-update/SKILL.md)覆盖只读解包差异、静态/图鉴候选、同版公共素材、
逐角色功能适配、验证及正式晋升。角色资料可见、面板、评分、战报与原生能力分别记录，不以导入成功替代功能适配。
各域重构时核对并维护 skill 的职责索引、真实构建参数和资源入口；公式、schema、版本数字与协议仍留在原有事实源。
技能只读审计脚本已提供，未来可直接传入解包目录；本轮不据此执行版本更新、静态晋升或增加新角色机制。
最终验收包括入口/引用/脚本验证和本机可调用副本；真实完整更新在新版本输入与对应授权到位后验收。

## 8. 验收、回退与文档收口

每批合并请求或本机记录说明四件事即可：改了哪个问题、有效消费者如何接管、怎样验证、怎样回退。
复用 Git diff、测试输出和现有文档，不为普通重命名另建多层报告系统。
涉及行为的迁移先确认关键公共保护点，优先复用有效用例；仅缺失关键验证时补最小测试，不为移动文件等量补测。
按用户授权执行专项、Ruff 硬门禁、精简后保留集合的 `core/full` 与性能测量。
未授权的测试、编译、部署、游戏操作和发布不执行；未运行项明确列出，不据静态阅读宣称通过。

重点验证按改动选择：

| 改动面 | 必要检查 |
| --- | --- |
| 启动/组合/生命周期 | 导入副作用、临时路径、账号切换、取消、关闭和迟到回调 |
| 配置/DAO/保存 | 草稿保留、旧库升级、事务失败回滚、保存冻结预览而非最新状态 |
| 分配/组件适配 | 身份与能力不匹配、畸形响应、UID 冲突、超时、取消，无生产回退 |
| 框架与代码收敛 | 至少两类真实用例接入；规则与 owner 唯一，旧补丁链和无意义包装已移除 |
| 中文关键注释 | 新增/迁移/保留模块关键流程均覆盖；说明符合代码，技术标识和第三方原文保持 |
| 页面/性能/语言 | 低配持续响应、资源有界、结果一致、键盘可用、三主题与混合 DPI；外观修复有依据 |
| 发行瘦身 | 同输入 EXE/安装包/完整目录/安装占用对比，必要依赖与素材完整，冷启动/内存/临时解包不显著恶化，升级与回退有效 |
| 删除代码/资源 | 所有静态和动态消费者、脚本、测试、打包清单，历史数据升级仍有效；代码量按统一口径拆分 |
| 目录模块化 | 领域包与责任清单对应；业务文件归组，全部引用迁移，旧路径与重导出壳清除；目录重排不产生导入副作用或循环 |
| 测试精简 | 非关键用例和无消费者夹具确实删除，重复保护合并；保留关键集合的发现、失败传播与覆盖可核对，删测与缺陷修复分别记结论 |

测试体系本身也要验收：将保留的关键保护点与质量入口实际发现集合对照；删除类别和领域结论按第 4.7 节简述。
运行数增加或标记了 `core` 都不自动证明覆盖；发现错误、子进程失败和前置条件缺失应成为可见结果。
本轮新增回归按真实根因处理；既有失败按[第 4.7 节](#47-随全仓审查主动删减测试)的暂挂边界执行，
历史存在只说明基线，并不构成推广未验证框架的通行证。

对有数据风险的改动使用隔离副本；SQLite 活库只用一致性备份，不复制活动 WAL/SHM。
回退只触及本批文件并检查后续改动；不全仓强制重置。数据迁移仅追加，已发布语义保持；源码回退与数据库兼容分别核对，
不把“还原文件”当作撤销已经发生的数据或外部操作。

完成一批后，把稳定结构更新到 [architecture.md](../architecture.md)，已验收行为更新到
[features.md](../features.md) 或对应专题，协议及组件约束更新到 [integrations.md](../integrations.md)。
本方案只留剩余目标和必要决定，不积累执行流水账。开发命令与资源前置集中在开发文档入口。

全项目完成的判断是：生产与测试领域审查无遗漏，框架缺口已补且由真实业务使用，全部计划消费者迁移、相关补丁合并，
