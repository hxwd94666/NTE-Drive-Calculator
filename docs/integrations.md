# 外部集成与扩展

本文说明外部能力进入项目时的边界。业务所有权与生命周期见 [系统架构](architecture.md)，真实环境步骤
见 [Windows 验收](validation/windows.md)。

## 1. nte-core

交付的采集 Core 内置其资源清单中的基础 JSON 数据，不依赖开发仓库的 `res/` 目录或启动工作目录。
组件冒烟验证须将 Core 放入独立目录再启动，避免从可执行文件的父目录意外读取开发资源。
缺少必需资源的启动失败显示为采集组件缺失，不能只显示标准输出关闭。

`src/integrations/nte_core.py` 负责 stdio 协议、进程、事件和错误适配，不负责评分、配装或 UI。当前产品
使用的能力包括：

- `capture.detect`；
- `capture.start(profile="inventory"|"combat")` 与 `capture.stop`；
- `inventory.get_latest`；
- 仓库状态写回与极速装配 RPC；
- `event.battle.summary`、`battle.get_summary`、`battle.get_record`、`battle.get_axis`、`battle.reset`。

`inventory.get_latest` 读取最近捕获结果，不等于强制刷新。完整库存事件进入快照稳定化；残缺状态事件只
更新固定完整快照中的已知 UID。RPC 接受只代表已提交，最终状态由后续稳定快照或正式范围事件确认。

设置页的 nte-core 抓包诊断只调用 `capture.detect`，并以 Windows 只读探测补充 Npcap 驱动服务、已启用
适配器、Npcap 安装痕迹和常见 `wpcap.dll`/`Packet.dll` 位置的摘要。它不创建抓包会话，不读写网络配置，
不输出 MAC、IP、远端地址、完整本机路径或核心 capability 清单。`capture.detect` 返回零设备时，报告按
安装缺失、驱动服务、无活动网卡或“驱动/过滤器/运行时待排查”给出下一步；核心没有提供 libpcap 枚举错误
文本或逐网卡过滤理由时，报告必须明确该边界，不能伪造原因。
抓包默认交由 nte-core 自动选择网卡；设置页仍保留手动网卡字段供明确排障使用。诊断仅在未获得自动推荐且
存在候选设备时提供二次确认后的高级入口，选择结果先填入设置，保存后才会影响后续 capture 会话。

新采集要求 nte-core battle contract v5；旧 v4 及更早战报只保证可查看，不补写新字段，也不承诺按 v5
重新校准。v4 继续保留逐击 `overkill_damage`，并新增结构化 `max_hp_reduction`。正数表示 Core 已对该来源逐击完成生命
上限扣减校准；零值只表示 Core 没有为该击生成结构化修正，不证明所有尚未注册语义的机制都没有发生。
应用不得恢复全局样本猜测，只能按[战报功能契约](features.md#9-战报)列出的已审计机制做窄回退。record ID 在当前 Core 进程内稳定，
generation、cursor、sequence 和总数按十进制字符串保留；axis 每页限制 1～500 行。逐击页携带 generation，
应用在停止采集后从空 cursor 重读，并逐页核对 generation、record ID、`finalized` 与 `complete`；Core 不额外
提供逐击来源或校准状态推断标签。

`overkill_damage` 只对应 primary `damage`，不包含追击；应用校验它不大于主伤害。Core 的
`Server settlement residual` 行以未知角色返回；应用把
非正角色 ID 或 `character_known=false` 统一投影为未归因，保留其有效伤害但不生成角色养成快照。
应用在采集期间轮询并暂存逐击，以免 Core 的 50,000 击保留窗口裁剪前缀；这些页不是最终事实。停止采集后
固定最终 record generation `G`，从空 cursor 重读完整轴，要求每页均为 `G`，在账号库事务中替换本场暂存轴，
再复核 record 仍为 `G` 后完成战报。`capture.stop` 返回后 Core 已排空并冻结记录，因此任一步发生代次变化、
cursor 过期或完整性不满足时直接把本场标记为不完整，不对同一冻结状态做无意义重试；仍不
稳定时保存为 incomplete 并记录安全原因，绝不混合代次。逐击只保存
Core 已脱敏字段，战报数据库不保存网络包、端点或 PCAP。设置页显式启用账号级原始抓包后，库存与战报
启动时会冻结该设置，并由 Core 把 `.pcapng` 独立写入当前账号日志目录；这些文件不属于业务数据，不随战报
历史读取、导出或数据库迁移。

`battle.get_summary.max_hp_reduction` 是与 `total_damage` 分离的原始削减量聚合值，只随原始 summary JSON
保留供逐击合计审计，不新增页面业务指标、不单独投影为历史字段，也不进入伤害、DPS、角色贡献或生命上限
结算公式。抓包来源的正式生命上限结算消费最终完整轴的逐击 `max_hp_reduction`；DLL 来源由独立分析核心
核对完整结算分量、生命与上限采样阶段，再生成独立派生结算。具体数值与置信度见
[生命上限结算](reference/damage-calculation.md#战报最大生命下降结算)，不把原始上限变化直接当成实际伤害。
每场采集在握手后冻结 `core_version`、协商协议、数据版本和 nte-core EXE SHA-256，并随战报持久化；同为
battle contract v5 但 Core 构建不同的记录不得仅凭 contract version 视为同一解析语义。原始
summary 和逐击 JSON 保持 Core 返回值；对照采集仅在保存的 record 顶层增加独立的
`calc_capture` 元数据，记录 `comparison_id` 和已核对的 `source=native|packet`，不修改 Core 的原有字段。

v5 为每个 `time_stop_intervals` 元素新增 `pause_type_mask`。新近保留区间携带非零 u32 mask，并在 mask
变化处精确切段；Core 为控制内存而生成的压缩历史区间以 `null` 明确表示类型未知。应用把所有完整区间的
并集用于有效时长和 DPS 扣除，但 Q 动作锚定只消费 mask 的 type2/type3/type4 位；type6 不得拉长 Q，
只作为灵可 E/QTE 派生推论的辅助旁证，不能单独证明 E 或同频触发。旧 v4 记录缺少 mask 时保持既有 Q
锚定兼容并明确标为旧类型未知；完整 E 与唯一后续同目标队友 QTE 另可形成低置信选人暂停回退。该回退从
E 第四段末击到 QTE 静态动作起点，静态起点不可用或不晚于 E4 时退到 QTE 首击；只有正区间才参与有效
时钟，且不会成为 Q 锚定证据。
v5 的 `null` 压缩区间不会伪装成 Q 或 type6。

战报和背包同步按已确认的[工作模式](reference/work-modes.md)选择来源；原生来源使用
`serve-native --stdio --game-pid`，抓包来源使用抓包入口。原生端点缺失、被占用、握手失败或中途断开均不切换来源。
独立 `NTE_Capture.dll` 由现有代理或注入插件从配套工作区正常加载，启动 DLL
不等于开始战斗采集；只有 `capture.start` 才开始记录。DLL 进程期驻留，更新后需重启游戏。
原生启动被明确拒绝为 `not_ready` 时，Calc 只按该响应中的固定原因判断：初始化、游戏线程或角色/场景
尚未就绪可在同一 worker 内持续等待，首次启动与场景续录均不设总等待时限，可随时取消。每次明确拒绝后
等待 0.5 秒再尝试，已发出的请求仍遵守单次 RPC 超时。SDK、Hook
明确失败及未知原因立即显示中文诊断，不重连、不切换来源。取消等待不保存空报告。
场景类型和采集就绪相互独立；场景未知不等于不能采集。通信字段由组件维护仓库的协议文档定义，本仓库
只维护消费行为和固定组件清单，不携带私有 DLL 源码、SDK 或其实现规范。

显式启用“同时抓包对照”时，Calc 为 DLL 和抓包分别创建采集进程、operation ID 与保存服务，两路原始
逐击和摘要各自保存，不合并计数或按相近时间强行配对。DLL 路必须连接原生端点，缺失不得降级为第二路
抓包。首次与续录均等待原生路进入运行态后才启动抓包，避免 DLL 初始化等待期间单独产生抓包战报。
两份 record 的 `calc_capture.comparison_id` 相同，但各自 operation ID、原始逐击和来源独立。
对照模式缺少最终 record 时本路明确失败，成功的另一路仍保留；不生成无法追溯配对的退化摘要。
一次停止会通知两路；一路意外终止或失败会停止另一方，待双方收尾后才恢复背包同步。页面显示各自记录
编号；切换历史后即时面板清空，已保存的配对标识继续保留，后续对比不依赖时间相近的猜测。

原生组件明确报告 `scene_transition` 时，Calc 先收尾旧场：造成伤害大于零则保存，否则丢弃前置空场。
双路在同一边界收尾；双方终态成功后才创建下一对 operation ID，继续暂停背包同步。原生路在现有 worker
内按上述规则持续等待明确的临时未就绪状态恢复，新场开始要求角色可操作；抓包对照等待原生路进入运行态后再启动，加载
过程不提前成为下一份抓包战报。手动停止、退出、账号代次失效或真实错误均阻止自动续录。`source_changed`
仍是不可续录的异常原因，不靠中文提示或任意失败重试来分场。

轨外正常上下半属于同一份战报，原生路消费正式玩法阶段事件并复用抓包 Core 的半场统计；正常换半保留
两半，重开/换层沿用 stdio 抓包的半场重置规则，原始全轴不伪装成最终两半合计。未观测到正式阶段时保留
半场未知，不以世界名称、角色名单或副本难度猜半场与楼层。加载期间的旧对象不可用于新场景逐击。

两路都请求扣除停表，并各自展示实际返回的计时方式和首末击时长；模式不同时不计算 DPS 百分差。
相同计时模式也不代表完全相同采集窗口，DPS 差异需要同时核对总伤与时长。原生采集复用既有
`combat-clock` 插件的时停变化及区间规则；时钟不可用、区间缺口等必须保留未知或不完整标记，不能
把恢复连接当作整场完整。双路同时采集的游戏内覆盖、时序及性能仍需实机验收。

### DLL 原始快照排错保存

Core 声明 `native_snapshot_inline_raw_v1` 时，背包与角色正式分页同时携带同页原始记录。自动同步与战报准备
复用这一轮分页建立当前基线，仍校验原始行数、游标、身份和大小预算；残缺证据不提交。
战报只取已装备物品和队伍面板，独立保存后不再依赖整个背包的版本或历史快照存续；角色面板连续性只消费
角色与队伍证据，环境由目标计算独立处理。编辑和边际共用当前稳定背包候选入口，打开页面时冻结本次候选池。
未声明该能力的固定旧组件沿用独立原始分页。原始记录仅进入内存基线和已授权的排错归档，账号同步只保存正式字段，
战报只冻结其队伍子集。正式映射失败仍可读取原始证据用于排错。

账号设置“保存原始采集数据”同时控制抓包 PCAP 和 DLL 原始快照。Core 声明 `native_snapshot_archive_v1`，
启动取消检查只在获得战报租约到采集成功前生效；采集成功后，正常停止使用采集服务自己的停止信号取消配置读取，继续读取最终逐击并保存。账号和模式约束继续核对，不能将正常停止意图当作启动取消而丢弃已接受的命中。

Calc 在共享原生连接核对时通过 `native.diagnostics.configure {enabled: bool}` 应用当前诊断授权和账号设置；
未开启时不创建快照文件。该控制只作用于 Core 本机归档，不改变 DLL 的采集开关。

启用后，Core 在原始响应校验和业务投影之前保存实际请求到的 `character`、`inventory`、`team`、`environment`
域请求、状态、refresh 元数据及原始分页，并关联转换错误；失败和不完整响应也保留。它不额外触发游戏扫描，
未请求到的域或页不标为已保存，也不将部分观察当完整库存。原始内容保留在账号
`logs/nte_core/raw_capture/native_snapshots/native-snapshots-*.jsonl`，不写普通日志、账号导出或战报导出。
每行含 schema、序列、本机微秒时间、方向和原始消息。按 64 MiB 分卷，保留最近五份；单条消息不拆分。
磁盘写入失败报告固定诊断错误并停止本次原始归档，不把已写文件标为完整，不因归档失败改变原始业务观测。

### 原生逐击证据与分析优先级

原生 `contextEvents` 原样保留公共事件信封、自然计算观察、只读补查询及属性观测。Core 只校验传输版本、
编号、时间和预算，不维护计算机制白名单；Calc 保存未知事件及其 payload，不在 Python 中解释或计算。
`supplemental_readonly_query` 表示 DLL 在记录的时间调用已审查的游戏只读方法，不等于原伤害执行。
查询基础值、聚合属性观测和已应用修正分别解释；不能把基础值直接当作 Buff 收益，也不能将战后查询回填到历史逐击。
当前组件增加上述取证能力，现有分析公式不会因保存了新字段而自动改变；逐击消费与反事实关联由独立分析组件核实。

增强采集通过同一摘要、record、axis 查询契约保存。每行 `native_capture` 保留 provider/capture/hit 身份与
完整 `rawHit`，sequence 沿用 DLL 原生 hitId，不重新编号；该编号只在对应 capture 内有效。
`rawHit.hitObservedUnixUs` 与 `settlementObservedUnixUs` 分别保留命中来源回调和结算回调的本机观测时间，
为十进制微秒字符串或 null；旧记录缺失时不补造。轴时间仍使用 `unixUs`，不按新字段重排或改写伤害。
来源回调通过原生身份关联到结算逐击，不额外生成零伤害行；这两个时点均不等于已确认的服务器执行时间。
增强战斗采集自动将 DLL 的紧凑原始回调与关联诊断保存到当前账号的 `logs/nte_core/raw_capture`，双路对照时
同样保存；该文件独立于战报内的最终 `rawHit`，用于追查未关联技能等缺口。
战报 `native_capture` 保留原始文件位置及写入完整性、计数和失败原因；写入完整不代表已覆盖所有游戏伤害入口。
原始文件属于账号私有诊断数据，不随组件交付或战报导出打包；导出副本移除本机原始文件路径，保留原生逐击、
采集计数与完整性证据，不修改本机原始记录。普通日志不记录其 payload 或绝对路径。
独立结算分量各占一击，伤害不再重复折叠为主击的追加值；正式显示类型优先用于覆纹等分量分类。
技能键使用正式 GA 标识，对象弱引用仅保留在原始证据。分析端只有核对同场精确结算身份后才能把独立覆纹
关联到主击；缺失或有歧义时保留未知，不把主击 GE 的倍率套给覆纹，也不改写历史原始记录。
采集 DLL 只提供原始观测、有效性和原生逐击关联；GE 类名与实际 Ability/统计源键可以独立存在，缺少技能键
不应丢弃 GE。静态技能映射、展示名称、业务伤害分类和 Buff 收益由消费端分析与展示，不要求 DLL 实时映射。
派生结果与 `rawHit` 分离，不能因 GE 可识别就把未知暴击、元素或 Buff 生效关系升级为实测事实。
`rawHit.executionEvidence` 保存能精确绑定到本击的执行前输入和执行后输出。DLL 只冻结原始值、
对象身份、采样阶段和读取状态；Core 原样传输，独立分析组件负责静态解释、伤害重放与反事实，
Calc 负责持久化、导入导出和只读展示，不在采集或 UI 层复算伤害。该对象随原始逐击保存，
不依赖外置诊断文件；缺失、空数组、读取失败与截断分别保留。当前接口支持 schemaVersion 1，
更高版本原文保留但不解释。逐击详情将动态属性、公式乘区与实际贡献分为独立弹窗，技术明细默认收起。
`rawHit.attackerAttributes` / `victimAttributes` 保存对应对象的动态属性及读取状态；
`executionEvidence.applicationEvidence.items` 保存已观察到的成功修正写入，`baseTerms` 保存客户端基础项
取值路径和返回值。属性写入、相对于面板的包含关系与服务器公式消费分别保留证据状态；不能把客户端读取
值当作服务器完整输入。分析组件先采用有效观测，再按公共属性规则补齐缺项，并标明首选推断。
原场观测基准及贡献解释在一次准备时冻结，逐击重放和反事实共用，候选变化不覆盖原始证据。
Spec 修正项、属性捕获定义和标签只证明执行时存在这些输入；未观测的属性求值、条件过滤与来源链
仍为未知，不能把这些数组解释成“本击实际采用的全部加成”，也不能用执行输出覆盖正式结算伤害。
`nameResolution=identity_only` 表示标签和字段路径的 FName 仅保留本次运行索引；没有对应名称池映射时，
不能离线恢复标签名称或通过索引猜静态效果。已冻结的属性名 UTF-16 内容与这些索引分开保留。
玩家对象的正式配置 ID 随 `attackerCharacterId` / `victimCharacterId` 传递，Core 按伤害方向选择
对应玩家侧并核对角色目录；只有缺少该证据的造成伤害记录才沿用效果目录归属。显示名称不参与身份匹配。
无法归属正式角色的逐击及 Buff 原文仍保存，未知编号不进入正式角色清单和养成快照。
DLL 提前发出本场终止事件时，Calc 自动收尾并读取已保留的逐击；Core 对已验证终止的同场停止请求
返回原终止结果。非用户停止的原因在采集结束提示中展示，不把保留数据的成功保存等同于全场采集完整。
原生超杀与最大生命扣减未知时保留 null，不套用抓包的数值校准契约。当前 HP 与最大 HP 的采样阶段可能
不同，原始来源和采样时间随证据保存，不组合成同一结算前后的血量对。分析端仅在保存轴与原生传输完整、
目标结算分量完整且浮点生命端点精确闭合时量化削上限；唯一来源还须正式 GE、角色及五觉 Buff 等证据。
分析核心返回逐字段证据判定，Calc 主表与详情消费同一结果：有效原生暴击和元素优先于公式拟合与静态映射；
独立已知标志分别校验，未知不变成未暴击或默认元素。正式覆纹分量的暴击显示不适用；公式无法重放不抹去
已观测暴击。缺少直接证据时保留静态映射或推断来源与置信度，不把拟合接近视为运行时实测。

Buff 状态只在对象身份、逐击采样时间、阶段和效果定义能核对时参与对应逐击的状态审计；来源侧不能借给另一公式面板角色。
目标 Buff 区间的 `scope_half` 随页面响应保留半场归属；旧区间未提供时为空，不能据此补造半场。
旧战报的快照内容版本时间与本击效果读取时间分别保留。结算时才读取的效果列表不充当较早命中的状态证据；旧记录缺少
独立采样时间时不补造。完整空列表只证明本次枚举无条目，不能否定已消耗或瞬时效果曾参与本击；未证明该效果
在此阶段应仍可枚举时，保留状态缺口。当前回调快照既可能包含本击新增的层数，也可能已丢失本击消耗的效果，
因此一般效果只展示回调观测层数和抑制状态，不直接替换公式采用层数，不因空列表禁用推断。
已审计的单层持续增攻（早雾大招、莫非克斯、效率套装与安魂曲偷取攻击力）在同一提供方、角色对象与效果实例的
前后命中观测一致时，允许以中置信度延续推断区间；新实例、变化、抑制、缺失或不完整观测均不作该覆盖。
安魂曲偷取攻击力只消费原生已求值 Spec 的单项 AtkAdd，旧记录缺值保留未知；配装或状态改变后，不能用本场
观测标量认定自定义计算后的完整收益。该旁证仍不等同执行前状态。其他效果的状态、静态 Modifier 数值与公式消费分别审计。

axis 的 complete 只说明本次已接纳逐击的传输与保存完整性；record.native_capture 单独保留 DLL 的
complete、sourceCoverage 和 integrityReasons。试用采集尚未验证完整游戏伤害覆盖及停表，分析不得因为
分页接收成功就宣称这些来源完整。旧战报的 Buff 快照只证明实际读取到的效果列表，不能据此认定每项效果实际贡献
了伤害；缺失和完整空列表仍分别保留。新逐击不携带角色身上的效果存在列表，实际写入贡献与规则推断分开。

声明 `combat.effects.v1` 的原生组件通过独立连续序号发送 Buff 生命周期回调；配套 Core
以 `native_buff_events_v1` 声明接收能力，并将原文保存到 `record.native_capture.buffEvents`。
采集结束核对最终事件数量，事件缺失不能标记为传输完整。实例身份、受益对象、层数、时间更新、移除与
定义叠层策略保留原始证据。新 DLL 在首次观察对象时初始化内部效果基线，不运行 100ms Buff 扫描，也不把
初始存在列表作为逐击应用贡献传输。旧战报已有初始状态或逐击快照时，仍保留实际观测边界，不能倒填到更早命中
或自动覆盖回调时序。

分析组件的 `engine_report_v2` 是独立诊断入口，冻结账号库、静态库、战报 ID 与面板来源 ID，只读加载
上述事件和原始逐击，在 Rust 内准备生命周期并重放。默认消费同场冻结面板；显式指定其他战报面板仅适用于
已确认配装未变的验证。开发命令为 `tools/battle_report/replay_native_evidence.ps1`。结果保留跳过原因、
模型缺口和部分数值误差；当前主页面仍使用既有 `battle_page_v1`，诊断接通不代表角色模型或反事实完整替换。

`team_snapshot_id` 当前仍为空；完整 Buff 生命周期区间与全场采集完整性仍需实机验收。
配套工作区同时包含采集 DLL、协议与哈希清单及许可通知；构建、安装包核对与工作区部署均验证清单。

### 1.1 nte-analysis-core

`nte-analysis-core.exe` 是独立 Rust 分析组件，与采集用 `nte-core.exe` 分别构建、部署和管理进程。
它不链接或启动采集 Core，不接入游戏、抓包或网络。正式战报页面消费组件声明的 `battle_page_v1` 能力；
只更新 Python 源码不会启用未部署的能力，能力缺失或版本、哈希不匹配必须报告组件错误。
总览、逐击、Buff 反事实、边际收益、装备副本比较及导出时的分析投影统一通过原生页面入口，缺失或失败均不回退旧计算。
旧 Python 页面、逐击、边际和副本比较方法已标记 `DEPRECATED`，仅保留离线差分用途；
`load_legacy_for_differential` 是显式旧入口，正式界面和导出不得调用。

整页协议使用 UTF-8 JSON stdin/stdout，一个页面请求由一个短期进程完成。请求冻结账号、generation、
战报编号、账号库与静态库路径、语义配置、分析范围、角色和用户候选，不传 Python 预计算的逐击或 Buff。
语义配置 `gameplay_effect_semantics.json` 只读取随应用发布的配置目录，不读取用户可写配置目录中的同名文件。
发行资源缺失时明确报告配套安装不完整，修复资源后可重试；不得以空规则继续分析。
Rust 核对账号库身份、静态 schema 和绑定的 dataset，以只读事务取得共享事实；账号库读取完后释放连接，
不让长计算持续占用账号 WAL。静态目录与规则缓存仅属于该请求，候选分别应用冻结编辑，不能追随活动配装
或在候选之间共享可变面板。公开规则声明由构建工具从正式静态来源生成并绑定 dataset，运行时不调用
Python builder；未识别的角色、机制和证据保留未知。

Rust 负责原始轴解析与来源配对、动作和时停投影、目标映射及拟合、面板与技能证据、角色及弧盘状态、
治疗和 Buff、完整逐击重放、构成、反事实比较及边际候选编排。响应同时提供页面分析、目标目录、候选
展示轴、边际收益和动态面板。非概览响应的 `hit_details` 使用 `interned_v1` 共享字符串、属性、决策与
投影表，按分析/候选、原始归属/公式来源及事件 ID 引用。Python 验证表索引和事件绑定，点击时只组合已有
只读对象与说明文案；详情缺失保留未生成，不回退计算 Buff 规则。
逐击与时间轴共用的原生证据只传一份：同一分析内，时间轴的 `native_evidence.reference_event_id`
指向 `hits` 中同一事件的完整证据。范围外或内容不同的证据保持内联，null 仍为未知；适配层还原后
页面消费原有只读领域对象，不修改缓存响应或原始战报。分析组件与解码适配层须配套部署。
反事实伤害构成及其角色、伤害条目按正式领域类型递归解码；不得把未校验的 JSON 字典直接交给页面绘制。
派生目标快照的兼容性由 payload schema、战报身份和静态 dataset 定义；算法版本由 Rust 原样提供并负责
缓存失效，页面不得要求它等于旧 Python 算法版本。推断准备过程的内部标记在 Rust 公共输出边界移除，
只把契约字段及原有依据说明传给页面。组件验收须覆盖页面解码和派生快照保存，不能只验证 EXE 输出成功。

同一协议的 `detail_level: editor` 是独立窄入口，只需冻结账号、generation、战报编号与账号库路径。
Rust 从最终逐击读取必要列，返回 `editor_facts` 中的角色推断事实和半场归属，不加载静态配置或运行整场重放。
Python 继续准备编辑器养成配置、库存候选和装备选择，并通过公共展示服务生成说明文案。

声明 `battle_page_identity_v1` 的组件支持 `detail_level: identity`，复用正式页面的只读事实加载，
仅返回有序输入的 SHA-256 摘要，不创建重放引擎。Python 以摘要、完整计算请求、账号代次、组件、静态库
及语义配置身份复用最多两份压缩原始响应，总压缩容量不超过 32 MiB；单份原始响应超过 64 MiB 不缓存。
缓存属于同一历史服务且切换战报清空，每次命中重新解码领域对象。冷计算前后输入摘要变化时取消结果，
失败与未完成响应不入缓存；未声明该能力的组件继续正常计算。单纯展示选择的持久化不会改变原生摘要，
目标推断快照等实际输入变化会使旧缓存失效。

声明 `battle_parallel_v1` 的组件可在独立进程内并行计算 Buff 移除组和空幕候选。数据库输入由 owner
准备，各 worker 独占可变投影状态，最后按原顺序组装完整结果，逐击浮点运算和求和顺序保持不变。
默认按可用 CPU、冻结的内存预算和任务规模选择最多四个 worker；低资源、无法查询内存或线程创建失败时
减少并发或串行。进度仍由 owner 按实际完成候选发送，取消仍结束整个独立分析进程。
`--threads auto|1|2|4` 仅供明确的性能对照；Python 不需要自行分发逐击或启动多个核心进程。

响应复核版本、dataset、账号、generation 和战报身份；取消或冻结上下文失效时结束并回收该分析进程，
不影响采集进程，也不把失败静默转成 Python 计算成功。账号及静态配置在返回和保存前再次校验。
声明 `battle_progress_v1` 的组件可通过 `--progress` 在 stderr 持续输出有界 NDJSON 阶段事件，
stdout 仍只返回一个完整页面结果。Buff 移除与空幕候选按实际完成项计数，其余阶段只报告阶段状态。
Python 在调用线程校验并转发进度，持续排空两条管道；进度与最终结果使用相同的取消和请求身份边界。
连续接收结果时按 100 ms 节奏核对取消与冻结输入，不按每个管道分片重复访问文件系统；进度回调及最终交付前仍立即核对。
Python 根据冻结请求包含的阶段，把核心事件映射为单调的整体工作量估算百分比；全部处理成功才发送 100%。
未声明进度能力的旧组件只能在开始、整理和成功时推进，不按耗时自动增长。事件不携带角色、账号或原始战报内容。
Rust 不写账号库；自动目标推断以完整版本化 `derived_snapshot` 返回，Python 通过既有 DAO 尽力保存，
相同结果跳过写入、用户确认条件优先，失败不丢弃已完成的页面结果。快照只属派生层，不改原始战报。

低层 `direct_v1`、`buff_projection_v1`、`buff_projection_plan_v1` 和 `battle_compute_v1` 继续用于
独立算法调用、旧组件边界与差分验证。投影保留半开时间边界、来源与目标标签、区间顺序、重复证据、
叠层覆盖和完整采用/排除决策；共享字符串与区间表只压缩传输，不降低机制覆盖或抽样。有效输入超出明确
工作量上限可按顺序拆批，其他协议错误直接上报。原 Python 算法作为差分依据，不能把它的编排耗时计作
整页原生入口耗时。

源码运行时组件位于 `third_party/analysis-core`，PyInstaller 内二进制与
`analysis-core-meta/component.json` 配套分发，加载前核对版本与 SHA-256。
`tools/counterfactual/package_rust_core.py` 收集独立产物、来源、许可和源码摘要，`--destination`
可先输出到隔离验证目录。缺失、损坏或能力不匹配的组件不能作为通过部署验收的版本。

差分工具只在冻结账号副本上验证，不改原始账号数据；覆盖完整结果、所有保留战报、范围、缺失输入、
用户候选、取消和派生恢复。性能分别记录原生内部计算、进程与传输、完整页面服务耗时，不以局部核倍率
代替端到端收益。无界面验证不包含 Qt 绘制、账号切换和实际交互，正式部署仍须完成
[Windows 验证](validation/windows.md)与组件升级、回滚检查。

## 2. 视觉、OCR 与游戏输入

`src/integrations/vision` 独占窗口坐标、截图、格位检测、鼠标动作和扫描后状态同步；`src/scanner` 与解析
Service 负责 OCR、归一化和装备字段。Integration 返回截图、索引、解析结果或诊断，不写业务快照，
不决定评分和保留规则。

鼠标与虚拟手柄全量扫描最终都提交为统一 `vision` 快照。游戏界面自动装配使用普通鼠标输入 contract；
页面不创建鼠标后端或虚拟手柄。

新增输入后端必须定义：窗口身份、物理像素坐标、前置页面、动作序列、可见后置状态、取消检查、输入
释放、超时和回滚。缺少后置确认时停止当前任务，不盲目补点。

## 3. 二进制与插件

根目录 `nte-core.exe`、`dwmapi.dll`、`nte-mod-loader.exe` 和插件副本是本机文件。`third_party` 只保存明确晋升的发行组件；
晋升前记录上游 commit、版本、许可和 SHA-256，并完成协议、打包和真实 Windows 验证。

本期原生组件采用采集 DLL 与最小 D3D 入口；可选 Loader 直接标准加载同一个采集 DLL。
采集默认不显示界面，可由 Calc 显式开启原生 Canvas 显示插件。
Toolkit 负责与 Core 成套核对后交付，Calc 不引入开发工具 UI、MCP、SDK 或内部构建明细。
旧 Mods 脚本链不再提供部署、加载、检测或打包入口，仅保留旧安装残留的单向清理。当前整包、加载入口、授权和清理的唯一契约见
[工作模式](reference/work-modes.md)与[组件包格式及生命周期](reference/game-component-bundle.md)。
游戏已加载的 DLL 需退出游戏后才能由 Calc 更新；Calc 不增加文件监视或热重载编排。
部署文件、加载管道、协议握手和业务快照分别检测，不以交付文件哈希证明游戏正在使用新版。
原生同步和战报共享同一个 Core 所有者，战报释放租约不关闭同步连接，停止超时可中止坏 Core。

### 原生显示插件

显示插件复用 `NativeGameSession` 和既有 Core 管道，不建立第二个采集连接。DLL 声明 `hud.configure.v1`，
配套 Core 才声明 `native_hud_v1`，将 `native.hud.configure` 转发为 `hud.configure`。
请求完整携带五个布尔字段：`cooldown`、`enemy_bars`、`ready_cue`、`hp`、`unbalance`。
响应 `options` 为完整位掩码，`installed` 表示 PostRender 入口已安装，`rejected` 表示入口校验不匹配。
接受配置不代表当前场景已有可显示对象。缺少能力时提示更新，不发送未知接口或开启第二个提供方。

生产 DLL 默认关闭插件；管道连接接管 HUD 后，断开时清除显示选项。现有工作模式观察线程负责应用偏好，
不新增轮询线程。HUD 控制不修改战报录制状态，录制中可独立切换。完全关闭后保留原生网关的透明转发，
不读游戏属性、不扫描 UI、不绘制；恢复时复用入口。实机验收分别检查两个开关、关闭后显示消失、Calc
退出和重连，以及录制期间切换和保存逐击。

正式背包同步要求 `inventory.snapshot.v1` 和 `native_inventory_dto_v1`；角色稀疏同步要求
`character.snapshot.v1` 和 `native_character_profile_v1`。读取先请求 `native.snapshot.refresh(domain)`，
再以同一快照调用 `native.inventory.page` 或 `native.character.page`，逐页核对冻结元数据和游标。
背包只接受完整 EQUIP 集合、完整角色引用与正式投影证明，复用既有稳定器及库存事务；原始 `complete`、
来源覆盖和变化覆盖原样保留，不将业务集合完整改写为原始全域完整。角色只提交已知等级和突破字段，
全批校验与最终取消检查在账号事务内完成；首次观测使用稀疏覆盖，不创建猜测的完整养成配置。
产品刷新及失败行为见[背包与角色状态同步](reference/work-modes.md#背包与角色状态同步)。
这些接口须由核对过的配套 Core 与 DLL 共同提供；源码、合成分页响应测试通过不能替代匹配二进制与实机验收。

Loader 由 Integration 使用既有 UAC、唯一 stop event 和 owner PID 管理，应用退出或用户停止时协作退出。
Integration 从所选 `HTGame.exe` 的安装根定位官方启动器，明确传入 launcher override，不依赖本地化卸载名称或固定盘符。
停止超时后禁止切换部署入口。可信同名 Loader 可以替换；标准加载按当前 EXE 与其内嵌 shim 的正式能力查询核验，
不以固定运行时 SHA 白名单阻断替换。详细参数、文件布局与失败重试规则由组件包契约维护。

### 插件发行基线与升级复核

发行组件的上游版本、提交、输入摘要、许可证、文件 SHA-256、公共签名、ABI 与协议必须进入组件来源记录。
升级或游戏更新后依次复核来源与依赖、正式能力、部署与清理、Loader 启动器和停止协作，以及目标业务的实机行为。
构建通过、组件交付和实机验收是独立状态；未验证的业务不得据此标为稳定。

## 4. 静态数据与资源

官方数据只通过 `tools/game_data` 生成候选静态库。已发布静态数据为 schema v31；待晋升的 schema v32 候选保存培养指南、推荐弧盘/属性/阶段、
技能说明、GameplayEffect 索引、怪物手册别名、装备 Modify/曲线，以及精确范围内的角色输入、技能效果引用、
关键效果属性和动画时间证据；同时保存敌方生命三段值、RogueLike 怪物/属性修正，并基于已导入 Blueprint
证据规范化 Buff/GE 的持续、周期、叠层、属性修正、事件触发及装备/弧盘/觉醒绑定；同时保存官方怪物图鉴、
材料/养成副本类目、难度、波次刷怪模板、高危委托及其逐难度怪物池、官方 Boss 支援模板成员、争锋赏宴和魔女赐福目录，以及限时奖励任务提供的轨外配置大陆服
生效区间，以及当前/下一配置的赛季名称、Buff 说明、正式 GE、数值曲线、已审计触发组成和怪物池官方本地化名称；
并保存人物逐级经验、突破阶段与成本、经验书规格及方斯消耗，并从弧盘精炼参数和对应的直接面板 Modifier 自动投影
唯一的无条件常驻属性；v31 发行库在运行时从相同规范化事实只读投影，v32 候选将其持久化。当前/下一轨外配置按构建日后的正式时间区间选取，不按 `AbyssID` 数字大小推断。导入器保留来源文件、
行键与摘要。版本更新先在 `build/` 完成候选构建和毕业模板重算，再由
`tools/game_data/promote_static_release.py` 显式读取仓库外本机配置，核对配置/数据库/manifest dataset、
当前 schema/importer、全部来源 SHA-256、payload 省略、外键、SQLite 完整性及最终报告后带回滚地晋升。
正式替换前使用同一工具的 `--finalize-only` 只在候选目录生成最终 manifest 与 JSON/Markdown 报告，再用
`--verify-only` 只读复核候选数据库、这些最终证据和全部官方来源；两步均不得接触 `data/`，预检不得
改写候选。
禁止直接构建到 `data/`、手工复制候选或只修改 manifest；晋升失败仍视为未完成。静态库和
`data/manifest.json` 作为同一次晋升产生的原子变更审查，改变规范化输出的 importer 修改必须递增版本。
解包后的 `Content` 目录只作为登记来源输入，不按目录做数据库全量覆盖；弧盘常驻属性由已规范化的
`fork_star_parameter`、精炼曲线、Buff Modifier、施加条件和标签证据重新投影。完整重建继续要求登记的
DataTable、本地化与 Blueprint 来源闭包；仅需验证解析器或更新 v32 候选投影时，维护工具
`tools/game_data/reproject_fork_permanent_properties.py` 必须从保留的规范化候选复制输出新文件，同时生成
逐弧盘审计，不能修改输入库或已发布 `data/`。
manifest 从 schema v30 起必须记录并严格核对 `database.size_bytes`；schema v29 旧清单仅在读取时按实际文件
大小校验并提示迁移。体积统一按 `1 MiB = 1,048,576 bytes`：95 MiB（99,614,720 bytes）默认阻断，只有完成
增量审计后可显式放行；96 MiB（100,663,296 bytes）是项目仓库绝对预算，100 MiB（104,857,600 bytes）是
GitHub 单文件永久硬边界。超过项目仓库预算时必须改为 Release 分发或拆分只读库，不能继续提交到 Git。
静态升级的增量报告必须单列本地化键和当前语言投影的字节贡献；发行库只保留这些必要投影，不导入完整多语言
原始 payload。`tools/release/prepare_release.py` 会再次核对安装包输入目录内静态库、游戏 UI 资源与各自
manifest 的文件集合、SHA-256 和精确字节数。

正式静态库重建前先原子备份上一发行库；推荐权重作为离线基线随候选生成，发布流程不访问工坊接口或读取
Key。主窗口首屏进入事件循环后延迟以无鉴权 GET 在后台获取公开权重；抓取、解析或网络失败均保留最近有效模板或离线基线。只有完整响应通过解析后，才以原子替换更新应用级模板，启动界面不等待该任务。
角色 1072 尚未实装或公开模板缺行时，使用 `tools/game_data/character_weight_overrides.json` 中的发行回退。
角色额外形状不继承旧库，直接由官方角色、底盘槽位和槽位属性修正三表关联导入。

游戏 UI 图片由资源构建工具生成到 `assets/game_ui`，`manifest.json` 明确记录 ID 映射、文件哈希和
`unresolved_assets`。角色头像来自正式角色目录；角色形象图只按 `DT_AppearanceData` 中 `IsDefault=true`
的 `CharacterID → SmallPortraitImg` 关系导入，并压缩为最大 512 px 的随程序资源，不靠文件名猜角色。
缺失资源保持显式 unresolved，不用相似图片或本机路径占位。

账号 schema 变化新增迁移并覆盖新建、升级、失败回滚和重试。DAO 独占 SQL；快照清理走公开 DAO 并
保护所有引用。

## 5. 新页面和公共组件

在 `src/features/<feature>/` 实现 Page/View 与 Controller，由 `src/ui/navigation.py` 注册导航，通过组合根
注入窄 dependencies。快捷入口使用导航 key，不使用堆叠页数字。跨功能复用先建立 Service、不可变 contract
或组合根公共组件，不经 MainWindow 字段和其他 Controller 转发。

## 6. 新算法、同步与装配方式

- 新算法复用官方 ID、固定快照、候选对象、配装槽位和保存方案 payload；输出包含真实 UID、目标位置、
  逐件评分、来源快照与算法/profile 版本。
- 多角色竞争由统一分配器处理，不用逐角色循环修改背包。
- 新同步方式提供等待、收集、完整性、稳定监听、单事务提交和明确错误状态；只提交完整快照。
- 新装配器只消费冻结的已保存方案，不在执行阶段重新优化；执行前校验来源、角色、槽位、UID 和位置，
  执行后产生可确认的新状态。
- 批量副作用使用持久任务、角色/槽位项和事件记录进度。
