### 0.1 原生完整性与业务验收

人物与配装、完整背包、队伍与环境三个逻辑模块共用 `NTE_Capture.dll`，对外分别提供 `character`、`inventory`、
`team`、`environment` 四个业务域。待验证各域在登录、换队、换装、场景切换及游戏重启后的真实能力、快照身份与
完整性，不能把已有逐击能力或接口声明视为四域全部可用。

完整原生库存尚需覆盖正式背包全集及未装备物品；`unknown`、`partial`、`complete=false` 或仅有已装备观察时，
不得写入正式库存、推进稳定快照或伪造 UID。人物养成和装备引用、队伍身份、场景/目标及世界等级等缺少直接证据的
字段继续保留未知。正式投影只同步已核实字段，不用抓包静默替代原生来源，也不修改历史战报的冻结事实。

通知修订与入场冻结的当前行为见[工作模式与本机生命周期](reference/work-modes.md)和[战报功能](features.md)。
共享基线、首击等待同修订与队伍证据裁剪仍需实机核对完整上下半场、半场重开、换队换装及账号切换。
仍需实机核对通知覆盖、连续换装和进出副本的修订时序，并测量回调和快照读取成本。场中变更后的多版本完整
快照、逐击版本绑定及分段重放尚未实现；此前统一计算配装保持缺失，不拿入场配置推算变化后的区间。

### 0.2 当前 Calc 整包交付

当前随附组件清单与整包校验契约见[组件包契约](reference/game-component-bundle.md#无界面采集链构建输入与发行映射)。
剩余交付验收是应用安装包、安装升级与真实游戏运行验证；组件候选目录通过核对不代表这些项目已完成。

上游源码合入、上游编译通过、候选 DLL/EXE 生成、Calc 配套组件晋升、实际游戏目录部署与 Windows 验收是不同状态。
源码接线和轻量专项不替代实际游戏验收，不将私有源码、SDK、PDB、账号数据或原始日志纳入公开组件。

### 0.3 抓包启动时序

当前等待能力支持等待游戏进程和网络条件，不能宣称已经在登录前完成监听。仍需实测早于启动、早于登录及晚于登录
启动 Calc/Core 时的网卡选择与首个完整包时序；如需保证登录前监听，须由 Core 进一步提供并验证相应能力。
进程出现或等待结束均不证明已捕获完整登录数据；错过完整包时保留旧稳定快照与原同步时间，不以增量补造完整集合。

### 0.4 Windows 与发布验收

按 [Windows 人工验证清单](validation/windows.md) 验证首次/旧版默认离线、确认取消、所有实际入口的模式门禁、
手动与自动两种加载方式、暂停和账号代次、DLL 原生共享会话、普通副本分场与轨外上下半场连续保存。
另须验证运行中降级的收尾、退出后的自动清理、未知/改写文件保护、Calc 重启后的待办恢复，以及 DLL/Loader 共存与性能。
没有实测完整库存时，验收结论必须明确保留这一缺口。

正式发布前另行完成已授权范围之外的发布门禁、安装升级与回滚验证；实际交付范围由目标版本、提交历史、构建输入和验证证据共同确认。
本节不构成全量测试、编译、打包、实机部署、提交或发布授权。

## 2. 队伍收益与全局配装

长期目标是把直伤边际、环合、倾陷、DOT、队伍增益和装备竞争统一到可解释目标函数，再扩展四人队与
八人双队搜索。新求解仍使用不可变快照、官方 ID、唯一 UID、配装槽位和冻结方案 contract，不建立第二套
评分事实源。

## 3. 倒带实机执行

倒带分析、八槽保存和输入链已接通，游戏执行仍处于实验状态：

- 启动前尚未识别并确认当前位于倒带首页；
- 坐标映射、余额/价格 OCR 和候选轮廓需要覆盖不同分辨率、DPI、语言与画面设置；
- 花费前尚未回显余额、十连价格和计划次数供最终确认；
- 页面内停止、阶段恢复和中断后的任务记录尚未形成；
- 账号 generation、执行快照与窗口身份尚未持久化为可复核任务。

当前公开策略只有“全面均衡”和“少角冲分”。领域层遗留的成本方案入口不进入 UI；增加策略前先确定
业务规则与公共行为测试。

## 4. 新版资源与未验证能力

CN1.4.2 独立角色目录已提供角色页预览与养成保存，已交付范围见 [功能文档](features.md#4-计算角色配置与自建角色)。
完整战报数据集仍保留原版本。同版本战斗 Blueprint、Buff 和 Montage 已有来源，完整库升级仍需补齐引用闭包，
并支持新轨外的参与者触发效果：`Abyss_11` 的导出可核对通用伤害加成与持续曲线，但环合参与者、施加时刻及
刷新区间尚需进入规范化协议和独立分析组件；不得将其作为全场常驻加成绕过赛季审计门禁。随后重新
验证技能绑定、精炼常驻效果、毕业模板、战报分析组件及真实游戏同步，不能用新 DataTable 与旧战斗资产拼接。
来源中缺少正式名称、基础/成长身份冲突或技能未完整公开的角色，待关系闭合后再开放编辑。

官方资源仍保留 `DT_AbyssCommanderConfig` 与 `DT_AbyssModifyPackData`，内容表现为部分角色担任某种
Commander 时给全队对应属性伤害 15%。当前尚未找到现行轨外 UI、关卡配置或战报字段对该机制的有效引用，
因此不把它导入为当前轨外 Buff，也不与预备备弧盘的“司令虎符”混同；只有取得现行玩法引用链或实机证据后
才建立静态目录和用户/运行时选择输入。

### 4.1 养成材料同步与计划持久化

养成计算器的当前单／多角色行为与最低体力算法分别见[工具功能](features.md#10-工具与游戏资料库)和
[养成体力规划](reference/progression-stamina-calculator.md)。尚未交付的只有材料库存同步及可选的跨会话计划保存：

- Core 需提供独立材料库存 DTO、完整性证明和账号 generation；Calc 仅在本次完整材料快照成立时填入已有材料。
  手工值与同步值保留来源，用户手工覆盖不被迟到同步改写；不得借用装备快照猜测材料数量。
- 若要保存计划，先增加账号库迁移及失败回滚，再保存冻结的目标、数据集身份和材料来源；在此之前计划仅属页面会话，
  不借用角色档案或装备背包表持久化。

## 5. 新能力验收原则

新能力先确定 payload、sequence/generation、完整性、错误码、隐私字段、失败状态和回滚方式，再进入
Integration 与账号库。路线图条目只有在实现、迁移、调用方收口和公共行为测试全部完成后才转为当前能力。

## 原生背包增量开发候选

独立采集候选恢复原全量读取节奏，支持在完整会话基线上按事件 UID 重读物品最终字段、复用未变化详情，
并以成员索引和关系复核派生新的完整快照。初始化、重连、事件缺失或不支持、队列溢出、根或身份变化、
校验失败重建基线；通知 Amount 不作加减运算。技能等级通知候选按 UID 重读对应角色的技能字段组，在完整基线上替换最终等级；其他角色事件仍保守重建。
技能通知不额外使库存失效，已识别材料的数量/移除事件可避免角色刷新。此专项路径仍待升级消耗实机验收。
此处并非直接把残缺事件提交为完整库存；旧稳定快照和历史方案保持不变。当前仍需对应组件实机完成新增、
部分消耗、完全删除、锁/弃置、强化、装卸、重连与帧时间验收，不能标为全类型事件增量同步已稳定交付。
