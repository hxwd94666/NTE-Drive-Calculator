# 养成体力规划

`ProgressionStaminaService` 将已知材料缺口和正式副本确定产出组合为最低体力方案。它是 Qt/SQLite 无关 Service：
页面或工具只投影输入和展示结果，不能复制鉴别等级、副本筛选或最短路算法。

工具页“养成计算器”与本 Service 的边界不同：工具页汇总角色、弧盘和技能的正式材料，不把材料猜成活力；
需要最低体力时，由调用方显式传入猎人等级和副本档位后调用本 Service。养成适配层只把正式材料副本可刷取项送入
体力请求：普通怪和世界 Boss 掉落物没有材料副本投影时直接留在材料清单，不参与体力完整性判断；方斯
不参与最低体力计算或“仅体力”材料范围。甲硬币 `Gold` 是可刷取材料，始终保留在“仅体力”范围；
需求扣除已有数量后，与同副本的正式确定产出合并求最低体力。若当前静态数据缺少甲硬币确定产出，
保留 `material_yield_unavailable` 缺口，不把未经核对的旧 `Fons` 掉落静默当作甲硬币。

主发行静态库已按已核对掉落闭包定点修复旧 importer 的 `gold` 误归并：145 条付费副本甲硬币产出与
角色突破、人物/弧盘经验材料成本均使用 `Gold`；玛门 `drop_fons1` 仍为 `Fons`。账号背包快照不做货币转换。
旧版独立图鉴目录如仍为已核对的旧 dataset/importer，计算服务保留只读兼容投影；其他数据集不套用。

## 冻结输入

一次请求包含：

1. 猎人等级（1–60）与可选生效鉴别等级；10/20/30/40/45/50/55 级对应鉴别 1–7，低于 10 级为 0；
2. 每种材料的正式 `item_id`、总需求和已持有数量；
3. 候选副本的稳定 ID、显示名、最低猎人/鉴别等级、单次体力与确定材料包；
4. 每个材料包的来源。

请求中的显式 `stages` 非空时优先于正式来源；为空时才读取注入的只读正式档位来源。Service 不自行打开数据库，
不读取页面控件或仓库外 JSON。随机、范围或缺失掉落不以均值进入精确规划；用户确认的档位可用
`source=user_supplied`，但必须保留来源标记。

## 算法与结果

先计算 `max(0, 需求 - 已持有)`，过滤当前等级不可进入的档位，再将每次副本的完整材料包作为整数动作求解。
Windows 正式环境在可重启的养成求解子进程内使用 SciPy MILP，先最小化体力，再在相同最低体力下最小化副本次数；
养成页面不在 GUI 进程加载该求解器。子进程原生异常、断连或超时使本次计算明确失败，下一次计算重建子进程，
不发布半成品结果。缺少该可选运行能力时保留原有
有界离散搜索。同一次掉落满足多种材料时只计一次体力，大额经验需求不按单位展开搜索状态。工具页对完整三档且在内置白名单内的材料使用相邻档 3:1 单向合成：先满足低档需求，剩余库存可逐档上合；整数规划把副本掉落与合成次数共同约束，低档掉落不足三件时可跨多次副本累积，不将同一件材料重复抵扣。没有 SciPy 时，有界精确搜索仍按同一合成规则检查终态。人物经验书 `CharacterUpMaterial` 与弧盘经验染剂 `WeaponUpMaterial` 使用独立经验值，始终不参与 3:1 换算；其他未列入白名单的物品也不根据名称猜测配方。

针对第三方输入法在应用进程内的原生异常，可在启动时添加 `--ime-compat`。入口在创建首个 Qt 窗口前调用
Windows 的进程级 IME 禁用接口；这是显式兼容选项，会停用本应用内中文输入，不修改系统输入法设置。
正常启动不改变输入法。该模式仍须按 Windows 清单用真实输入法和连续计算验收，不能以 Python 单元测试代替。

结果保留原生/生效鉴别等级、每种材料的需求/持有/缺口、档位次数与体力、已知最低体力、完整最低体力和稳定
gap code：

- `complete`：全部缺口有确定产出，`total_stamina` 为精确最低值；无缺口时为 0。
- `partial`：只计算已闭合部分，显示 `known_stamina`，总量保持 unavailable。
- `unavailable`：没有可用确定产出，或搜索触及保护上限。

## 正式静态档位

`clone_activity_difficulty`、`clone_drop_projection` 与 `clone_drop_projection_item` 提供只读档位。
稳定 ID 为 `clone_id:difficulty_ordinal`；`team_level` 投影最低猎人等级，`difficulty_level` 投影最低鉴别等级，
体力读取 `stamina_cost`。

只有确定正整数掉落进入 `FarmingStage`。`name_missing` 不否定已闭合的正式物品 ID 与数量；
`drop_group_missing`、`sequence_branch_divergent` 及其他非名称 gap 会令该档位退出确定集合。缺少正式来源时结果必须
保留 `partial/unavailable`，不得由中文说明、概率、上下限、经验值或外部解包文件推算。

当前发行静态库保留上述正式副本、单次活力和确定掉落投影；调用方只使用其已核验的只读 schema，
不从抓包装备快照或中文说明推算材料持有量与掉落效率。

## 多角色合并与已有材料分配

多角色请求在开始时一次冻结账号、generation、dataset、页面顺序、每个角色的人物／技能／弧盘目标、公共猎人／
鉴别等级及已有材料；每行使用稳定 `line_id`，业务关联仍使用正式角色、弧盘、技能和物品 ID。相同角色只能出现
一次，但没有人为角色数量上限。`CultivationBatchPlannerService` 逐角色调用唯一的材料规划 Service，按
`line_id → 模块 → item_id` 保留来源账本，再按正式 `item_id` 合并需求；页面和 Controller 不复制公式。

已有材料按页面稳定顺序只分配一次，同一模块先满足低档，再对内置白名单按 3:1 单向上合。合计“仍需”对合并
需求独立抵扣，不把不同档位原始件数直接相减；人物经验书和弧盘经验染剂不参与合成。逐角色体力是其获分配
后的解释值；**跨角色最低体力**对合并缺口只求解一次，同副本多材料掉落只计一次，不能用逐角色体力求和冒充。
部分或缺失掉落分别保留 `partial/unavailable` 与具体 gap。

结果回调、复制及任何持久化动作前复核冻结身份；过期请求静默丢弃。同一时间只运行一个求解任务，取消或
子进程故障不发布半成品。目标变化可以提交新请求，已有材料编辑仅使结果过期，必须由用户点击“重新计算”
才重新求解。材料库存同步及跨会话保存仍属[路线图](../roadmap.md#41-养成材料同步与计划持久化)。
