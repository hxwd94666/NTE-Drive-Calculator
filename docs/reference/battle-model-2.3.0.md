# 2.3.0 分析核心迁移与产品验收

状态：设计待实施。当前随附分析组件继续使用冻结的既有引擎；组件基线记录见
[`third_party/baseline-2.3.0.json`](../../third_party/baseline-2.3.0.json)。分支名不代表正式发布版本。

## 职责与产品行为

独立私有分析核心设计、计算并解释规则与反事实；Calc 负责账号、场景副本、静态数据晋升、进程、展示和结果保存。
UETools 生产采集 DLL，采集 Core 提供正式原始证据。分析重构不把 Rust 源码迁入 Calc，不复制规则到 UI。

未来新角色/弧盘的数据只使用已支持的属性、曲线、公式和效果操作时，应通过更新静态库获得计算能力。
遇到新机制允许只计算已支持部分，同时明确显示缺口；不能把未识别被动、未知倍率或状态默认为零/一后显示完整预测。
专用精确规则只覆盖对应行为，并保留适用版本、来源与验证依据；新旧规则不得重复加成。

实际重放、换装备、改养成/觉醒、移除效果和边际共用同一计算链。来源面板改变时重新计算依赖它的队伍增益，
移除来源后不得借用原战报中该来源的已求值效果。主页面的实测逐击、伤害、时间与 DPS 不随候选变化。
固定轴反事实继续以实际逐击为基础，不模拟换配置后的操作循环或提前击杀；超杀不截断其原始逐击权重。

## 质量与验收

计算结果分别说明可用性、机制覆盖、证据来源和验证程度；采集来源的“完整/部分”不替代计算准确度。
原场未校正预测用于残差；按实际伤害加权的候选收益另行展示，不能当作原场公式准确度。
历史差分同时报告解析成功、可计算条数/伤害覆盖率、同一集合的加权绝对误差、逐击误差分布和未量化项。
分角色、技能、伤害类型和半场检查，不能通过删掉高误差样本或减少计算覆盖达标。

完整输入的正常组先以残差低于 10% 为阶段目标；有充分机制和输入证据的样本追求取整后零差异。
旧数据未知与推断必须保留。真实残差降低不能替代无干预等价、移除来源、队伍依赖和候选暴击政策的专项验算。

## 切换条件

冻结旧源码和组件作离线对照；新实现首先通过独立验证入口运行，不新增永久 UI 引擎选择。
现有必需伤害类型、逐击解释、Buff/装备/觉醒反事实、单位边际、上下半场和取消能力全部覆盖后，
才迁移正式组件协议与缓存版本。账号库迁移只增加必要结构，不改原始战报或已发布迁移。
旧入口在新链路验收后删除，Git 历史及差分工具保留。正式交付仍需组件核对、性能测量和 Windows 实机验收。
