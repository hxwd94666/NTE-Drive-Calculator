# 游戏组件整包与清理契约

本期采用最小 D3D 采集入口，同时保留可选 Loader；两者加载同一个无界面采集 DLL，Calc 通过配套 Core 统一消费业务接口。Calc 不承载开发工具界面、MCP 或热重载编排。

本契约定义本机应用级组件检查与清理；管道、协议握手、人物/配装、完整背包、队伍/环境及战报业务能力须另行检测。
文件检查成功不代表组件已加载，Loader 停止不代表游戏进程内 DLL 已卸载。

## 随附组件清单

自动管理仅消费当前 Calc 的 `component-bundle.json`。源码布局在
`third_party/mods-plugin/component-bundle.json`（旧脚本链）或 `third_party/native-capture/component-bundle.json`（无界面采集链），发行布局在应用资源根目录；所有清单文件路径相对当前应用资源根目录。
PyInstaller 发行的资源根目录为 `_internal`，与主 EXE 所在目录不同；发行清单须使用该布局内的路径。
缺少清单、来源声明、配套文件或哈希不符时，自动管理不可用，不追随外部仓库或其他安装的文件。

清单为 UTF-8 JSON 对象：

| 字段 | 契约 |
| --- | --- |
| `protocol_version` | 整数 `1`。 |
| `source_commits` | 非空的公开组件标识至来源提交十六进制摘要的映射。 |
| `files` | 根目录内 POSIX 相对文件路径至 SHA-256 的映射；检查全部声明文件。 |
| `roles` | 组件语义至 `files` 中确切路径的映射。 |

未声明 `layout` 或显式声明 `legacy-mods-v1` 时保留旧脚本链契约，必需角色为 `proxy`、`loader`、`core`、`equipment_mod`、`combat_clock_mod`、`workspace_version`、`enabled`、
`native_capture`、`native_manifest`、`native_license`、`native_notices`。
三个逻辑 Mod 共用 `native_capture` 指向的 `NTE_Capture.dll`；业务域与完整性定义见[工作模式契约](work-modes.md)。
所有声明角色必须分别对应文件；路径不得越界、使用绝对路径或重复键。独立采集 DLL 还须通过其配套
`native-capture.json` 的协议、能力和哈希校验。清单不替代来源与许可证审核，也不证明实机验收通过。

此清单格式已实现检查入口；当前发行组件是否提供清单，以实际检测结果为准。

## 无界面采集组件清单

`layout: "native-capture-v1"` 选择无界面采集链。必需角色为 `host`、`capture_plugin`、`core`、
`capture_license`、`capture_source`、`core_license`、`core_source`；每个角色绑定不同的声明文件。
`host` 仅表示最小 D3D 转发入口，不是开发工具宿主；`capture_plugin` 是同目录的 `NTE_Capture.dll`。
源提交须包含 `capture` 和 `core`，`input_digests` 精确包含这两个输入集合的 64 位 SHA-256 摘要。
`file_sizes` 对全部 `files` 路径声明字节数；程序、许可与公开来源声明逐项核对大小和哈希。

可选 `upgrade_from` 声明可自动替换的已核实旧版本：键只能是游戏目录的 `d3d12.dll` 或 `NTE_Capture.dll`，
值为非空、无重复的 SHA-256 列表。名单只收录已核对来源的确切旧组件，不使用文件名、大小、版本文本或二进制标记
推断归属。缺少该字段的旧清单仍有效，但不授予额外接管权限。发行映射必须保留该名单。

`capture_protocol_version` 为整数 `1`。`capabilities` 是无重复的字符串列表，至少包含
`combat.hit_buff.v1`、`character.snapshot.v1`、`inventory.snapshot.v1`、`team.snapshot.v1`、`environment.snapshot.v1`。
额外能力只有在清单明确声明时才作为文件声明事实保留；运行时仍须核对 Core 握手及业务就绪。

游戏目录只部署 `d3d12.dll` 与 `NTE_Capture.dll`；Loader 独立运行目录只准备 `NTE_Capture.dll`。
已部署检查逐文件报告是否存在、实际大小与哈希、是否匹配随附整包、本机记录或已核实旧版本。
已确认模式允许自动部署且游戏退出后，匹配旧版本名单的组件即使没有本机部署记录也可升级；写入前再次复核检测时
的文件哈希，目标变化则取消。成功后登记新组件，后续更新和清理沿用本机记录。不读取旧工作区注册表，
不把其他工具文件的存在视为删除理由。Core、许可和来源留在应用目录。原生会话只选择清单中已核对的 Core。

采集组件先由 Toolkit 核对并与 Core 成套交付给 Calc。交付只包含经核对的无 UI 采集二进制、必要依赖、许可和
公开组件清单，不包含私有源码、源码归档、调试符号、内部构建输入明细或工具界面/MCP。二进制也须核对实际依赖
和内置功能，不能只凭扩展名判断可公开。开发工具自身继续在其独立仓库维护。

文件匹配不证明加载、管道、hello 或业务就绪。正常 Calc 使用不要求用户打开独立开发工具或按键初始化；
采集组件在合适的游戏阶段自行初始化，Calc 沿用现有等待与错误检测。实际交付和实机验收分别记录。

## 无界面采集链构建输入与发行映射

构建、安装器及发布验证按清单布局选取同一套输入。原生清单仅允许固定采集程序、公开组件说明、配套 JSON 和明确的许可文件名；所有 Core 依赖许可必须逐文件列入清单。源码、归档、调试符号和未声明成员不得进入发行目录。D3D 与采集 DLL 映射到资源根目录，Core 映射到 `nte-core.exe`，许可及来源映射到 `licenses/native-capture/`；不携带旧 Mods 工作区。

可选 Loader 必须成套声明 `loader`、`loader_license`、`loader_source` 角色与其第三方许可；缺少该组时 D3D 发行仍可构建，Loader 不随包出现。已声明 Loader 的程序映射到 `nte-mod-loader.exe`，公开元数据和依赖许可映射到 `licenses/mod-loader/`。

发行清单完整保留来源提交、输入摘要、能力、协议、字节数及额外公开版本声明，仅转换文件与角色路径。程序不得在打包期间再次 UPX 改写已核对字节。安装器及复用既有产物的发布校验核对当前来源清单、所有实际文件、完整许可目录以及清单外成员；不同布局不能互借旧 DLL 或旧脚本通过门禁。

## 旧脚本链构建输入与发行映射

构建必须先提供有来源证据的源码清单。清单的 `files` 须完整覆盖实际选择的代理、Loader、Core、全部工作区输入，
以及组件的许可证、来源和随附元数据；不得漏项，也不得包含未选择的文件。三类组件的 `LICENSE` 和 `SOURCE.md`
是构建必需项。新增元数据或依赖许可必须先进入明确的发行文件范围，不能通过递归目录收集带入未经核对的源码。

`tools/release/game_component_bundle_build.py` 对实际选择的输入逐项核对源清单哈希，再暂存并生成发行路径清单。
环境变量覆盖路径也执行同一核验；相同哈希的异地文件可使用，内容变化则必须先重新审核并更新来源清单。
构建不会根据当前 Git 状态或新文件摘要补造 `source_commits`，发行清单只转换路径，保留已批准的来源与哈希。

代理、Loader 与 Core 分别映射到资源根目录的 `dwmapi.dll`、`nte-mod-loader.exe`、`nte-core.exe`，工作区映射到
`plugins/`，组件元数据映射到 `licenses/`。PyInstaller 携带该发行清单；单目录构建结束、安装器生成前及发布校验
均复核资源目录中的清单与实际字节。安装器和发布校验还核对发行清单与当前已批准来源，不能用另一个版本的自洽
清单通过验收。来源核对与构建共用明确的路径映射，逐路径比较全部文件哈希，包括许可与来源记录；未知来源路径、
文件内容及清单哈希互换均不能通过。关键输入或来源缺失时拒绝构建，不删除已有应用构建产物后才发现清单错误。

最终门禁还完整枚举 `plugins/` 与 `licenses/nte-core/`、`licenses/mods-plugin/`、`licenses/mod-loader/`，
实际文件必须与清单声明一致；清单外文件、无对应声明文件的额外目录、文件或目录链接及重解析点均拒绝。
跳过应用构建而复用既有发行目录时执行同一检查；该枚举范围不扩展到 Qt、Python 或其他组件的发行资源目录。

这些门禁已通过临时组件测试；真实组件整包、PyInstaller 输出、单文件运行时解包及 Windows 安装验收仍须单独执行。

## 原生整套部署

D3D 手动部署先完成旧清理待办；归属冲突或清理失败时保留旧记录并阻止新部署，避免把新文件误当作旧待办删除。清理完成后重新核对模式和账号代次，再在游戏完全退出后部署固定两文件，先写采集 DLL，最后写 D3D 入口。已有同名文件先备份；
替换和回滚均使用目标同目录临时文件，支持配置备份与游戏分属不同磁盘。普通失败恢复本次写入前状态；
撤权或游戏启动时保存实际写入和此前仍归本程序管理的文件记录，交由既有退出后清理流程处理。
实际文件、管道、握手、业务快照分别核对；缺少战报或装配所需能力不阻止已声明快照域的独立检测。

Loader 保留原有明确选择、受控提权、启动器定位和协作停止机制，使用配置目录的 `native-loader` 仅准备同一个
采集 DLL。标准加载参数为 `--dll <运行目录>/NTE_Capture.dll --payload-load-mode loadlibrary`，
不得将该运行时送入旧的默认 manual-map 路径，也不登记旧脚本工作区。选择 Loader 时自动管理沿用该入口。
启动前通过 `--capabilities-json --dry-run --once` 核验当前可替换 Loader 与内嵌 shim；要求 shim 协议 3、
标准加载能力及 `payload_kinds` 中的 `nte_capture_runtime_v1`。仅旧版标准加载声明不能证明新采集运行时适配。
Calc 采用既有启动提权流程，普通非提权测试的错误不代表正常 Calc 加载失败。不使用固定 Loader SHA 白名单。

启动期间冻结模式、路径、选择与配置代次；预检或清理期间选择变化会取消旧请求。已有待清理文件先完成既有清理，
再允许重试；启动后授权失效立即停止后续加载并保留文件记录。清理保留用户最新的加载方式选择。启动失败不恢复
已清理的旧 D3D 入口，独立运行目录按实际记录等待清理。采集组件完成初始化前不能把 Loader 进程存活标成业务可用。

## 手动部署检查

自动管理关闭或缺少整包清单，不妨碍单独检查手动部署：读取游戏目录的实际代理 DLL 哈希，与当前随附版本比较；
读取当前加载登记指向的实际工作区并校验工作区文件与独立采集清单。存在旧部署记录时，另列实际文件与记录哈希
是否一致，不将记录本身当作当前版本证明。不连接原生管道，也不推断完整业务快照已经就绪。

## 清理与待处理

清理只删除部署记录哈希仍匹配的代理 DLL，并移除本程序仍拥有的工作区加载登记。不恢复备份旧 DLL 或历史加载配置。
文件或登记已不存在视为已清理；未知归属、文件改写、目录占位或登记改变均报告冲突并保留现状。
游戏运行期间不得删除、替换组件或修改加载登记；返回等待游戏退出状态，不能显示已卸载。

清理结果为 `cleaned`、`waiting_game_exit` 或 `conflict`；文件/登记/进程检查失败单独返回故障。
应用保存待处理事实，并在下次启动或观察到游戏退出后重新核对。应用退出后不保留隐藏监视进程。

部署与 Loader 启动在写入前复核显式模式授权和游戏退出条件。事务失败只有在原授权仍有效且游戏仍未运行时
才可回滚；若写入后授权撤销或游戏启动，保留已写入文件的路径、哈希和工作区事实，由应用持久化待清理状态。
