# 游戏组件整包与清理契约

组件包按清单区分旧的独立采集布局与新的受限插件宿主布局。Calc 通过采集 Core 统一消费业务接口；新布局额外提供显式插件更新。两种布局均不承载开发工具界面或 MCP。新布局的验证与实际晋升分别记录，不能以源码接入代替当前包身份。

本契约定义本机应用级组件检查与清理；管道、协议握手、人物/配装、完整背包、队伍/环境及战报业务能力须另行检测。
文件检查成功不代表组件已加载，Loader 停止不代表游戏进程内 DLL 已卸载。

自动部署的写入、校验或 Loader 启动故障会保存到本机 `config/component_deployment_failure.json`，
停止同一故障的后台重试；轮询、刷新检测缓存及重启 Calc 都不会恢复部署。
用户处理原因后，可通过“检测并处理”或确认组件准备显式重试；只读预检不清除故障。
Windows 明确报告恶意软件阻止时显示系统拦截原因；临时文件消失只说明写入结果不可用，不自行判定为 Defender。

## 随附组件清单

自动管理仅消费当前 Calc 的 `component-bundle.json`。源码布局在
`third_party/native-capture/component-bundle.json`，发行布局在应用资源根目录；所有清单文件路径相对当前应用资源根目录。
PyInstaller 发行的资源根目录为 `_internal`，与主 EXE 所在目录不同；发行清单须使用该布局内的路径。
游戏代理 `d3d12.dll`、插件及签名统一存放在 `_internal/native-capture/`，
不进入 Calc 的资源根 DLL 搜索目录；Core 与 Loader 可执行文件仍在 `_internal`。
部署按清单读取隔离目录中的来源文件，再写入游戏目录或 Loader 专用运行目录的正式布局，文件名不变。
依赖扫描不从工作目录自动收集同名 `dwmapi.dll` 或 `d3d12.dll`，成包门禁同时拒绝资源根目录中的
`d3d12.dll`、`dwmapi.dll`、`NTE_Capture.dll` 和旧 `plugins/`，并核对隔离目录的完整清单与哈希。
原生安装包覆盖升级时清除 Calc 安装目录中旧的 `_internal/dwmapi.dll`；当前隔离布局还清除
旧 `_internal/d3d12.dll`、`_internal/NTE_Capture.dll` 及 `_internal/plugins/` 中 User、Combat、HUD、Performance
四个正式插件及各自签名。只删除确切文件，保留目录和其他文件；不清理游戏目录、账号、战报或工作模式配置。
配套 Core 可用性受整包校验约束；校验失败表示组件包未通过核对，不能仅据此断言 Core 可执行文件缺失。
缺少清单、来源声明、配套文件或哈希不符时，自动管理不可用，不追随外部仓库或其他安装的文件。

清单为 UTF-8 JSON 对象：

| 字段 | 契约 |
| --- | --- |
| `protocol_version` | 整数 `1`。 |
| `source_commits` | 非空的公开组件标识至来源提交十六进制摘要的映射。 |
| `files` | 根目录内 POSIX 相对文件路径至 SHA-256 的映射；检查全部声明文件。 |
| `roles` | 组件语义至 `files` 中确切路径的映射。 |

运行与部署接受显式声明 `native-capture-v1`、`native-plugins-v2` 或 `native-plugins-v3` 的组件包；新的发行输入要求 v3，旧布局仅保留读取及现有部署支持。缺少布局或旧 `legacy-mods-v1` 清单不再支持，原生包缺失或损坏时不会回退到旧 DLL、脚本工作区或其他组件副本。
所有声明角色必须分别对应文件；路径不得越界、使用绝对路径或重复键。清单不替代来源与许可证审核，也不证明实机验收通过。

## 受限插件布局与迁移

`native-plugins-v2` 复用 UETools 的无界面 Toolkit 宿主，部署 `d3d12.dll`、`plugins/NTE_PluginUser.dll`、`plugins/NTE_PluginCombat.dll` 及同名 `.dll.sig`。
声明 `performance.trace.v1` 时还须成对交付 `performance_plugin` 和 `performance_signature`，固定对应 `plugins/NTE_PluginPerformance.dll` 及其 `.sig`。
旧包没有此能力时不要求该插件。新宿主仅扩充这一明确的签名插件身份，仍拒绝任意 DLL。
在下述公共来源、哈希、大小、许可与 Core 契约之外，新增 `user_plugin`、`user_signature`、`capture_signature` 角色，且 `plugin_policy` 必须为 `calc-publisher-rsa3072-sha256-v1`。
相应角色必须绑定固定文件名；不扫描任意 DLL。首次迁移游戏必须退出，旧 NTE_Capture 不能热卸载。

v2 根据角色准备 User、Combat 及可选 Performance 和各自签名，先插件与签名、最后宿主。v3 固定加入 HUD 与 Performance，共五个 DLL、四份签名；D3D 与 Loader 专用目录保持同一布局。Loader payload 为专用目录中的 `d3d12.dll`，沿用 `loadlibrary`，额外核验 `nte_calc_host_v1` 能力；旧 Loader 不因支持独立采集 DLL 就自动兼容宿主。
发行映射保留插件子目录和签名；新布局不混入旧 `NTE_Capture.dll`。Core 和许可证仍保留在应用资源目录。
后台冷部署继续要求游戏退出。插件热更新仅供开发维护工具按 [宿主更新契约](native-plugin-host.md) 调用，允许在游戏运行、业务已停止且宿主不变时更新插件；界面不提供独立热更新按钮。
后台清理仅处理已登记的固定宿主、插件和签名路径；用户明确点击“清理游戏目录”时，按正式布局的精确文件名清理同目录旧组件及插件签名，不要求旧哈希或部署记录，不删除整个 plugins 目录。详见下文清理契约。

下文提到两个文件、单独 NTE_Capture 或 `nte_capture_runtime_v1` 的部分专指旧布局；路径归属、操作代次、失败处理、许可与文件核对规则两者共用。新布局实际分离范围、第三方限制及结果未知的处理见 [本方插件宿主](native-plugin-host.md)。

## 独立 HUD 的 v3 清单

v3 保留 v2 的宿主、User、Combat 和签名身份，新增必需 `hud_plugin`／`hud_signature`，固定对应 `plugins/NTE_PluginHUD.dll` 及其 `.sig`；Performance 及签名在 v3 同样必需。部署、记录恢复、清理、Loader 和显式更新全部按这些精确角色处理。

来源或发行中的 `capture-component.json` 必须属于整包哈希输入，其 `layout` 和 `sourceTreeSha256` 分别匹配 v3 与 `input_digests.capture`。其中保护记录的 DLL 集合必须精确覆盖五个文件，每项最终 SHA-256 匹配正式角色。五个 DLL 统一使用 `selected-functions-v1` 和 StripDebugInfo，宿主不再使用整文件 Pack／ResourceProtection；函数数量为正，声明身份及必要授权字段完整。旧整文件宿主回执不得伪装为当前函数保护交付，仍需重新生成整套清单和最终字节签名。保护与签名不代表安全检测或实机验收已通过。

每项声明是 `nte.component-notice/1`，构建方在原始 DLL 中核对并保留声明导出，Calc 按受保护哈希核对随附解析副本。授权声明与业务能力分开，不在此清单里发明私有源码权限或 AI 审查保证。

当前工作区随附包已接入重新构建的 v3 五 DLL、最终签名和配套采集 Core，来源与发行映射均通过整包核验。清单记录未提交工作树及其冻结输入摘要；本地接入不代表已发布或实机验收完成。升级必须使用重新构建和核验的整套输入，不能只把旧清单改为 v3。

## 旧独立采集组件清单

`layout: "native-capture-v1"` 选择无界面采集链。必需角色为 `host`、`capture_plugin`、`core`、
`capture_license`、`capture_source`、`core_license`、`core_source`；每个角色绑定不同的声明文件。
`host` 仅表示最小 D3D 转发入口，不是开发工具宿主；`capture_plugin` 是同目录的 `NTE_Capture.dll`。
源提交须包含 `capture` 和 `core`，`input_digests` 精确包含这两个输入集合的 64 位 SHA-256 摘要。
`file_sizes` 对全部 `files` 路径声明字节数；程序、许可与公开来源声明逐项核对大小和哈希。

可选 `upgrade_from` 记录用于诊断的已核实旧版本：键只能是游戏目录的 `d3d12.dll` 或 `NTE_Capture.dll`，
值为非空、无重复的 SHA-256 列表。名单只收录已核对来源的确切旧组件；缺少该字段的旧清单仍有效。
发行映射保留该名单，但固定文件名的自动替换不依赖命中名单。

`capture_protocol_version` 为整数 `1`。`capabilities` 是无重复的字符串列表，至少包含
`combat.hit_buff.v1`、`character.snapshot.v1`、`inventory.snapshot.v1`、`team.snapshot.v1`、`environment.snapshot.v1`。
额外能力只有在清单明确声明时才作为文件声明事实保留；运行时仍须核对 Core 握手及业务就绪。

游戏目录只部署 `d3d12.dll` 与 `NTE_Capture.dll`；Loader 独立运行目录只准备 `NTE_Capture.dll`。
已部署检查逐文件报告是否存在、实际大小与哈希、是否匹配随附整包、本机记录或已核实旧版本。
已确认模式允许自动部署且游戏退出后，按正式目录中的确切文件名替换上述组件，不要求已有文件匹配部署记录或旧版本名单。
随附新组件仍须通过整包哈希校验；写入前再次复核检测时的目标文件哈希，目标在操作期间变化则取消。
成功后登记新组件，后续更新和清理沿用本机记录。后台自动部署不接管缺少记录的旧工作区注册表，
不把其他工具文件的存在视为删除理由。Core、许可和来源留在应用目录。原生会话只选择清单中已核对的 Core。

采集组件先由 Toolkit 核对并与 Core 成套交付给 Calc。交付只包含经核对的无 UI 采集二进制、必要依赖、许可和
公开组件清单，不包含私有源码、源码归档、调试符号、内部构建输入明细或工具界面/MCP。二进制也须核对实际依赖
和内置功能，不能只凭扩展名判断可公开。开发工具自身继续在其独立仓库维护。

文件匹配不证明加载、管道、hello 或业务就绪。正常 Calc 使用不要求用户打开独立开发工具或按键初始化；
采集组件在合适的游戏阶段自行初始化，Calc 沿用现有等待与错误检测。实际交付和实机验收分别记录。

## 无界面采集链构建输入与发行映射

构建、安装器及发布验证按清单布局选取同一套输入。原生清单仅允许固定采集程序、公开组件说明、配套 JSON 和明确的许可文件名；所有 Core 依赖许可必须逐文件列入清单。源码、归档、调试符号和未声明成员不得进入发行目录。D3D 与采集 DLL 映射到资源根目录，Core 映射到 `nte-core.exe`，许可及来源映射到 `licenses/native-capture/`；不携带旧 Mods 工作区。

可选 Loader 必须成套声明 `loader`、`loader_license`、`loader_source` 角色与其第三方许可；缺少该组时 D3D 发行仍可构建，Loader 不随包出现。已声明 Loader 的程序映射到 `nte-mod-loader.exe`，公开元数据和依赖许可映射到 `licenses/mod-loader/`。

发行清单完整保留来源提交、输入摘要、能力、协议、字节数及额外公开版本声明，仅转换文件与角色路径。程序不得在打包期间再次 UPX 改写已核对字节。安装器及复用既有产物的发布校验核对当前来源清单、所有实际文件、完整许可目录以及清单外成员；不同布局不能互借旧 DLL 或旧脚本通过门禁。

## 原生整套部署

发行 Loader 与内嵌 shim 成套构建，清单同时列出程序、来源和许可。覆盖安装更新应用内 Loader，安装器将旧 Loader 与 Core 纳入占用检测。专用 Loader 运行目录中的 `NTE_Capture.dll` 与当前整包哈希一致时直接复用；旧版在游戏退出后按确切文件名更新，不要求旧记录仍存在。显式清理或退出原生模式仍按清理契约处理，不能以“当前最新版”为由保留用户要求卸下的组件。

自动部署、自动更新、自动启动 Loader 及后台退出清理只管理当前原生组件和本程序拥有的加载登记，保留游戏目录中的
`dwmapi.dll` 及其他非当前组件文件。旧代理存在不影响当前两文件的匹配判定，不触发重复部署或 Loader 重启。
只有手动确认部署原生组件、手动启动 Loader 或手动清理旧部署记录时执行旧代理退役：游戏完全退出且当前组件和授权核对通过后，
直接删除游戏主程序同目录的 `dwmapi.dll` 部署副本，不创建旧代理备份。不要求旧代理已登记或匹配旧版本白名单；
该规则仅适用于这个确切文件名，目录、链接或重解析点不删除。校验或删除失败立即中止新组件部署或 Loader 启动；
核对期间游戏启动、授权撤销或文件变化时保留现场。移除成功后不因后续失败或清理自动恢复旧代理。
即使两个新 DLL 已匹配当前版本，或 Loader 已在等待游戏，手动操作仍按上述规则处理旧代理；游戏运行中等待退出。

D3D 手动部署先完成旧清理待办；归属冲突或清理失败时保留旧记录并阻止新部署，避免把新文件误当作旧待办删除。
部署按操作授权代次核对模式、暂停与游戏路径，并独立核对账号代次和战报占用；后台保存部署记录、清理状态或自动同步偏好不取消已确认的部署，不将配置保存修订号用作操作授权代次。
清理完成后重新核对模式和账号代次；仅手动部署退役旧代理，再部署固定两文件，先写采集 DLL，最后写 D3D 入口。已有同名组件直接替换，不创建旧 DLL 备份；
新版文件使用目标同目录临时文件校验后替换。普通失败移除本次已写入的新组件，不恢复旧 DLL，可重新部署；
撤权或游戏启动时保存实际写入和此前仍归本程序管理的文件记录，交由既有退出后清理流程处理。
实际文件、管道、握手、业务快照分别核对；缺少战报或装配所需能力不阻止已声明快照域的独立检测。

Loader 保留原有明确选择、受控提权、启动器定位和协作停止机制，使用配置目录的 `native-loader` 仅准备同一个
采集 DLL。标准加载参数为 `--dll <运行目录>/NTE_Capture.dll --payload-load-mode loadlibrary`，
不得将该运行时送入旧的默认 manual-map 路径，也不登记旧脚本工作区。选择 Loader 时自动管理沿用该入口。启动或重新准备 Loader 前，除游戏进程外，还按已选安装目录解析官方启动器并核对其运行进程的完整映像路径；启动器仍在运行或身份查询未完成时等待用户关闭并重试，不结束外部进程，也不以同名其他安装的启动器替代。
启动前通过 `--capabilities-json --dry-run --once` 核验当前可替换 Loader 与内嵌 shim；要求 shim 协议 3、
标准加载能力及 `payload_kinds` 中的 `nte_capture_runtime_v1`。仅旧版标准加载声明不能证明新采集运行时适配。
Calc 采用既有启动提权流程，普通非提权测试的错误不代表正常 Calc 加载失败。不使用固定 Loader SHA 白名单。

启动期间冻结模式、路径、选择与配置代次；预检或清理期间选择变化会取消旧请求。已有待清理文件先完成既有清理，
再允许重试；启动后授权失效立即停止后续加载并保留文件记录。清理保留用户最新的加载方式选择。启动失败不恢复
已清理的旧 D3D 入口，独立运行目录按实际记录等待清理。采集组件完成初始化前不能把 Loader 进程存活标成业务可用。

## 手动部署检查

手动部署与自动管理共用原生整包与实际文件检查。检测游戏目录的 `d3d12.dll`、`NTE_Capture.dll`，或 Loader 专用目录的采集 DLL，与当前清单核对。缺少有效整包时不可部署，不使用旧工作区或旧代理作兼容回退；业务可用性继续由原生连接、握手与各域响应确认。

## 清理与待处理

退出加载模式时，已登记的原生组件按正式布局的确切文件名清理，不要求历史部署哈希匹配；Loader 运行目录内已登记的组件使用同一规则，组件升级不阻塞退出清理。用户明确点击“清理游戏目录”（包括旧组件升级引导）时，以已选游戏目录和固定文件名为本次清理范围：`d3d12.dll`、`NTE_Capture.dll`，以及 `plugins/` 下 User、Combat、HUD、Performance 四个正式插件及各自 `.sig`；不要求部署记录、旧版哈希或随附整包可用。先核对全部目标，再删除 D3D 入口和其他组件；当次哈希只用于防止核对后文件被并发替换，删除前仍复核游戏未运行、文件类型和内容未变化。目录或链接保留并报告冲突，其他文件和整个 `plugins/` 目录不在删除范围内。后台清理保留旧 `dwmapi.dll`，不会因同名目录、链接或其他工具文件阻塞登记收尾。清理只移除本程序专用旧工作区注册表值；后台检测遇到注册表与旧部署记录的工作区不同仍保持冲突，不自动接管。用户明确点击“清理游戏目录”或确认手动部署后，若旧记录有工作区且注册表值为有效绝对路径，先把当次注册的工作区写入本机 `work_mode.json` 的部署记录，再按该路径清理；记录缺失时仍采用当次值作为一次性旧版归属。删除前再次核对注册表，登记变化则保留现场及待清理记录；
手动旧代理退役另按上节执行。不恢复备份旧 DLL 或历史加载配置。
文件或登记已不存在视为已清理；正式布局以外的文件名、链接、目录占位或登记归属改变均报告冲突并保留现状。
游戏运行期间不得删除、替换组件或修改加载登记；返回等待游戏退出状态，不能显示已卸载。进程状态无法核对时按“未确认”处理，不得等同“游戏未运行”：用户显式发起的部署、清理与 Loader 启动继续执行，成败交由文件系统结果裁决；后台自动部署与自动 Loader 只在确认游戏已退出时执行。观测、报告与连接不得因未确认而永久等待，事实栏如实显示未确认。

清理结果为 `cleaned`、`waiting_game_exit` 或 `conflict`；文件与登记检查失败单独返回故障，进程检查不可核对按未确认处理，既不作为故障，也不作为游戏未运行。
应用保存待处理事实，并在下次启动或观察到游戏退出后重新核对。应用退出后不保留隐藏监视进程。

才可清除本次已写入文件；若写入后授权撤销或游戏启动，保留已写入文件的路径、哈希和工作区事实，由应用持久化待清理状态。
